# 事件总线：`base/event`

`EventBus`：类型安全的**同步**发布 / 订阅，事件类型就是 C++ 类型，不需要枚举或字符串；`ScopedSubscription`：析构时自动退订的守卫。
只有头文件（`breeze_event`，INTERFACE），依赖 `breeze_assert`（递归发布超限时用 `ASSERT_RET_VOID`），所以与它一样只在 Linux 上构建。

放在 `base/event` 而不是旧仓库的 `framework/event`：它不依赖 `App` / `Module`，一个进程里想要几条总线都行，不需要框架介入。
要让所有模块共享同一条总线，由 main 装配时创建一个、传给各模块即可。

本文记录**为什么是这个样子**。API 的细节与约束写在头文件注释里，本文不重复。

**状态**：debug / release / asan+ubsan 下通过；对关键判断逐个改坏做过变异验证（19 个，17 个被杀死，其余 2 个是行为等价，见 §4）。
**tsan 没有在本机跑过**（环境原因，见 `网络库设计.md` §11.2）；总线本身不是线程安全的（只在主逻辑线程里用），没有并发可验证，但订阅句柄的序号 / 类型编号是进程内的原子计数器，上真机前不要当作已验证。

## 1. 来源与取舍

前身来自同一位作者的两个目录，是同一个东西的两代：`cpp-wind-server/src/framework/event/EventBus.h`（2026-03-28，v0.1）→
`cpp-game-server-main/src/framework/event/event_bus.h`（2026-04-06，v0.2）。接口一样：`Subscribe<E>(handler)` / `Publish(event)` / `Unsubscribe(id)` / `Clear()`，
都是 `unordered_map<type_index, vector<订阅条目>>` 加若干辅助映射。**以 v0.2 为底**，保持接口兼容（`bus.Subscribe<PlayerLogin>(lambda)` 的写法不变），内部重写。

## 2. 在原代码里发现并处理的问题

下面是读代码推演出来的（旧版没有测试，我没有去跑它）；新实现对应的用例列在括号里。

- **回调里订阅同一类型 → 正在执行的回调被搬走**（v0.2）：`Publish` 用下标遍历 `vector<SubEntry>` 并直接调用 `list[i].handler(...)`，回调里 `Subscribe` 同一类型会 `push_back`，vector 一扩容就把元素（含正在执行的 `std::function`）搬走，回调后面再读自己的捕获物就是 use-after-free。注释里写的"`unordered_map` 链式哈希保证引用不失效"只对 map 的元素成立，对里面的 vector 不成立。现在每个订阅条目各自在堆上、地址稳定，vector 里放的是 `unique_ptr<Entry>`（`event_bus_test` `TestSubscribeInsideHandlerDoesNotMoveRunningHandler`：回调里订阅 2000 次，再读一个超出 SSO 的捕获字符串）。
- **`Clear()` 之后新订阅的被一起清掉**（v0.2）：发布期间 `Clear` 只置 `pending_clear_`，最外层发布结束时 `handlers_.clear()`，把 `Clear` 之后才订阅的也清了。现在 `Clear` 只标记调用时已经存在的条目，之后新订阅的不受影响（`TestClearInsideHandler`）。
- **嵌套发布别的类型时，已取消的条目不释放**（v0.2）：清理只在最外层那个类型的列表上做，嵌套类型里被取消的条目（连同回调捕获的资源）一直留到下一次那个类型在最外层发布。现在每个类型各自在它的"正在发布层数"回到 0 时清理（`TestCancelledEntriesAreReleasedPromptly`）。
- **回调抛异常后深度计数不复位**（v0.2）：`++publish_depth_` / `--publish_depth_` 之间没有 RAII，抛一次深度就多 1，抛 8 次之后所有发布都被当成递归丢弃，延迟清理也再不执行。现在用守卫（`TestHandlerThrows`：连抛 24 次，仍然能正常发布）。
- **`Publish` 里取消没有生效**（v0.1）：先把整个订阅列表拷贝一份（每次发布都复制所有 `std::function`，要分配），再检查拷贝里的 `cancelled`——回调里退订后面的订阅者，拷贝里的标记不会变，它在这次发布里仍然会被调用。现在直接检查真实条目的标记（`TestUnsubscribeInsideHandler`），也不拷贝。
- **`SubId -> hash_code -> type_index` 的间接映射**（v0.1）：两个类型的 `hash_code` 碰撞时（`hash_to_type_.emplace` "已存在时不覆盖"）退订会找错类型的列表。v0.2 改成了直接映射；现在更进一步，句柄里直接带类型编号，不需要任何 id → 类型的表。
- 依赖 `logger` 与 `NonCopyable`、头文件里用 `assert`：现在递归超限走 `ASSERT_RET_VOID`（Debug 崩、Release 丢弃并按调用点限流记日志），不再依赖 logger 头。

## 3. 设计

- **类型 → 订阅表是数组下标**：每个事件类型第一次被用到时从一个进程内的原子计数器领一个小整数（函数内 `static`），总线里是 `vector<unique_ptr<Slot>>`，`Publish` 是一次数组索引，不是哈希表查找。`const E` 与 `E` 是同一个类型（`remove_cvref`）。按**静态类型**分发：发布 `const Base&` 只通知订阅 `Base` 的（`TestDispatchIsByStaticType`）。
- **订阅句柄**：高 24 位是类型编号 + 1，低 40 位是进程内唯一的序号。所以退订不需要映射表；拿另一条总线的句柄来退订不会误伤（序号全进程唯一，`TestUnsubscribe`）。
- **发布语义**：只通知发布开始时已经存在的订阅者（回调里新订阅的从下一次起生效）；回调里被退订、还没轮到的不会再被调用；订阅者按订阅顺序调用。
- **延迟清理**：退订 / `Clear` 只置 `cancelled`，等那个类型的"正在发布层数"回到 0 再真正删除；没在发布时立刻删除。删除时先把状态整理好，**最后才销毁回调**——回调的捕获物的析构函数里再来订阅 / 退订（甚至订阅一个新类型让槽数组扩容）都是安全的（`TestHandlerDestructorMayTouchTheBus`）。`Slot` 在堆上，所以回调里订阅新类型让 `slots_` 扩容也不影响正在发布的那个。
- **递归深度**：全总线一个计数，跨类型的环（A 的回调发布 B、B 的回调又发布 A）也能拦住，上限 `kMaxPublishDepth = 8`。超限是编程错误：Debug 下 abort，Release 下丢弃这次发布并记日志。
- **回调类型**：任何能用 `const E&` 调用的东西，包括只能移动的、`mutable` 的、返回值被忽略的；内部是 `std::move_only_function`。
- **`ScopedSubscription`**：只能移动，析构 / `Reset()` 退订，`Release()` 放弃管理。注意它不能比所属的 `EventBus` 活得更久。
- **`HasSubscribers<E>()`**：发布前先问一句，省得为没人订阅的事件构造昂贵的事件对象。

### 没做的

- **线程安全**：同步总线只在一个线程里用；跨线程要自己投递到主线程再 `Publish`（`framework/app` 的 `Notify` / `IWaker` 就是干这个的）。
- **异步 / 排队的事件**（`Post`，下一帧再投递）：旧版没有。需要避免重入时可以在回调里把事件放进自己的队列，等 `Tick` 时再 `Publish`。
- **优先级、事件继承分发、通配订阅**：旧版没有，也没有人要。

## 4. 验证

- `event_bus_test`：分发、按静态类型、各种回调形态、退订、四种回调里的重入（订阅 / 退订 / `Clear` / 嵌套发布）、递归深度（含跨类型的环）、回调抛异常、`ScopedSubscription`、生命周期（捕获物的引用计数）。
  另有与朴素"快照语义"参考实现的随机对照：3 个事件类型、随机订阅 / 退订 / 发布 / `Clear`，回调里按脚本再订阅新的、退订别人、退订自己、`Clear`、嵌套发布，两边的调用序列与订阅者个数必须逐步一致（300 个种子 × 150 步）。
- 变异验证（`/tmp` 里的隔离副本上逐个改坏关键判断，要求至少一个测试失败）：19 个，17 个被杀死。没被杀死的两个都是行为等价：`ScopedSubscription::Release` 里不清 `bus_`（`id_` 已经清成无效值，守卫照样不会退订）；`Publish` 开头的"条目为空就返回"（只是少进一次守卫，只在递归超限时能看出区别——会多触发一次不必要的断言）。
- 递归超限的用例把断言模式强制成 Release（丢弃路径）；Debug 路径（abort）由 `assert_fatal_test` 覆盖，没有为总线单独再测。
- **没验证的**：tsan（见文首）。
