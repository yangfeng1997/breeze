## 0. 结论速查

### 要做

1. Reactor 线程池，one loop per thread；回调默认在 IO 线程，业务经 `MainLoopExecutor` 回投 app 主循环，保持「主循环单线程、业务无锁」。
2. 一个 `Connection` 同时承载 TCP 与 UDS，差异只在建立时，热路径没有 `if tcp`。
3. 连接生命周期只有一套机制：`ConnectionHandle`（generation）+ 延后回收，不叠加引用计数或 weak 句柄。
4. 背压用 `PauseRead`，不阻塞 IO 线程；写缓冲靠 `HighWaterMark` 兜底。
5. 断线 fail-fast：断开立即 `OnClosed`；`StreamClient` 未连通时 `Send` 立即失败，不暗中缓冲。
6. 错误走 errno 返回值，库内不抛、不 catch。

### 不做（理由见 §8）

io_uring、TLS、WebSocket、DNS 解析、RPC 相关性/deadline/取消、有限次数重连；（UDP/KCP 已作为 rudp 实现，见 §4.14；它自己的不做项在那一节）
群发、鉴权、限流策略、心跳内容、客户端协议格式一律留给应用层；sidecar 转发面暂不做。

### 不变量（见 §7，改设计前先看）

句柄不串话；每连接恰一个 `OnClosed` 且在最后一个 `OnMessage` 之后；`Send` 只有 `Ok`/`Closed` 两种结果；
解码错误即关闭；`Connection&` 只在其 IO 线程使用；`base/net` 不依赖主循环；回调 `noexcept`；net 库内不抛不 catch。

## 1. 背景与范围

### 1.1 要承载的几类链路

| 链路 | 传输 | 特点 |
|---|---|---|
| 客户端 ↔ 服务器（gate 接入） | TCP | 连接数多（1e4~1e5），慢消费者、半开连接、恶意包 |
| app ↔ sidecar | UDS | 同机、低延迟、可校验 peer 身份，sidecar 崩溃要让 app 立刻知道 |
| sidecar ↔ sidecar | TCP | 少量长连接，需自动重连 |
| 服务内部 | TCP/UDS | 同上 |
| 客户端 ↔ 网关（弱网、要低延迟） | rudp（KCP） | 凭控制面发的票据握手；不自动重连；v1 无加密（§4.14） |

现状：`src/cpp/framework/app` 已有单线程主循环 + `IWaker`/`Notify()`。
网络库在传输层落实「主循环单线程、业务无锁」「断线 fail-fast」「句柄不串话」等约束。

### 1.2 范围与边界

- Reactor 线程池（one loop per thread）；回调默认在 IO 线程，可经 `MainLoopExecutor` 投递回 app 主循环。
- Linux epoll；`EventLoop` 直接使用 epoll，不设 poller 抽象。
- 传输层 + 可插拔 `FrameCodec`；RPC 相关性、deadline、取消属于上层。
- 无锁队列独立成 `base/queue` 公共库，基于 moodycamel，业务层同样可用。
- `base/net` 不认识主循环：回投主循环的事件队列、`Notify`、`Drain` 只在 `framework/net`。
- 本阶段只做基础库，不做 sidecar 转发面。

### 1.3 设计准则

- 每个公开类型都要能指向本文某条需求，否则不加；概念多少由需求决定。
- 连接生命周期只有一套机制：`ConnectionHandle`（generation）+ 延后回收。
- 每个行为都能用一句话规则说清，说不清就是设计有问题。

## 2. 命名约定

名字取自 muduo / Netty / asio / gRPC / brpc 的既有术语，风格与仓库一致：类型与方法 PascalCase，成员 `name_`，枚举 `enum class` + PascalCase。

| 概念 | 名字 |
|---|---|
| IO 线程上的事件循环 | `EventLoop`（内部类型，不公开） |
| 一组 `EventLoop` + 线程 | `EventLoopGroup` |
| 进程级 group 注册表 | `GroupRegistry`（内部） |
| 拥有 fd 的 RAII 句柄 | `UniqueFd`（内部，只能移动、析构关闭） |
| 连接建立后按类型设 socket 选项 | `ConfigureSocket`（内部；TCP 的选项在 `tcp/`，UDS 的在 `uds/`） |
| 监听一个 endpoint | 传输无关的接口 `NetServer`；实现：`TcpServer` / `UdsServer`（共用基类 `StreamServer`，内部用 `Acceptor`）、`RUdpServer`（一个 UDP socket，见 §4.14） |
| 类型化的端点 | `TcpEndpoint`、`UdsEndpoint`、`RUdpEndpoint`（`Endpoint` 的外壳，构造即校验，只能从自己那一类的写法得到；三者互不接受对方） |
| TCP 专有的选项 | `TcpOptions`（keepalive、`TCP_USER_TIMEOUT`）；UDS 的选项类型里没有这些字段 |
| 连接一个对端并重连 | 传输无关的接口 `NetClient`；实现：`TcpClient` / `UdsClient`（共用基类 `StreamClient`，内部用 `Connector`）、`RUdpClient`（凭票据握手、不自动重连）；选项里有 `on_connect_failed`、`connect_timeout` |
| 一条已建立的连接 | `Connection`（接口，只在 IO 线程使用，没有数据成员）；字节流的实现是内部类型 `StreamConnection`，rudp 的是 `RUdpConnection` |
| rudp 的准入票据 | `RUdpTicket{conv, token}`；服务端 `IssueTicket / AddTicket`，客户端 `SetTicket`；内部 `TicketTable` |
| rudp 的传输参数 | `RUdpOptions`（mtu、窗口、interval、nodelay、dead_link、`max_message_size`、`flush_on_send`、套接字缓冲） |
| rudp 的内部件 | `KcpSession`（ikcp 的封装）、`UdpSocket`（注册在 `EventLoop` 上的 UDP socket）、`rudp_protocol.h`（线格式） |
| 跨线程安全的连接句柄 | `ConnectionHandle`（8 字节、可平凡复制，`group:4 \| loop:8 \| slot:20 \| generation:32`） |
| 回调接口 | `ConnectionHandler`：`OnConnected / OnMessage / OnClosed` |
| 在主循环上执行回调 | `MainLoopExecutor`，业务回调接口 `MainLoopHandler` |
| 分帧编解码 | `FrameCodec`、`LengthPrefixCodec`、`FrameCodecFactory` |
| 读缓冲 | `Buffer` |
| 引用计数的不可变字节块 | `SharedBuffer`（`(block, offset, len)` 切片值，最终名字） |
| 对端信息 | `PeerInfo{endpoint, credentials}`（两者都可空：UDS 客户端通常未命名，credentials 只有 UDS 有）、`PeerCredentials{uid,gid,pid}` |
| 每连接用户数据 | `ConnectionContext`（带虚析构的基类） |
| 接受前过滤 | `AcceptFilter`（`StreamServer` 选项） |
| 暂停/恢复读 | `PauseRead / ResumeRead` |
| 发送水位 | `HighWaterMark`（发送侧） |
| 发送结果 | `SendResult{Ok, Closed}` |
| 慢消费者关闭原因 | `CloseReason::SlowConsumer` |
| 优雅关闭单个连接 | `CloseGracefully(timeout)` |
| 整组停机 | `EventLoopGroup::Shutdown(deadline)`；`StreamServer::Stop()` 只停 accept；`StreamClient::Stop()` 停重连并关闭当前连接 |
| 统计 | `GetStats() -> NetStats` |
| 跨线程投递到 loop | `EventLoop::Post` |
| 断言当前在 loop 线程 | `EventLoop::AssertInLoopThread()` |
| 线程封装 | `Thread`（`pthread_create`，在 `base/thread`，见 [线程基础库.md](线程基础库.md)） |
| 空闲超时 | `idle_timeout`（默认 0 = 关闭）、`last_active_time` |
| 队列 | `SpscQueue / MpscQueue`、`Enqueue / TryEnqueue / TryDequeueBulk`、`ProducerToken`、`SizeApprox` |
| 重连退避 | `ReconnectPolicy{initial_delay, max_delay, multiplier, jitter}` |

业务用的是 `TcpServer` / `UdsServer`（客户端同理）：端点与选项按传输类型化，TCP 专有的选项只出现在 TCP 的选项类型里。
它们共用基类 `StreamServer` / `StreamClient`（TCP 与 UDS 都是字节流，accept / 重连 / 背压的逻辑只写一份），基类收通用的 `Endpoint` 与
`StreamServerOptions` / `StreamClientOptions`，给"按端点种类分派"的代码用：`NetModule` 按配置里的 `tcp://` / `unix://` 字符串选类并经基类指针持有，
测试按端点参数化。不叫 `Server` / `Client`（避免与上层 RPC 层冲突）。
`NetServer` / `NetClient` 是**传输无关的接口**（`Start` / `Stop` / `endpoint()`，客户端另有 `Send` / `handle()`）：`StreamServer` / `StreamClient` 与 `RUdpServer` / `RUdpClient`
都实现它，`NetModule` 经它持有各种服务端与客户端。这两个名字原先是 TCP 与 UDS 共用的那个具体类（一个类同时管两种传输，TCP 专有的选项配在 UDS 上被静默忽略）；
具体类改叫 `StreamServer` / `StreamClient`，`NetServer` / `NetClient` 留给接口——有了并列的 rudp 实现之后，只有接口才配得上不带传输前缀的名字。

**内部名字的取法**（只在 `base/net/` 内可见的类型与函数；改名之前先看这里，免得来回）：

- **前缀表示归属**：`EventLoop*`（`EventLoop` / `EventLoopGroup` / `EventLoopThread` / `EventLoopOptions`，对应 muduo 的 `EventLoopThread`）；`tcp::` / `uds::` 命名空间放各自专有的函数，`sock::` 放字节流共用的。
- **函数名写明做的是什么**：`sock::CreateStreamSocket`（以后数据报是另一个名字）、`sock::GetSocketError`（读 `SO_ERROR`，原名 `SoError` 太隐晦）。
- **动词在前**：`RegisterIdle / UnregisterIdle / SetIdlePaused / TouchIdle`，与同一个类里的 `AddShutdownHook / RemoveShutdownHook` 一致。
- **函数类型的别名带 `Callback` 后缀，不用 `Fn`**：`ConnectFailedCallback`。
- **"Transport"一词留给传输抽象**（TCP / UDS / KCP 之间的差别；现在各传输各有自己的类，没有统一的 `Transport` 类型），所以"建立后设 socket 选项"叫 `ConfigureSocket`，不叫原来的 `SetupTransport`。
- 文件名与类名对应（`UniqueFd` ↔ `unique_fd.h`），目录名按传输类型（`tcp/`、`uds/`）或层次（`core/`、`stream/`）。
- **可靠 UDP 的类型名与函数名写 `RUdp`**（`RUdpServer`、`RUdpClient`、`RUdpEndpoint`、`AddRUdpServer`）：`R` 是 Reliable 的首字母、`Udp` 与 `UdpSocket` 同写法，读起来是"可靠的 Udp"；
  文件名、命名空间、CMake 目标仍是小写 `rudp`（`rudp_server.h`、`rudp::`、`breeze_net_rudp`），宏与环境变量是 `RUDP_`。

**考虑过、决定不改的名字**（理由都是"改动面大于收益"或"会撞别的概念"）：

| 名字 | 为什么不改 |
|---|---|
| `ConnectionHandle` 与 `ConnectionHandler` 只差一个字母 | 两个都是行业通用词（Netty 的 `ChannelHandler`、brpc 的 `SocketId` 式句柄）；改任何一个要动 60 多处代码与文档；类型出现的位置能区分（前者按值传，后者总是引用） |
| `Pollable` | 改成 Reactor 教科书里的 `EventHandler` 会与 `ConnectionHandler`（用户回调）撞概念 |
| `GroupAccess` | 只有内部与测试用的友元访问器 |
| `LoopStats` / `LoopServer` | 名字表达的是归属（"每个 loop 一份的计数""绑在一个 loop 上的服务端"），不是 `EventLoop` 类的一部分 |
| 全部类型平铺在 `namespace breeze` | 与仓库其它库一致；只有 `sock` / `tcp` / `uds` / `str` 这类放函数的小命名空间 |

## 3. `base/queue`：通用无锁队列库

业务层也会用，所以是 `base/` 下的独立公共库。

- `breeze_queue` 为 `INTERFACE` 库，链接 `concurrentqueue::concurrentqueue` 与 `readerwriterqueue::readerwriterqueue`
  （模板必须在头文件里，所以依赖经 target 传递）。
- 用 `<moodycamel/concurrentqueue.h>` 与 `<readerwriterqueue.h>`，不用已 deprecated 的 `unofficial-concurrentqueue`。
  vcpkg 端口 `concurrentqueue` 1.0.5、`readerwriterqueue` 1.0.7 均在 manifest baseline 内；两个端口都没有 `usage` 文件，
  target 名 `concurrentqueue::concurrentqueue`、`readerwriterqueue::readerwriterqueue` 已按安装后的 `*Targets.cmake` 核实。
- **TSAN 对 `ConcurrentQueue` 有误报**：它用 `atomic_thread_fence` 同步（如 `Block::is_empty`），TSAN 不建模 fence，
  会报"生产者复用已读完的槽位"的数据竞争（作者在 `concurrentqueue.h` 里承认，`ReaderWriterQueue` 则整体标了 `no_sanitize`）。
  用 `src/cpp/tsan.supp` 只压制带 `moodycamel::ConcurrentQueue` 帧的报告，ctest 在 `tsan` 预设下自动带上；自己代码里的竞态照常报出。
- **对外 API 不暴露 moodycamel 任何类型**（含令牌），以后换实现业务代码不动。

| 类 | 约束 | 接口 |
|---|---|---|
| `SpscQueue<T>` | 恰一个生产线程、一个消费线程 | `Enqueue`（无界，不失败）、`TryEnqueue`（不分配，失败返回 false）、`TryDequeue`、`TryDequeueBulk(out, limit) -> n` |
| `MpscQueue<T>` | 多生产线程、一个消费线程 | 同上；另有 `MakeProducerToken()` 返回 RAII `ProducerToken` |

契约（写进头文件注释）：

- `TryDequeueBulk` 返回 `n < limit` ⇒ 队列已空。
- MPSC 只保证**每个生产者内部有序**，跨生产者无全局顺序。
- `TryEnqueue` 失败 = 没有预分配空间，**不是容量上限**；需要硬上限的调用方自带计数。
- 队列不负责唤醒；不提供阻塞版本。
- Debug 构建记录首个生产者/消费者线程 id，违反线程角色即断言。
- `SizeApprox()`；峰值由消费者在每次批量出队前采样，生产者路径零额外开销。

## 4. `base/net`

### 4.1 组件划分

| 本库 | muduo 对应 | 持有什么 | 职责 |
|---|---|---|---|
| `EventLoopGroup` | `EventLoopThreadPool` | N 个 `EventLoop`、N 个线程 | `Start/Shutdown`（启动时登记、结束时注销 `GroupRegistry`）；私有的 `PickLoop`；汇总 `GetStats`。不路由 `Send/Close` |
| `EventLoop` | `EventLoop` | epoll fd、eventfd 与 `sleeping` 标志、任务队列、`ConnectionTable`、本 loop 的 `Connection`、最小堆定时器、统计计数 | 一个线程上的全部 IO；idle 扫描；`Post` |
| `TcpServer` / `UdsServer`（基类 `StreamServer`） | `TcpServer` | `Acceptor`、`Endpoint`、选项（含 `AcceptFilter`）、`ConnectionHandler&`、`FrameCodecFactory&` | 一个对象一个 endpoint；accept 后选 loop、把 fd 交过去 |
| `TcpClient` / `UdsClient`（基类 `StreamClient`） | `TcpClient` | `Connector`、当前连接句柄（`std::atomic<uint64_t>`）、`ReconnectPolicy`、`ConnectionHandler&`、`FrameCodecFactory&` | 一个对象一个对端；固定在一个 loop 上（重连定时器也在这里）；自己不建线程 |
| `Connection`（接口）/ `StreamConnection` | `TcpConnection` | `StreamConnection`：socket、读 `Buffer`、写队列、`FrameCodec` 实例、`ConnectionContext` | 一条连接的全部读写、水位、半关闭 |
| `ConnectionHandle` | — | 64 位 id（不含指针） | 可复制的值；`Send/Close/CloseGracefully/PauseRead/ResumeRead` 经 `GroupRegistry` 找到所属 loop，校验后 `Post` |

- gate 要同时监听 TCP 与 UDS：建两个 `StreamServer`，共用一个 `EventLoopGroup`；需要不同线程数的链路用不同的 group。
- `StreamServer`/`StreamClient` 只持有 handler 与 `FrameCodecFactory` 的引用，调用方保证它们比 `Shutdown` 活得久（`Shutdown` 之后不再有回调）。
- **`StreamServer`/`StreamClient` 对象自己的生命周期必须覆盖到 `EventLoopGroup::Shutdown` 返回之后**：`Stop()` 是异步的，loop 上可能仍有引用 `this` 的任务和定时器。
  运行期按服务发现动态增删对端所需要的"停止完成通知"（如 `on_stopped`）暂不做，见 §8。
- 启动顺序：`StreamServer`/`StreamClient` 的 `Start()` 之前必须已 `EventLoopGroup::Start()` 成功，否则按编程错误处理。

### 4.2 一个 `Connection`，不分 TCP / UDS

差异只在建立时，不在热路径。

- `Endpoint` 值类型：`Tcp(ip,port) | Udp(ip,port) | Unix(path) | UnixAbstract(name)`，可从 `tcp://h:p`、`udp://h:p`、`unix:///p`、`unix-abstract://n` 解析
  （`udp://` 给数据报传输用，即 rudp；TCP 与 UDP 的地址写法与校验完全一样，字节流的类不收 UDP 端点：`StreamServer` / `StreamClient` 的 `Start` 返回 `EPROTONOSUPPORT`；
  `NetModule` 把 `udp://` 的 `AddServer` 分派给 `RUdpServer`，`AddClient` 不收 `udp://`（rudp 客户端要票据，见 §4.14））
  （配置里直接写字符串，走 `config/schema`），解析返回 `std::optional<Endpoint>`。**只接 IP 字面量，不做 DNS**：`getaddrinfo` 阻塞，不能在 IO 线程跑。
- `Endpoint` 的构造约束（三个工厂函数与 `Parse` 都返回 `std::optional`，拿到手的一定合法）：IP 规范化后保存（`::1` 与 `0:0:0:0:0:0:0:1` 相等）；
  v6 必须写方括号、方括号里必须是 v6（避免 `::1:80` 的歧义）；`Unix` 路径必须是绝对路径（相对路径依赖进程工作目录）；
  路径与抽象名都不能含 `'\0'`（`inet_pton` 遇到内嵌 `'\0'` 会悄悄截断成合法地址）。
- 建立连接时按 Endpoint 分支设选项（`ConfigureSocket`；TCP：`NODELAY`、keepalive，函数在 `tcp/`；UDS：取 `SO_PEERCRED` 填进 `PeerCredentials`，函数在 `uds/`）。`Connection` 以上不出现 `if tcp`，无传输层虚函数。
  TCP 专有的选项（`keepalive_*`、`tcp_user_timeout`）在 `TcpOptions`（`tcp/tcp_options.h`）里，只出现在 `TcpServerOptions` / `TcpClientOptions`；
  `UdsServerOptions` / `UdsClientOptions` 里没有这些字段（以前配在 UDS 上会被静默忽略，现在写不出来）。
  只有通用的 `StreamServerOptions` / `StreamClientOptions`（基类与 `NetModule` 的显式选项重载用）同时带 `tcp`，对 UDS 端点不看它。
- UDS 契约：路径 ≤107 字节，超长报错；bind 前对残留 socket 文件做 connect 探测，无人监听才 unlink，有人监听报 `EADDRINUSE`。

### 4.3 `ConnectionHandle`：generation 与 group 注册表

`ConnectionHandle` = 64 位 `[group:4 | loop:8 | slot:20 | generation:32]`
（限制：每进程 ≤16 个 group、每 group ≤256 个 loop、每 loop ≤2^20 个连接）。8 字节、可平凡复制，提供 `==` 与 `std::hash`，可直接作 map 的键；日志打印为 `g<group>.l<loop>#<slot>.<generation>`。
**raw == 0 恒为无效句柄**：generation 从 1 起（2^32 次复用不可达，不处理回绕），所以 `StreamClient` 的 `atomic<uint64_t>` 可用 0 表示无连接。
**位宽校验**：`EventLoopGroup::Start()` 校验 `io_threads` 在 1 到 256、`max_connections_per_loop` 在 1 到 2^20，否则返回 `EINVAL`。

与 brpc 的 `SocketId`（32 位 version + 32 位 slot，全局解析）同构；区别是多一层 `GroupRegistry`，且不用引用计数。

**连接表**

- `ConnectionTable` 是 generational slot map，每个 `EventLoop` 一张，按 `max_connections_per_loop` 预分配。
- 每槽有原子的 `generation / state / pending_bytes`（热字段，槽按 64 字节对齐 `alignas(64)`，避免主线程与 IO 线程更新相邻槽造成伪共享）。
- 发送侧：`generation` 不符 → `Closed`；`pending_bytes.fetch_add(len)` 后超过 `HighWaterMark` → 慢消费者（返回 `Closed` 并投递 Close）。
  校验与累加不是原子的，**不处理**：要在两者之间槽被回收并被新连接占用，而空闲槽按 FIFO 复用（要转完整条空闲链）；即使发生，也只是新连接的 `pending_bytes` 偏差一条消息的字节数。
  brpc 的 `_unwritten_bytes` 同样在检查之后累加，水位本就是软上限。
- IO 线程写完后 `fetch_sub(len)`；回收槽时 `generation + 1`、`pending_bytes` 清零。
- **任务在 loop 线程上执行时必须再校验一次 `generation`**，不符则丢弃并释放 `SharedBuffer`——这是"迟到的消息/事件不会串到新连接"的第二道保证。
- `last_active_time` 放在**单独的连续数组**里（只有所属 IO 线程访问），idle 扫描不碰 `Connection` 对象。
- 空闲槽按 FIFO 复用，拉长同一槽的复用间隔。连接状态（`Connecting | Connected | Disconnecting | Disconnected`）是槽里的原子量。
- `EventLoopGroup::PickLoop()` 选当前连接数最少的 loop，避免"某个 loop 满了总量没满却拒绝 accept"（muduo 为 round-robin，见 §10.2）。

**注册表**

- 进程级 `GroupRegistry`：固定 16 项的原子指针数组。`EventLoopGroup::Start()` 分配第一个空位作为 group 编号（使用方不指定），16 项用满返回 `ENOSPC`；`Shutdown`/析构末尾注销。
- 任意线程 `ConnectionHandle::Send` 的解析顺序：按 `group` 位取 group（空 → `Closed`）→ 校验 `loop`、`slot` 是否越界（越界 → `Closed`）→ 校验槽的 `generation` 并累加 `pending_bytes`（不符 → `Closed`）→ `Post` 给所属 loop。
- **group 销毁后其句柄作废**：解析不到时返回 `Closed`；若同一编号已被新 group 占用则不再保证；使用方须在销毁 group 前丢弃其句柄，并保证销毁时没有线程仍在 `Send`。
- 重连得到新句柄，迟到的消息/事件带旧句柄，不会串到新连接。

### 4.4 回调模型：`ConnectionHandler`

`base/net` 里只有一种回调，在连接所属 `EventLoop` 的 IO 线程上执行。

```cpp
struct ConnectionHandler {                      // 回调都在 IO 线程，必须非阻塞、noexcept
    virtual void OnConnected(Connection&) noexcept {}
    virtual void OnMessage(Connection&, std::span<const std::byte> payload) noexcept = 0;  // 视图，仅回调内有效；唯一必须实现的回调
    virtual void OnClosed(Connection&, CloseReason, int sys_errno) noexcept {}  // 每连接恰一次，且在最后一个 OnMessage 之后
};
```

- `Connection&`（只在 IO 线程有效，不可复制）提供 `handle()`、`Send`、`Close`、`CloseGracefully`、`PauseRead/ResumeRead`、`GetContext/SetContext`、`peer()`。
- **每连接上下文**放 `ConnectionContext`：基类带虚析构，`SetContext(std::unique_ptr<ConnectionContext>)`，`GetContext<T>()` 在 Release 下 `static_cast`、Debug 下 `dynamic_cast` 校验；避免业务按句柄再查一次哈希表。
- **接受前过滤**是 `StreamServer` 选项里的 `AcceptFilter`（`bool(const PeerInfo&) noexcept`，在 IO 线程运行）；不放进 `ConnectionHandler`，因为 `StreamClient` 也用它。
- `PauseRead/ResumeRead` 是正式的流控接口：`MainLoopExecutor` 用它做入口背压，业务也可用于自己的限流。
- **消息所有权**：`OnMessage` 的 payload 是读缓冲上的视图，只在回调内有效，要保留就自己拷贝。IO 线程路径因此零分配；拷贝只发生在真正需要跨线程的地方——`MainLoopExecutor` 入队时。
  在回调里立即回包不需要先拷：用 `Send(std::span<const std::byte>)`（见 §4.6），它直接从视图写出，写不完的部分才由库拷走。
- IO 线程回调适用于不需要业务状态的前置处理与低延迟路径，具体做什么由应用层实现。
- 默认给业务用的是 `framework/net` 的 `MainLoopExecutor`（见 §5），它自己实现一个 `ConnectionHandler`。两种用法共享同一个 `Connection`；回调线程由"给 `StreamServer/StreamClient` 传哪个 handler"决定，是它们构造时的必填参数。
- **`FrameCodec` 每连接一个实例**：`StreamServer/StreamClient` 构造时收 `FrameCodecFactory`，连接建立时创建。分帧器有状态（半包、序号），不能被多线程共享。

### 4.5 `EventLoop`：任务队列与唤醒

- 提供阻塞的 `Run()` 与 `RunOnce(timeout)`，**不在内部创建线程**；线程由 `EventLoopGroup` 创建并持有。loop 可独立存在，便于测试，也为"主线程内联跑"留口子。
- **`EventLoop` 不是公开类型**：放在 `base/net/internal/core/`，`ConnectionHandle` 不指向它；`StreamServer`/`StreamClient` 的公开头只前置声明；测试以私有 include 路径直接使用，不需要 `friend`。将来做主线程内联模式时再公开。
- **公开头 `connection.h` 以路径 include 了 `internal/core/pollable.h`**（`Connection` 的基类）。所以它必须自包含（不能再 include 别的内部头），
  `PUBLIC` 的 `base/net` 路径也不能去掉；其余内部头对使用方不可见。（抽象成接口之前是三个头：`connection_table.h` 与 `unique_fd.h` 是具体类的成员，现在跟着 `StreamConnection` 走了。）
- 每个 `EventLoop` 一条 `MpscQueue` 任务队列（主线程与其他 IO 线程生产），**隐式生产者**，`TryDequeueBulk` 批量取。
  任务是小的带标签结构体 `{op, handle, SharedBuffer}`（`op` ∈ Send/Close/CloseGracefully/PauseRead/ResumeRead 等），**不用 `std::function`**，避免每次 `Send` 多一次堆分配。
  通用投递 `Call`（`unique_ptr` 持有可调用对象，这一次分配只发生在通用投递上）与 `Quit` 之外，对连接的热路径 op 是 `Send` / `Close` / `CloseGracefully` / `PauseRead` / `ResumeRead`（带 handle、一个 32 位参数、可选的 `SharedBuffer`，不分配）。
  每轮最多处理 4 批（每批 64 个）任务，剩下的留给下一轮：下一轮睡前复查会取到它们，所以既不会在还有任务时睡着，也不会让"任务里再投递任务"的链饿死 IO。
- **不缓存 `ProducerToken`**：按 `EventLoop` 在 `thread_local` 缓存令牌，group 销毁重建后地址可能复用而拿到失效令牌，线程退出时令牌析构也会碰已销毁的队列。基准显示成为瓶颈再引入，且令牌生命周期须随 `EventLoop` 实例管理。
- 每轮顺序：`epoll_wait` → 分发就绪事件 → 处理任务队列。处理任务期间新入队的任务（含本线程投递的）必须在下一次睡眠前被看到。`epoll_wait` 的超时取最近的定时器与 idle 扫描时间。
- 少量定时器（重连退避、`connect_timeout`、`CloseGracefully` 超时）用 loop 内最小堆；时钟由 loop 注入，测试可用假时钟。

**唤醒协议**

- 无锁队列无法精确判断"空→非空"，不能靠它决定要不要唤醒。
- 消费者维护原子标志 `sleeping`：睡前置 true，再复查一次队列再睡；生产者入队后 `if (sleeping.exchange(false))` 才写 `eventfd`（只有一个生产者会写）。消费者**无论被什么事件唤醒，醒来后先 `sleeping.store(false)`，再把 `eventfd` 读空**，否则水平触发会空转。消费者忙时零系统调用，也不丢唤醒；"不丢唤醒"测试以此为断言对象。
- **内存序全部用 `seq_cst`**：这是 Dekker 式握手，两侧都需要 StoreLoad 屏障——生产者「入队 → `atomic_thread_fence(seq_cst)` → `exchange(sleeping, seq_cst)`」，消费者「`sleeping.store(true, seq_cst)` → `atomic_thread_fence(seq_cst)` → 复查队列 → 再睡」。丢唤醒是逻辑错误而非数据竞争，TSAN 与 x86 都抓不到，所以靠规格写死，并加带超时断言的长时间压力测试。
- **所有需要唤醒 loop 的状态变化都必须走任务队列，不能只改一个标志位**：标志位不受"睡前复查队列"保护，改完到进入睡眠之间会丢唤醒。
  `Quit()` 因此也是一个 `Quit` 任务；`quit_` 只在 loop 线程上读写。

### 4.6 写路径

- `Send` 返回 `SendResult{Ok, Closed}`：`Ok` 只表示网络层已接收，**不表示送达**；`Closed` 表示连接已关闭或正在关闭（句柄过期、状态非 `Connected`、或本次发送触发了慢消费者关闭），原因由 `OnClosed` 告知。
  用枚举而不是 `bool`：调用点可读，将来若要非关闭式背压，新增枚举值即可，不改签名。
- **`HighWaterMark`**（默认 256KB，内部链路按需调大）：`pending_bytes` 超过它 → 本次 `Send` 返回 `Closed`，并关闭连接（`CloseReason::SlowConsumer`）。
  这是**唯一的内建策略，作为内存安全兜底**；更细的策略（丢弃、降级、通知上游）属于应用层，留待将来的 `OnWriteBufferHigh` 钩子。
  **与先例不同**：brpc 超限返回 `EOVERCROWDED` 但保留连接，muduo/Netty 只通知应用。这里选择关闭，因为库内没有应用层策略钩子时，关闭是写缓冲有上界的唯一手段。
  检查与投递不是原子的，并发 `Send` 可能略超水位，水位是软上限。库内不设发送侧全局上限：最坏占用为连接数 × `HighWaterMark`（10 万连接约 25GB）；`pending_bytes` 对共享 payload 按每条连接各算一次，会高估实际占用。
- **`CloseGracefully(timeout)`**：连接转入 `Disconnecting`，发送队列排空后 `shutdown(SHUT_WR)`，同时启动 `timeout` 定时器，对端未在期限内关闭则强关。`Close()` 立即关。
- 出队列的每条消息是「内联帧头 + 共享的 `SharedBuffer` payload」，`writev` 一次最多 64 个 iovec（一条消息占两个），部分写记偏移；`EPOLLOUT` 仅在队列非空时注册。同一 loop 一轮内对同一连接的多次 `Send` 合并成一次 `writev`。
- **`SharedBuffer`**：引用计数的不可变块上的 `(block, offset, len)` 切片值。同一块 payload 可被多条连接同时持有，发送时不拷贝数据；应用层做群发时自己持有一组句柄循环 `Send` 即可受益。用通用分配器，不自建池（`SharedBuffer` 在 IO 线程分配、主线程释放，自建池需要跨线程归还通道）。
- **`Send` 与 `OnMessage` 对称，都只处理 payload**：帧头由该连接的 `FrameCodec::EncodeHeader(payload_len, header_out)` 生成。接口允许帧头带魔数、序号等字段，但这些属于应用协议，库不定义；逐连接加密 payload 无法让多条连接共享同一块 payload，若将来需要，放在 codec 之上并接受每条连接各一份的代价。序列化直接写进 `SharedBuffer::Create(size)`。
- **IO 线程直写**（默认开启）：IO 线程内的 `Connection::Send` 先尝试直接 `write`（写队列为空且未注册 `EPOLLOUT`），写不完才入队并注册 `EPOLLOUT`；跨线程的 `ConnectionHandle::Send` 经任务队列。
- **`Send` 有两个重载**：`Send(SharedBuffer)` 与 `Send(std::span<const std::byte>)`。
  - 视图版**不拿走所有权**：写队列为空时直接从视图写出，整帧写完就一次分配、一次拷贝都没有；写不完的部分、或前面已有积压必须排队保序时，才把内容拷成 `SharedBuffer` 入队。
    所以**返回之后视图指向的内存可以立刻改写或释放**（测试里返回后立刻把 3MB 原内存整个毁掉，客户端收到的仍是原内容）。
  - 用法：在 IO 线程里立即回包的 handler（echo、小的应答、栈上拼出来的响应）用视图版；已经有 `SharedBuffer`、要跨连接共享或要入队时用 `SharedBuffer` 版。
  - 先例：muduo 的 `send(const void*, int)` 同样是"能直接写就不拷贝，写不完才进输出缓冲"。P2a 最初只有 `SharedBuffer` 版，echo 回调手里只有仅在回调内有效的视图，只能先 `CopyFrom` 再发，
    每条消息白白多一次分配和拷贝，与 muduo 的 echo（`send(Buffer*)` 直接交换数据）并不对等（§9.1）。
- **用 `sendmsg(MSG_NOSIGNAL)` 而不是 `writev`**：对端已关闭时 `writev` 会向进程发 `SIGPIPE`，库不该替使用方改信号处置。
- **`Send` 的 payload 超过 codec 上限**（`EncodeHeader` 返回 0）：记 ERROR、以 `ProtocolError` 关闭连接并返回 `Closed`。
  对端按同样的上限会判协议错误并断开，不如本端先关，别让它带着错位的流继续跑。
- **读缓冲：线程本地优先，每连接只存半个帧**。`read` 进一块线程本地的 64KB 缓冲（所有连接共用，IO 线程一次只服务一条连接，回调里也不会再进入读路径），
  直接从它分帧；只有尾部不完整的半个帧才拷进每连接的 `Buffer`，下次读到的数据拼在它后面再解。每连接的 `Buffer` 初始容量为 0（空闲连接不占读缓冲内存），
  读空后若已长到 4KB 以上就释放（带滞后，避免稳定的跨读帧流量反复分配释放）。
  依据（P2a 基线分析，§9.1）：原先"每连接 1KB 缓冲 + 线程本地溢出缓冲"的写法，冷的每连接缓冲约让 UDS 小消息吞吐低 2.5%，且 10 万连接常驻 100MB。

### 4.7 读路径、分帧、空闲与半开检测

- 读：**水平触发，每次就绪只 `read` 一次**（最多 64KB），不循环读到 `EAGAIN`：一个灌包连接不会饿死同 loop 的其他连接。`accept` 同理。
- **事件分发顺序**：`EPOLLHUP` 且无 `EPOLLIN` → 关闭；`EPOLLERR` → 读 `SO_ERROR` 记入 `sys_errno`；`EPOLLIN`/`EPOLLRDHUP` → 读（读到 0 字节即对端关闭）；`EPOLLOUT` → 写。
- **`FrameCodec`**（每连接一个实例，有状态）：解码 `Decode(span data, sink, size_t& used) → NeedMore | Ok | Error`，sink 收到 `data` 内部的 payload 视图；编码 `EncodeHeader(payload_len, header_out) -> n`，只生成帧头（≤16 字节）。
  **`Decode` 一次最多解一帧**：`Ok` = 解出一帧并已交给 sink，`used` 是这一帧占的字节数，调用方据此推进并继续调用——这样才能在两帧之间检查连接是否已在回调里被关闭；
  `NeedMore` / `Error` 时 `used = 0`，`Error` 由调用方关闭连接。sink 是 `std::function_ref`（不分配），视图只在 sink 调用期间有效。
  接口只吃 `span`、不碰 `Buffer`，所以调用方可以直接从线程本地读缓冲分帧，只有半个帧才需要拷进每连接的缓冲。
  `EncodeHeader` 在 payload 超过上限时返回 0。`FrameCodecFactory::Create` 会被多个 loop 的线程并发调用（accept 在一个 loop，连接可能落在另一个 loop），实现必须线程安全。
  库只内置 `LengthPrefixCodec`（`u32` 长度 + `max_frame`），用于内部链路与测试；客户端协议由应用层实现自己的 `FrameCodec`。**解码错误/超长 = 关闭连接，不重新同步。**
  `max_frame` 默认值要小（如 64KB），它同时是读 `Buffer` 的上界。
- **idle timeout**：每个 loop 周期性分批扫自己的 `last_active_time` 数组（如每 100ms 扫 1/10），精度 ≤ 1s。**默认关闭**（`idle_timeout = 0`）；"活跃"= 收到任何字节，是库唯一的定义，更严格的判定（必须收到合法心跳，或按"上次完整消息时间"关闭滴灌式慢速连接）由应用层实现：`OnMessage` 只在完整帧到达时触发。
- **暂停期间不计空闲**：被 `PauseRead` 暂停的连接，idle 扫描跳过；`ResumeRead` 时刷新 `last_active_time`。
  否则后端过载、连接被长时间暂停时，开启了 idle 的连接会在过载期间被集体误杀。
- **半开连接（TCP）**：选项 `keepalive_idle / keepalive_interval / keepalive_count`（库默认 60s / 10s / 3，约 90s 发现对端消失）与 `tcp_user_timeout`；只开 `SO_KEEPALIVE` 而不设参数时内核默认 7200s，等于没开。UDS 不适用。
- 库内这类策略值默认保持中立（idle 超时默认关闭）；**生产默认值由 `framework/net` 的 `net.proto` 给出**。

### 4.8 重连、断线与停机

**`StreamClient` 状态**：`Idle ⇄ Running`。`Start()` 在 `Idle` 下合法，在 `Running` 下重复调用是编程错误；`Stop()` 回到 `Idle`。
`Start()`/`Stop()` 可在任意线程调用，**都 `Post` 到所属 loop 串行处理**，状态机只在 loop 线程上推进：先 `Stop` 再 `Start` 的顺序由队列 FIFO 保证，`Running` 下重复 `Start` 的编程错误在 loop 线程上检测。因此 `Start()` 只返回参数类错误（如 UDS 路径过长 `ENAMETOOLONG`、端点非法 `EINVAL`），连接建立失败走 `on_connect_failed`；group 未启动是编程错误，不走返回值。
`Stop()` 停止重连并**关闭当前连接**（等价 `Close()`；要优雅关闭，业务先对句柄调 `CloseGracefully`）。该连接的 `OnClosed` 仍会且仅会触发一次，在它之后该 client 不再有任何回调；`Stop()` 本身不等待。
遇到不可重试错误时，状态先回到 `Idle`，再回调 `on_connect_failed(sys_errno, will_retry=false)`（IO 线程），回调内可直接调用 `Start()`。当前连接句柄是 `std::atomic<uint64_t>`（0 = 无连接）：IO 线程在连接/断开时写，任意线程的 `StreamClient::Send` 读。

- `Connector` 持有 `ReconnectPolicy`（指数退避 + jitter、上限），**无限重试**，要停由调用方 `Stop()`；**断开立即发 `OnClosed(reason)`**。退避默认从 500ms 起翻倍、上限 30s，**连接成功后重置**。
- `StreamClient` 未连通时 `Send` 立即返回 `Closed`，**不暗中缓冲**。
- **连接失败可观测**：`OnClosed` 只在连接建立之后才有，所以 `StreamClientOptions` 带可选回调（IO 线程，`noexcept`）——`on_connect_failed(sys_errno, will_retry)`（每次尝试失败；遇到不可重试错误时 `will_retry = false`，此后不再尝试，需调用方显式 `Start()` 重来）。放在 `StreamClientOptions` 而不是 `ConnectionHandler`，因为服务端也用后者。
- **`connect()` 的 errno 分类用黑名单**：不可重试 = `EACCES`、`EPERM`、`EAFNOSUPPORT`、`EBADF`、`EFAULT`、`ENOTSOCK`、`EINVAL`、`ENAMETOOLONG`；其余一律按退避重试——含跨机常见的 `ETIMEDOUT`、`EHOSTUNREACH`、`ECONNRESET`、`ENETDOWN`，以及 `EAGAIN`、`ECONNREFUSED`、`ENETUNREACH`、`EADDRNOTAVAIL`、`EADDRINUSE`、UDS 的 `ENOENT`（sidecar 尚未创建 socket 文件）。非阻塞 connect 以 `EPOLLOUT` 就绪后读 `SO_ERROR` 判定。
  与 muduo `Connector` 同构（它对 `handleWrite` 里任何非零 `SO_ERROR` 也一律重试）；这里改成黑名单，避免白名单漏掉跨机常见的 errno。
- **`connect_timeout`**（默认几秒）：非阻塞 connect 启动时挂定时器，超时按失败重试；否则连到黑洞地址要等内核 SYN 重试约 2 分钟。muduo 没有这一项。
- TCP 连接建立后检测 **self-connect**（本地与对端的地址、端口相同），按失败处理并重试。
- **连接的销毁延后**：`Connection` 在自己的回调里被 `Close` 时不立即销毁——标记关闭、投递 `OnClosed`，fd 关闭与槽释放（generation 自增）放进本轮事件分发之后的回收列表，保证回调栈内对象仍然有效；`OnClosed` 同样在回收时回调，不在 `Close()` 的调用栈里（回调里 `Close()` 之后的代码照常跑完）；`OnClosed` 之后不再有该连接的回调。
- `CloseReason`：`PeerClosed | LocalClose | IdleTimeout | ProtocolError | SlowConsumer | IoError(errno)`。
- **`EventLoopGroup::Shutdown(deadline)`**：拒绝新的 `Start`；各 loop 停掉自己的 `Acceptor`/`Connector` → 对所有连接 `CloseGracefully` → 等各 `ConnectionTable` 变空或到 deadline，到点强关 → 停 loop、join 线程。`App` 只管启动不管停机，所以这条由网络库自己提供；析构只做兜底。`StreamServer::Stop()` 只停 accept，已接受的连接继续服务，由 `Shutdown` 收尾；`StreamClient::Stop()` 见上；两者都不影响 group。

### 4.9 可观测性

每 loop 一份 relaxed 原子计数：accept/close（按 reason）、连接拒绝数（按原因：filter / 满载 / fd 耗尽 / 新连接登记 epoll 失败）、字节/消息、`Send` 返回 `Closed` 的次数（按原因）、**event loop lag**（单轮最大耗时）、`PauseRead` 中的连接数。`EventLoopGroup::GetStats()` 累加成普通结构体 `NetStats`。
**统计不是一致快照，读它的人（包括测试）不能假定"看到事件的那一刻计数已经到位"**。各计数的记录点不同：

| 计数 | 记录点 | 观察者看到对应事件时 |
|---|---|---|
| `bytes_in` | `read` 之后、分发给 `OnMessage` 之前 | 已记上 |
| `accepted` / `connected` | `Establish()`（含 `OnConnected`）返回之后，同一个 loop 线程上 | 这条连接的第一个读事件之前已记上；只看到 `OnConnected` 回调时**可能还没记** |
| `rejected_filter` / `rejected_full` | fd 关闭之前 | 对端看到连接被关时已记上 |
| `closed[reason]` | `OnClosed` 回调之前 | 看到回调时已记上 |
| `messages_in` | **`OnMessage` 返回之后**（每次 `read` 记一次） | 回声是在 `OnMessage` 里发的，对端收到回包时**可能还没记** |
| `bytes_out` / `messages_out` | **`write` 返回之后** | 对端收到数据时**可能还没记** |

`stream_server_test` 的 `TestStatsAddUp` 曾经在客户端收到最后一条回包后立刻断言 `messages_in` / `messages_out` 等于总数，release 下约 1% 的概率读到少 1（`messages_in=119`，期望 120）；稍后再读就是 120。库的行为是对的（`net_stats.h` 头注释早就写了"不是同一时刻的一致快照"），错在测试：现在先 `WaitUntil` 这三个计数到位再取快照。压力对照（只循环这个测试，release）：改前 500 次里失败 6 次，改后 500 次加 24000 轮零失败。

事件队列深度/峰值与全局入站预算占用由 `MainLoopExecutor` 统计。

### 4.10 日志

`base/net` 只依赖 `breeze_logger`，不依赖 framework。热路径不打日志；只记连接建立/关闭（带 `CloseReason`）、重连、协议错误等状态变化，逐消息日志一律不要。
部署建议（进程配置，不是库的约束）：日志 `Overflow` 默认 `Block`，磁盘变慢会卡住 IO 线程，网络库所在进程建议配 `DropOldest`，写进 `NetModule` 的部署说明。

### 4.11 错误与异常处理（只约束 net 库）

适用范围：`base/net` 与 `framework/net`，以及 net 的依赖 `base/buffer`（`SharedBuffer` 在 IO 线程分配）与 `base/thread`（`Thread` 创建失败不抛）。`base/queue` 等其他库不受此约束。

**net 库内不 `throw`、不 `try/catch`，不引入 `Result` / `expected` / `error_code` 作为返回类型。** 按错误性质分类：

| 类别 | 例子 | 处理 |
|---|---|---|
| 建立期失败（环境/配置原因） | `epoll_create1` / `eventfd` / `socket` / `bind`（`EADDRINUSE`、`EACCES`、`ENAMETOOLONG`）/ `listen` / 创建线程 / group 注册表已满 / 选项越界（`EINVAL`） | `Start()` 返回 errno（0 = 成功），**已获取的资源自行回滚**；`NetModule` 转成框架 `Result<>`，带上 endpoint 与 `strerror`，`App` 干净退出 |
| 运行中不可恢复的系统调用失败 | 对**已注册 fd** 的 `epoll_ctl`（MOD/DEL）失败、`eventfd` 写失败 | `LOG_FATAL` |
| 资源耗尽 | 新连接 `epoll_ctl(ADD)` 遇 `ENOSPC`/`ENOMEM` | 记日志并计数，只关闭这一条新连接，进程继续（同样不产生回调） |
| 过载拒绝 | 所有 loop 的 `ConnectionTable` 都满；`AcceptFilter` 拒绝；`accept` 遇 `EMFILE`/`ENFILE` | accept 后立即关闭，**不产生 `OnConnected`/`OnClosed`**，按原因计数（filter / 满载 / fd 耗尽），日志限频 |
| 编程错误 | 错线程使用 `Connection&`、在 `Running` 状态重复 `Start`、`Connection` 状态非法 | `LOG_FATAL`（`EventLoop::AssertInLoopThread()`） |
| 运行期可恢复错误 | `accept` / `read` / `write` / `connect` 失败、对端 RST | 记日志；关闭该连接，经 `OnClosed(conn, CloseReason, sys_errno)` 告知上层；`StreamClient` 按 `ReconnectPolicy` 重连 |
| 内存耗尽 | `bad_alloc` | 不处理，进程终止 |

细则：

- **返回约定**：`int`，0 成功，非 0 为 `errno` 值，不另造错误类型；net 库特有的失败也映射到现有 errno（路径过长 → `ENAMETOOLONG`，端点非法 → `EINVAL`）。返回它的函数标 `[[nodiscard]]`。
- **全有或全无**：`EventLoopGroup::Start()` 中途失败（如第 3 个线程创建失败）要先 join 已起的线程、关闭已开的 fd 再返回；`EventLoop` 构造函数不做系统调用，fd 在 `Init()` 里创建并返回 errno；`Shutdown` 对没有成功 `Start` 的对象是安全的空操作。
- `NetModule::Start()` 遵守 `Module::Start` 的约定（`framework/app/module.h`：返回错误的模块必须自清理）：任一步失败，先停掉已启动的 `StreamServer`/`StreamClient` 并 `Shutdown` group，再返回错误。
- **线程用 pthread 封装的 `Thread`**（`base/thread`），`Thread::Start()` 返回 errno；不用 `std::thread` / `std::jthread`，因为它们失败时抛 `std::system_error`。
- **`Acceptor` 预留一个空闲 fd**（打开 `/dev/null`）：`accept` 遇到 `EMFILE` 时先关掉它，接受并立即关闭这条连接，再重新打开，避免水平触发下 accept 死循环。
- **`ConnectionHandler` 的回调声明 `noexcept`**：派生类必须同样声明，回调里抛异常即 `std::terminate`，标准库默认的 terminate 处理器会打印异常类型与 `what()`，库里不需要 `catch`。`MainLoopHandler` 跑在 App 主循环上，沿用 App 的惯例。
- **`Endpoint` 解析**失败返回空 `optional`；`NetModule` 在边界处转成框架的 `Result<>`（带上原字符串）。
- **机械检查**：`ctest` 里加一个用例，对 `base/net`、`base/buffer`、`base/thread`、`framework/net` 下的源码 grep `throw` / `try` / `catch`，出现即失败。

### 4.12 P2b 落地时定下的细节

只记代码读不出来的东西，锚点是文件与测试名。

- **暂停（`PauseRead`）只影响之后的 `read`**：已经读进线程本地缓冲的帧（≤64KB）照常交付，所以 `MainLoopExecutor` 的在途上限是软的，超出量有界。
  暂停时连 `EPOLLRDHUP` 一起摘——它水平触发，对端半关闭后会一直就绪，留着就是空转（`net_flow_test` `TestPausedConnectionNoticesFinOnResume` 断言没有空转）；
  `EPOLLERR` / `EPOLLHUP` 内核总会报，所以暂停的连接遇到 RST 照样被关（`TestPausedConnectionStillClosesOnReset`）。
  代价：**暂停着的连接要到恢复读才发现对端的 FIN**。
- **`CloseGracefully` 期间继续读、继续分发**（对端在 FIN 之前发来的最后几条消息不丢），`Send` 返回 `Closed`；暂停着的先恢复读。
  对端回应的 FIN 与超时强关，`CloseReason` 都是 `LocalClose`。我方 `SHUT_WR` 之后对端再 FIN，内核会报 `EPOLLHUP`（两个方向都关了），所以不恢复读也能结束，
  但来不及读的数据就丢了——这才是自动恢复读的理由（`TestGracefulResumesReadingToDeliverPeerMessages`；变异验证过）。
- **idle**：`last_active` 在 `ConnectionTable::IdleEntry` 数组里，只有登记了 `idle_timeout` 的连接才进去，扫描只读这个数组。有登记的连接时才有扫描定时器（`EventLoop::ArmIdleScan`），
  每 100ms 扫 ⌈容量/10⌉ 个槽，一圈约 1s；活跃时间用每轮开头取的一次时钟（`cached_now_`），不为每次 `read` 单独取。`idle_timeout` 小于一圈时精度由一圈决定。
- **`StreamServer`** 的 Acceptor 挂在 `Start()` 时 `PickLoop` 选中的 loop 上，该 loop 也服务连接。accept 线程上：建立期选项 → `AcceptFilter` → 选目标 loop 并 `TryReserve` →
  目标就是自己则内联建连接，否则 `Post`，`FrameCodec` 在目标线程创建。`AcceptFilter` 放在选项设置之后，因为 UDS 的 `PeerInfo` 要带 credentials。
- **`StreamClient`** 固定的 loop 在第一次 `Start()` 时选定（构造时 group 可能还没 `Start`）。`Connector::Forwarder` 夹在用户 handler 与 `Connection` 之间，只为感知断开；
  句柄先于 `OnConnected` 发布（回调里就能经 `StreamClient::Send` 发数据），先于用户的 `OnClosed` 清除（回调里的 `Send` 得到 `Closed`）。
- **`Stop()` 之后立刻 `Start()`**：旧连接的 `OnClosed` 要等 `ProcessClosing`（本轮分发之后）才回调，而 `Start` 的任务在这之前的 `RunTasks` 里就会执行。
  `Connector` 用 `awaiting_closed_` 把新的尝试推迟到旧连接的 `OnClosed` 回调之后，并且用 0 延迟的定时器到下一轮才真正尝试（旧连接的槽要到本轮回收才释放，连接表恰好满时直接尝试会误报 `ENOMEM`）。TCP 的 connect 要多等一轮 epoll，天然掩盖了乱序；UDS 同步连上才会暴露——
  `stream_client_test` `TestStopThenStartNeverOverlaps` 两种传输都跑。
- **析构保险**：`StreamServer` / `StreamClient` 析构时 group 仍在运行就同步停掉（`EventLoop::CallSync`）；`StreamClient` 还要等 `awaiting_closed_` 清零。
  清零是 `Connector::OnConnectionClosed` 的最后一步，且在用户的 `OnClosed` 返回之后——否则析构会与仍在执行的用户回调赛跑（ASAN 在 `stream_client_test` 里抓到过）。
- **`EventLoop::CallSync` 只认"确实在这个 loop 的线程里"才内联**。`InLoopThread()` 对"还没跑过第一轮"的 loop 一律放行（装配阶段的宽松语义），
  group 的线程已创建、尚未进入 `RunOnce` 时，主线程会被它误判成 loop 线程，`StreamServer::Start` 就在错误的线程上 `Listen` 了。
- **`Shutdown(deadline)` 的实现**：先进入 `Stopping`（`running()` 为 false，loop 仍在跑）；各 loop 执行 `BeginShutdown`：先跑停机钩子（`StreamServer` 停 Acceptor、`StreamClient` 停重连；
  group 不认识它们，只认 `EventLoop::AddShutdownHook`），此后 `accepting()` 为 false（跨线程投来的"新连接"任务丢弃并归还预留名额），再对现有连接 `CloseGracefully(deadline)`
  （`deadline` 为 0 则直接关）；然后轮询各连接表的 `Live()` 到 0 或到点；到点 `CloseAllConnections`，再等最多 2s 让 `OnClosed` 跑完；最后停 loop、join。
  每条连接自己的 grace 定时器同样会在 deadline 强关，所以 `CloseAllConnections` 是兜底（变异验证里它的删除是等价变异）。`PickLoop` 在 `Stopping` 期间仍可用（accept 线程可能恰好走到）。
  **等待排空时还要求每个 loop 的 `BeginShutdown` 都已跑完**（`EventLoop::shutdown_started()`）：只看连接表为空会在空闲 server 上立刻"排空"，而某个 loop 还没处理到停机任务、它的 Acceptor 还在接新连接，
  这时 `Quit` 出去，投给已退出 loop 的连接就永远没人服务。
  `state_` 是原子量：IO 线程里 `on_connect_failed` 回调调 `StreamClient::Start()`（文档允许）会读 `running()`；停机期间（`stopping()`）`StreamServer` / `StreamClient` 的 `Start()` 返回 `ESHUTDOWN`，不是编程错误。
  析构兜底不排空、不回调（那时 handler 可能已销毁）。
- **统计的写法**：热路径的计数单写者，用 load + store（`LoopStats::Bump`），不做 `lock xadd`；`Send` 返回 `Closed` 的计数任意线程都会写，只用 `fetch_add`。
  两种写法不能混在同一个计数上。`bytes_in` / `messages_in` 每次 `read` 记一次，不是每条消息一次。
- **已知且接受**：任务队列无界，`Close` 之类的任务排在队尾；moodycamel 无 token 出队时先排空较新的生产者，最老的生产者（常是主线程）要等其他生产者的积压清完。
  别的线程持续灌 `Send` 时，`Close` 会被拖到灌入停止之后（`connection_handle_test` `TestSendRacingClose` 曾因此把内存吃光，现在发送线程有上限）。
  上界是各连接的 `HighWaterMark`（按字节计，小消息的任务开销是其字节数的数十倍）。
- **已知且接受**：`StreamServer` / `StreamClient` 的 `Start` / `Stop` / 析构要由同一个线程驱动（或各步之间有外部同步并不够）：任务队列只保证每个生产者内部有序，
  线程 A 投递的 `Stop` 与线程 B 析构时的 `CallSync` 之间没有先后保证，`Stop` 可能在对象销毁之后才执行。单线程调用时 FIFO 保证无此问题。
- **没有集成测试的**：TCP self-connect 的识别（`Connector::OnSocketConnected`）——要内核恰好挑中与目标相同的临时端口，造不出来；只有 `socket_test` 覆盖 `sock::IsSelfConnect`。

```
tcp/ uds/（公开）  →  stream/（公开基类）  →  internal/stream/  →  tcp/internal  uds/internal  →  internal/core
```

- `tcp/internal`、`uds/internal` 只依赖 `core`（`UniqueFd`、`socket_address`），不依赖 `stream`。
- `internal/stream` 里按类型分派的地方很少：`Bind`（UDS 先清残留文件）、`ConfigureSocket`（TCP 设选项 / UDS 取身份），`Acceptor` 与 `Connector` 里各有一两处 `if (kind == …)` 去调 `tcp::` / `uds::`。
- `rudp/` 与 `stream/` 并列：只依赖 `internal/core`，不依赖 `internal/stream`（rudp 的 bind / connect / `SO_ERROR` 在 `UdpSocket` 里自己写了十来行）。
  公开头 `rudp_options.h` 要用 `rudp_protocol.h` 里的常量，所以线格式头放在公开的 `rudp/` 而不是 `rudp/internal/`。
- `TcpServer` / `UdsServer` 只是基类上的薄壳：把类型化的端点与选项换成基类的通用形式，再加一个按类型的访问器（`local_endpoint()` / `peer()`）。
- 头文件一律用**扁平文件名** include（`#include "acceptor.h"`、`#include "connection.h"`，与仓库其它库一致），所以所有目录之间的文件名必须唯一
  （`tcp_socket.h` / `uds_socket.h`，不都叫 `socket.h`）。CMake 里 `NET_PUBLIC_INCLUDE_DIRS` 是公开的目录（`breeze_net` 以 PUBLIC 给使用方），
  `NET_INTERNAL_INCLUDE_DIRS` 给库自己，以及要直接用内部头的测试与 bench，`NET_TESTING_DIR` 只给测试。
- 测试放在被测代码所在的目录（`connection/connection_handle_test.cpp`、`internal/core/*_test.cpp`、`stream/stream_server_test.cpp`、`tcp/tcp_server_test.cpp` ……），
  跨组件的集成测试放 `testing/`；`breeze_net_test(<名> [INTERNAL] DIR <子目录>)`。

**加 rudp（内部用 KCP）要做的结构调整**（三项结构调整先做完，再做 rudp 本身）：

- **`Connection` 抽象（已完成，2026-10-31）**：`Connection` 现在是纯接口（只有虚函数、没有数据成员），具体类是内部的 `StreamConnection`（`internal/stream/`），将来再加 `RUdpConnection`。
  rudp 的会话没有自己的 fd（共用一个 UDP socket），所以业务回调拿到的 `Connection&` 不能是带 fd 的具体类。`ConnectionHandler` 与 `ConnectionHandle` 不变，业务代码与 `NetModule` 的回投、背压都共用。
  继承链 `StreamConnection → Connection → Pollable` 上只有一个 vptr，`sizeof(StreamConnection)` 仍是 288，热字段布局没动；`connection_test` 里用 `static_assert(sizeof(Connection) == sizeof(void*))` 守着"接口不能带数据成员"，
  并用一个与流无关的假连接证明业务回调只认接口。`EventLoop` 不再认识具体的连接类：`NewConnection` 搬成 `StreamConnection::Create`，`EventLoop` 只留 `MakeHandle` 与连接表，所以 `core` 不依赖 `stream`。
  代价：公开入口多一次虚调用，`HandleRead` / `HandleWrite` 这些内部热路径仍是非虚的。实验与 A/B 见 §9.5 / §9.6。
- **`NetServer` / `NetClient` 接口（已完成，2026-10-31）**：`connection/` 里的两个抽象基类，`StreamServer` / `StreamClient` 实现它们；`NetModule` 经它们持有各种服务端与客户端
  （`AddServer` / `AddClient` 返回 `NetServer*` / `NetClient*`），加 rudp 时不用再动 `NetModule` 的持有方式。这是控制面的虚调用（`Start` / `Stop` / `endpoint()`），
  只有客户端的 `Send` / `handle()` 在业务发送时多一次间接调用，与 §9.5 / §9.6 测过的是同一类成本。
- **`Endpoint` 加 `Kind::Udp`、`RUdpEndpoint`（已完成，2026-10-31）**：见 §4.2。`core` 里的地址互转与 `CreateSocket(ep, SOCK_DGRAM, …)` 本来就是通用的，只补了 `FromSockaddr` 的种类参数
  （字节流的 accept / getsockname 取 Tcp，数据报的 recvfrom 取 Udp）与 `IsIp()`；`socket_address_test` 里有一个 UDP 回环的一来一回，是 rudp 的地基。
  加 UDP 要堵住的"不是 TCP 就是 UDS"假设有四处：`UdsEndpoint::From`、`CreateSocket` 的协议族、`ConfigureSocket`（UDP 会落到 UDS 那一支去取 credentials）、
  `NetModule` 的分派（会解引用空的 optional）；字节流的服务端 / 客户端对 UDP 端点还要自己拒绝，否则 `udp://1.2.3.4:80` 会悄悄变成 1.2.3.4:80 的 TCP 监听。每一处都有测试，且逐个做了变异验证。
- rudp 本身（已完成，2026-10-31）：见 §4.14。`rudp/` 照 `tcp/` `uds/` 的样子放，没有动目录结构；`internal/core` 没有为它改一行逻辑（只加了两个统计计数 `rejected_ticket` / `datagrams_dropped`）。

### 4.14 rudp：KCP 之上的可靠消息通道

**定位**：给"网络不好、又要低延迟"的链路（游戏客户端到网关）用的可靠传输；服务间仍走 TCP / UDS。KCP 是 ARQ 协议（重传、窗口、快速重传），不管连接与准入，
所以本库在它外面补了三样：握手与准入（票据）、会话管理（心跳、关闭、空闲）、与 TCP 同一套的 `Connection` / 背压 / 统计语义。
业务代码不区分传输：`ConnectionHandler`、`ConnectionHandle`、`MainLoopExecutor` 都是同一套。选 KCP 而不是自己写：ikcp 小而稳、业界验证过，消息模式（`stream = 0`）保持消息边界，
正好免掉 codec；代价是它的 C 接口与 32 位毫秒时钟，所以包了一层 `KcpSession`。

| 组件 | 位置 | 职责 |
|---|---|---|
| `rudp_protocol.h` | `rudp/`（公开） | 数据报格式与解析 / 编码（线格式，见下），一个 `Parse`、六个 `Encode*`，纯函数 |
| `RUdpTicket`、`RUdpOptions` | `rudp/`（公开） | 准入票据（conv + 16 字节 token）；传输参数（mtu、窗口、interval、nodelay、dead_link、`max_message_size`、`flush_on_send`、套接字缓冲） |
| `RUdpServer` / `RUdpClient` | `rudp/`（公开） | 实现 `NetServer` / `NetClient`；服务端有 `IssueTicket` / `AddTicket`，客户端有 `SetTicket` |
| `RUdpConnection` | `rudp/internal/` | `Connection` 的 rudp 实现：没有 fd，拥有者（服务端 / 客户端）按来源把数据报交给它、定时调 `Tick` |
| `KcpSession` | `rudp/internal/` | ikcp 的薄封装（`Input / Send / PeekSize / Recv / Update / Flush / WaitSnd / QueuedSegments`） |
| `UdpSocket` | `rudp/internal/` | 注册在 `EventLoop` 上的 UDP socket：`recvmmsg` 批量收（一个事件最多 4 批 × 16 个，公平）、`sendmsg` 两个 iovec 发（包头与段不拷贝） |
| `TicketTable` | `rudp/internal/` | 待用票据表：控制面线程签发 / 登记，IO 线程握手时一次性取走，一把互斥锁 |

构建上 rudp 单独一个库 `breeze_net_rudp`（KCP 只在它里面 PRIVATE 链接，只用 TCP / UDS 的使用方不背这个依赖）；`RUdpEndpoint` 仍在 `breeze_net`
（它只是地址类型，`NetModule` 解析端点字符串要用）。依赖方向：`rudp/` → `internal/core`（`EventLoop`、连接表、`socket_address`），不依赖 `internal/stream`：
`UdpSocket` 里的 bind / connect / `SO_ERROR` 自己写了十来行，不借字节流的 `socket.h`。

**线格式**（整数小端，第一个字节是 `0xA0 | 类型`；改动就是协议不兼容，`rudp_protocol_test` 逐字节锁着）：

| 类型 | 方向 | 内容 | 大小 |
|---|---|---|---|
| Hello | 客户端 → 服务端 | `version(1) conv(4) token(16)` | 22 |
| Accept | 服务端 → 客户端 | `version(1) conv(4)` | 6 |
| Reject | 服务端 → 客户端 | `reason(1)`：Ticket / Busy / Filtered / Version / Stopping | 2 |
| Data | 双向 | KCP 段（它自己的头里有 conv） | 1 + 段 |
| Ping / Pong | 客户端 → 服务端 / 回应 | `conv(4)` | 5 |
| Close | 双向 | `conv(4) reason(1)` | 6 |

`Parse` 是严格的：长度差一个字节、类型不认识、高 4 位不是 `0xA` 一律丢（别的东西打到这个端口也不会被误当成本协议）。
**服务端的回应都不比触发它的包大**（Reject 2 < Hello 22；Close 6 < 最小的 Data 25；Accept 6 < Hello 22），不能被拿来放大流量；唯一例外是回 Ping 的 Close（6 对 5），多一个字节，已知并接受。

**握手与准入**：

```
控制面 ──(可信通道，如 TCP+TLS)──▶ 客户端：RUdpTicket{conv, token}
            ▲ 服务端 IssueTicket(ttl) / AddTicket(ticket, ttl)
客户端 ──Hello(conv, token)──▶ 服务端：AcceptFilter → 占连接表名额 → 验票据（一次性）→ 建会话
客户端 ◀──Accept(conv)──────── 服务端：Accept 先于 OnConnected 发出（OnConnected 里的 Send 排在它后面）
```

- 票据**一次有效**、有 ttl：conv 是非 0 的随机 32 位，token 是 16 字节随机数（`getrandom`），比较是常量时间的。token 错**不烧票据**（否则知道 conv 的人用错 token 试一次就能作废合法用户的票据）；
  版本不对、被过滤器拒绝、连接表满也不消耗票据（先占名额再验票据，验票失败再归还）。待用票据有上限（`max_pending_tickets`，默认 65536），过期项在取用时顺手删、表满或每秒一次登记时整表清扫。
- 没登记的来源发什么都建不起会话——这是 UDP 上"随便一个包就让服务端分配资源"的口子被堵上的方式。
- **Hello 会丢**：客户端每 `hello_interval`（默认 200ms）重发，直到 Accept、Reject 或 `connect_timeout`（默认 5s）。同一来源已有会话时再来的 Hello 是重传，重发 Accept（幂等，不建第二个）；conv 不同的 Hello 不理。
- 握手期间的 ECONNREFUSED（服务端还没起）**不算失败**，重试到超时，超时时报最后一个 socket 错误；Reject 的原因映射成 errno 给 `on_connect_failed`（EACCES 票据、EBUSY 表满、EPERM 被过滤、EPROTO 版本、ESHUTDOWN 服务端停止中），`will_retry` 恒为 false。
- **放弃握手要告诉服务端**：握手超时、或握手中 `Stop`，客户端尽力发一个 Close——Accept 可能只是丢了或来晚了，服务端那边其实已经建好会话；不通知，它就只能等空闲超时才回收。
  **所以服务端必须开 `idle_timeout`**（默认 0 = 关）：客户端消失、Close 丢光、半途放弃的会话都靠它兜底回收，rudp 没有 TCP 的 keepalive / RST。
- **不自动重连**：票据只能用一次，断线后要向控制面要新票据（`SetTicket`）再 `Start()`。握手失败与断开之后客户端都回到 Idle。`NetModule` 因此不随模块启动 rudp 客户端。
- **会话按来源 ip:port 固定**：别的来源即使知道 conv 也读不到、写不进、关不掉别人的会话（`TestAddressPinning`）。代价是不支持迁移——客户端换网络（IP 或 NAT 端口变了）要重新握手、拿新票据。

**会话的生命周期**：

- **心跳与空闲**：客户端连通后每 `ping_interval`（默认 1s，0 = 关）发 Ping，服务端回 Pong；"活跃"= 收到任何有效数据报（合格的 KCP 段、Ping、Pong），Hello 重传不算。两端的 `idle_timeout` 因此都能放心打开，
  建议设成心跳间隔的几倍。连通之后的 ICMP 不可达**不**关会话（偶发的不可达不该断线），断线靠 Close、`idle_timeout`、KCP 链路判死。
- **关闭**：`Close` / 超限 / 空闲 / 慢消费者关闭时向对端发 3 个 Close（尽力而为，丢光了对端靠空闲超时）；对端 Close 引起的关闭、链路判死（IoError，ETIMEDOUT）不再发。
  **优雅关闭**（`CloseGracefully`）：之后的 `Send` 返回 `Closed`，已排队的消息被对端**全部确认**之后才发 Close 并结束，`timeout` 到了强关，原因一律 LocalClose；对端以 PeerClosed 结束。
  与 TCP 的差别：只等"我发的被确认"，不等对端的发送方向（没有半关闭）。
- **链路判死**：同一个段重传（含首次）`dead_link` 次仍没被确认，以 IoError / ETIMEDOUT 关闭。默认 20 次在 nodelay 下要**好几分钟**（每个段的 RTO 按 1.5 倍无上限增长：RTT 估计很小时约 2 分钟，没有 RTT 样本时约 15 分钟），`dead_link = 5` 约 2 秒；
  要及时发现对端消失，靠 `idle_timeout` + 心跳，别指望 dead_link。
- **服务端重启的快速失败**：没有会话的来源发来 Data / Ping，服务端回一个 Close(conv)，重启前的客户端立刻以 PeerClosed 结束，而不是干等空闲超时（`TestServerRestartFailsFast`）。

**数据路径与语义差异**（都是 TCP 没有的，业务要知道）：

- **消息自带边界**，没有 codec；一条消息最多 127 段（ikcp 的限制，`kMaxFragments`），即 `127 × (mtu − 25)` 字节（mtu 1400 时 174625）；`max_message_size`（默认 64KiB）不得超过它（`RUdpOptions::Valid`）。
  超限的 `Send` 与 TCP 的 codec 超限一样关连接（ProtocolError，`send_closed_oversize`）；收到比自己上限大的消息同样关连接。两端的 `max_message_size` 要兼容，其余参数各管各的。
- **发送是批量的**：`Send` 只把消息排进 KCP 的发送队列，下一次定时 `Update`（`interval_ms`，默认 10ms，范围 10–100）才 flush，多条小消息合进一个数据报。要低延迟可开 `flush_on_send`（每次 `Send` 立刻发一个数据报，不再凑包）。
  定时器由拥有者每个 interval 推进一次：服务端一个定时器，只检查"活跃表"里的会话（没有未确认的数据、没有待发的确认、对端窗口不为 0 的会话是静止的，不在表里、不占 CPU；没有活跃会话就不装定时器），
  表里的会话只有到了点（有待发的确认 / 排队的数据，或最早的重传时刻到了）才真的调 `Update`（§9.8），`NetStats::rudp_updates` 记的就是真调的次数。
- **`PauseRead` 是真背压**：停止向 handler 交付，消息留在 KCP 的接收队列里，队列占满接收窗口后对端自然被拖慢，不丢；`ResumeRead` 之后在下一次 Tick（≤ `interval_ms`）里补交付
  （不在调用栈里直接交付：调用方可能就在 `OnMessage` 里）。暂停期间不计空闲。
- **发送积压（`high_water_mark`）只算"整条消息还没进发送窗口"的排队字节**，与 TCP 只算"内核缓冲放不下的用户态排队"是同一个边界；已进窗口、等确认的部分由 `send_window` 限界，不算积压
  （否则 RTT 内的在途数据就会让健康对端上的突发越过水位）。对端慢了、窗口关上，队列才会涨，越线就是慢消费者。队列先进先出，按累计段数**精确**释放（`TestPendingBytesAccounting`）。
  KCP 只在 flush 时才把队列移进窗口，所以 IO 线程里的 `Send` 在排队量超过水位一半时立刻 flush 一次再判水位（`TestBurstWithinWindowIsNotSlowConsumer`）；
  **跨线程的 `ConnectionHandle::Send` 在句柄侧判水位、不能 flush**：同一个 interval 内从别的线程塞进的量超过水位仍会越线，突发大的业务调大 `high_water_mark` 或开 `flush_on_send`。
  握手完成前对端窗口按 KCP 的初始值 128 段算，刚连上就一口气排的量超过"128 段 + 水位"也会越线。
- **没有 `CloseReason` 的新成员**：链路判死是 IoError（errno = ETIMEDOUT），对端的 Close 是 PeerClosed。

**威胁模型与已知限制（v1）**：

- **没有加密与完整性保护**。票据防的是"谁能建会话"，不防在路径上的人读 / 改 / 注入数据报；路径外的人要注入需要同时伪造来源地址并猜中 32 位 conv。生产环境暴露到公网之前要补
  AEAD 数据报层（做在 `UdpSocket` 与 `RUdpConnection` 之间的一个过滤层，不动协议的其余部分）；在那之前只适合可信网络或应用层自己加密。
- **票据就是凭证**：控制面到客户端的通道要自己保证机密性（TLS）；token 不要写日志。
- **Hello 洪泛**：每个 Hello 在 IO 线程上做一次 Parse + 一次互斥锁下的哈希查找，回一个 2 字节的 Reject。不做限速；要防 DoS 靠网络层（防火墙、`AcceptFilter` 按来源 IP 过滤）。
- **单 socket、单 loop**：所有会话都在 `Start` 时选定的那个 loop 上，一个 loop 的 IO 与 KCP 计算是上限；横向扩展就多开几个 `RUdpServer`（不同端口）。`SO_REUSEPORT` 多 loop（内核按四元组哈希，天然把一个客户端固定在一个 loop）是自然的下一步，没做。
- 没有 MTU 探测（默认 1400，以太网 + 隧道下一般不分片）；没有迁移；KCP 的拥塞控制默认关（nodelay 快速模式，拿带宽换延迟）。
- **多网卡主机上不要绑通配地址**（`udp://0.0.0.0:port`）：服务端用一个未 connect 的 socket 回包，内核按路由选源地址，可能与客户端连的那个地址不同，
  而客户端的 socket 是 connect 过的，内核会把"来源不是对端"的包直接丢掉，表现为握手永远超时。单网卡或只绑具体地址没有这个问题；要支持通配地址得用 `IP_PKTINFO` 记下并指定每个包的本地地址，没做。
- `net.proto` 里还没有 rudp 段，配置驱动的 `NetModule(app)` 用代码里的默认值。
- **会话多时的开销**：每会话约 5.5KB（大头是 `ikcp_setmtu` 分配的 4.3KB 收发缓冲，§9.7）；空闲的会话不占 CPU，在途数据在等重传的会话只被检查、不被推进（§9.8，优化前 10000 个空闲会话要占服务端线程约 7%–9%）。容量上限是单 loop（见上）。

## 5. `framework/net`：回投主循环

```
IO 线程 N ──ConnectionHandler──▶ MainLoopExecutor（IO 侧）：事件入 SpscQueue ──▶ 主循环 Drain 后回调业务
```

- `MainLoopExecutor` 实现一个 `ConnectionHandler`，在 IO 线程里把事件塞进该 IO 线程专属的 `SpscQueue`（`OnMessage` 的 payload 视图在此处拷贝成 `SharedBuffer`），主循环 `Drain` 后调用业务的 `MainLoopHandler`；业务回调拿到的是 `ConnectionHandle`。
- 事件队列每个 IO 线程一条。`Connected → Message* → Closed` **走同一条**，不分两道（分道会让 `Closed` 超车）。`Enqueue` 无界、不阻塞。
- **入口背压 = `PauseRead`，不是阻塞线程**：IO 线程服务成千上万连接，阻塞它等于全体停摆。
  - 每连接在途上限（条数+字节，原子计数，主循环消费时递减）：超限摘掉该连接的 `EPOLLIN`；消费到低水位时 `ResumeRead`；高低水位之间留滞后区间，避免来回 `epoll_ctl`。
  - **全局入站字节预算，强制生效**（计数与策略都在 `MainLoopExecutor`）：超出则对所有连接 `PauseRead`。每连接默认值要小（如 64KB），否则 10 万连接 × 256KB ≈ 25GB。
- 事件总量因此被"连接数 × 每连接上限"与全局预算双重约束。
- `NetModule : Module, IWaker`：持有一个 `EventLoopGroup`、若干 `StreamServer`/`StreamClient` 与 `MainLoopExecutor`（装配，不含 IO 逻辑）。`Wake()` = `Drain(budget)`，返回 true 表示仍有积压；IO 线程入队后调 `App::Notify()`。
- 配置走 `config/schema` 新增 `net.proto`（io_threads、max_connections_per_loop、每连接在途上限、全局入站预算、idle_timeout、keepalive 等的生产默认值），写法照 `framework/kernel/log_module.cpp`。

### 5.1 P3 落地时定下的细节

- **事件队列按 `(group, loop)` 懒创建**，由该 IO 线程自己在第一个事件时创建（`MainLoopExecutor::QueueFor`，加锁，少见）；消费者遍历的是另一个只追加的指针数组，先写指针再发布计数。
  `Drain` 从上次停下的下一条队列开始轮转，一条队列的积压饿不死别的。`Drain` 返回 `ran >= limit`：取满 limit 个就当作"可能还有"，多一次空转的唤醒，不会漏。
- **在途计数是每连接的 `ConnState`（`shared_ptr`）**：连接对象（经 `ConnectionContext`）与队列里每条未分发的 `Message` 事件各持一份——连接在 `OnClosed` 之后就销毁了，
  主循环上没消费完的事件仍要能安全地扣账。先记账再入队；主线程在把 `msg` 交给业务**之前**扣账（从那一刻起 payload 归业务，不再占网络层的额度）。
- **暂停 / 恢复的仲裁**：`paused` 是原子量，IO 线程（`MaybePause`）与主线程（`TryResume`）都可能翻转它，**翻转用 `exchange`，拿到旧值的一方负责调 `PauseRead` / `ResumeRead`**。
  IO 线程暂停之后必须重查一次——主线程可能在翻转之前就把积压消费光了，它看到 `paused` 还是 false，不会替我们恢复；两边都用 seq_cst（Dekker 式握手，和 §4.5 的唤醒协议同类）。
  主线程发出的 `ResumeRead` 经任务队列，一定排在 IO 线程当前回调里那次直接 `PauseRead` 之后。
  **物理上还暂停着时，IO 线程不翻转标志**（`MaybePause` 里的 `c.IsPaused()` 守卫）：主线程清掉标志、投递了 `ResumeRead` 而它还没执行时，IO 线程若在同一次 `read` 的后续帧里又把在途推过高水位，
  翻转标志再 `PauseRead` 是空操作（物理上本来就是暂停的），随后那个过期的 `ResumeRead` 生效，连接物理上恢复读而标志仍是 true，`MaybePause` 从此直接返回，这条连接的入站不再受限。
  等恢复生效之后再判断：这次 `read` 剩下的帧照常入队，下一次 `read` 的消息再暂停（`main_loop_executor_test` `TestStaleResumeDoesNotDisableBackpressure` 用一个门 handler 把 IO 线程卡在 `read` 中间来复现，变异验证过）。
- **全局预算的 `waiters_`**：因全局预算（或"本连接已降下来、只剩全局没降下来"）而暂停的连接排进去，主线程在每次 `Drain` 末尾、全局降到低水位时统一 `TryResume`。
  IO 线程暂停之后，**全局只要还没降到低水位就排队**，不只是"超过高水位"时：全局落在（低水位，高水位]之间同样阻止恢复，而这时连接可能已经没有在途消息、没有 `Release` 会为它触发。
  **`TryResume` 恢复不了且只因全局时必须重新排队**：逐个处理 waiter 期间 IO 线程还在往全局里加字节，处理到一半全局又被推高是常态；
  早先的实现把"这次恢复不了"的连接从列表里摘掉就不管了，它没有在途消息、再不会有 `Release` 为它触发，连接永久暂停——`main_loop_executor_test` 的小限额压力用例抓到的。
- **滞后区间**：高水位 = 配置值，低水位 = 一半；每连接（条数、字节）与全局预算各自如此。暂停是软的：本次 `read` 已读进来的帧照常入队（≤64KB），所以在途量最多超出上限一次 `read`。
- **`NetModule` 的停机由 main 负责**（§10.3 的定案）：`App::Run` 返回之后，main 在**同一个线程**上调 `NetModule::Shutdown()`——group 优雅关闭（到 `shutdown_deadline_ms` 强关），
  再把事件 `Drain` 到空，业务才看得到每条连接的 `OnClosed`。要求同一个线程，是因为事件队列是 SPSC，消费者必须固定（Debug 断言）。
  **等待期间也在消费**：`EventLoopGroup::Shutdown(deadline, idle)` 在等连接关闭时每轮调一次 `idle`，`NetModule` 传的是 `Drain`。进入优雅关闭的连接要读到对端的 FIN 与最后几条消息，暂停读不再生效，
  主线程若只阻塞等着，对端还在灌数据时事件就无界地堆在队列里（不变量 3 在停机期失效）；边等边消费之后，上界是"对端发送速度 − 主线程消费速度"在 `shutdown_deadline_ms` 内的累积。
  `TestShutdownKeepsDrainingWhileWaiting`（对端要等业务收到它的消息才肯关）变异验证过。
  没调就销毁只做兜底：直接停 IO 线程，未消费的事件丢弃、不回调业务（那时业务对象多半已经销毁）。
- **`NetModule` 的装配**：`AddServer` / `AddClient` 只能在 `Init` 之后、`Start` 之前（通常在依赖 `net` 的模块的 `Init` 里），之后是阶段错误——运行期动态增删对端要先有 `on_stopped`（§8）。
  endpoint 写字符串，解析失败的错误里带原字符串。`Start` 失败：先停已启动的 server / client，`Shutdown` group，再返回带 endpoint 与 `strerror` 的错误（`net_module_test` 覆盖）。
  `NetModule(app)` 在 `Init` 时从 `ConfigModule` 读 `net` 段（`DependsOn("config")`），`NetModule(app, options)` 直接给选项、不依赖 config。
- **配置**：`config/schema/net.proto` 的默认值就是生产默认值；`CommonConfig` 里的 `net` 段**不是 required**（字段全有安全的默认值，缺省即用默认值；
  不像 `world_id` 取 0 会出事），但 `common.yaml` 照例写全量。`idle_timeout_ms` 的默认值是 0（不检测）：内部链路没有心跳时开了会把安静的连接关掉，面向客户端的进程（gate）在部署配置里设。
- **`Notify` 的开销**：每个事件入队后都调 `App::Notify()`，已有 token 时只是一次原子交换，但所有 IO 线程与主线程争同一条缓存行。目前没有测出问题（§9.3），
  真成瓶颈的办法是在 executor 里用一个"已通知"标志合并，主线程每次 `Drain` 前清标志（需要双侧 `seq_cst` 屏障，同 §4.5）——现在不做。

```cpp
// ---- base/net：回调在 IO 线程 ----

class EventLoopGroup {
  public:
    explicit EventLoopGroup(EventLoopGroupOptions); // io_threads、max_connections_per_loop…
    [[nodiscard]] int Start();                      // 0 成功，否则 errno（ENOSPC：注册表已满；EINVAL：选项越界）；失败已回滚
    void Shutdown(std::chrono::milliseconds deadline,
                  std::move_only_function<bool()> idle = {});  // idle：等待期间每轮调一次，返回 true 表示做了事（不睡）
    NetStats   GetStats() const;
    bool running() const;                           // 已 Start 且未开始停机
    bool stopping() const;                          // 正在 / 已经停机：此时 StreamServer / StreamClient::Start 返回 ESHUTDOWN

  private:
    friend class StreamServer;
    friend class StreamClient;
    EventLoop& PickLoop();                          // EventLoop 是内部类型，公开头只前置声明
};

enum class SendResult { Ok, Closed };

class ConnectionHandle {                            // 8 字节、可平凡复制：[group:4|loop:8|slot:20|generation:32]
  public:
    uint64_t raw() const;                           // 日志/哈希用
    [[nodiscard]] SendResult Send(SharedBuffer payload) const;  // 线程安全；帧头由连接的 codec 生成
    void       Close() const;
    void       CloseGracefully(std::chrono::milliseconds timeout) const;
    void       PauseRead() const;
    void       ResumeRead() const;
};
// group 销毁后其句柄作废；解析不到时 Send 返回 Closed。使用方保证销毁 group 前丢弃句柄、且无线程仍在 Send。

class StreamServer {                                   // 一个对象一个 endpoint
  public:
    StreamServer(EventLoopGroup&, const Endpoint&, StreamServerOptions,   // StreamServerOptions：connection（水位、idle、keepalive）、accept_filter、backlog
              ConnectionHandler&, const FrameCodecFactory&);     // 必填；max_frame 是 codec 工厂的参数，不在选项里
    [[nodiscard]] int Start();                      // 阻塞到 bind / listen 在 IO 线程完成；0 成功，否则 errno（EADDRINUSE 等）；失败已回滚
    void Stop();                                    // 只停 accept，异步
    const Endpoint& endpoint() const;               // 实际绑定的地址（端口填 0 时是系统分配的）
};

class StreamClient {                                   // 固定在一个 loop 上；状态 Idle ⇄ Running
  public:
    StreamClient(EventLoopGroup&, const Endpoint&,                  // 只收 IP 字面量
              StreamClientOptions, ReconnectPolicy,                    // StreamClientOptions 含 on_connect_failed / connect_timeout
              ConnectionHandler&, const FrameCodecFactory&);
    [[nodiscard]] int Start();                      // 任意线程，Post 到所属 loop；Idle 下合法，Running 下重复是编程错误；只返回参数类错误（EINVAL）
    void       Stop();                              // 任意线程；停止重连并关闭当前连接，回到 Idle；不等待
    [[nodiscard]] SendResult Send(SharedBuffer payload);  // 未连通 → Closed，不暗中缓冲
    ConnectionHandle handle() const;                // 当前连接，没有时 raw() == 0
};

class RUdpServer : public NetServer {                  // 一个 UDP 端口、一个 socket、一个 loop；没有 codec（消息自带边界）
  public:
    RUdpServer(EventLoopGroup&, const RUdpEndpoint&, RUdpServerOptions,   // 含 connection、rudp（RUdpOptions）、accept_filter、max_pending_tickets
               ConnectionHandler&);
    [[nodiscard]] int Start();                      // 0 成功，否则 errno（EADDRINUSE、EINVAL：选项不合法、ESHUTDOWN）
    void Stop();                                    // 不再接受新会话，已有的继续；最后一个结束后端口释放
    std::optional<RUdpTicket> IssueTicket(std::chrono::milliseconds ttl);   // 任意线程；控制面把票据发给客户端
    bool AddTicket(const RUdpTicket&, std::chrono::milliseconds ttl);       // 登记别处签发的
};

class RUdpClient : public NetClient {               // 凭票据握手；不自动重连（票据一次有效）
  public:
    RUdpClient(EventLoopGroup&, const RUdpEndpoint& server, RUdpClientOptions, ConnectionHandler&);  // 选项含 ticket、connect_timeout、ping_interval…
    [[nodiscard]] int Start();                      // EINVAL：票据 / 选项不合法；握手结果走 OnConnected / on_connect_failed
    void Stop();
    void SetTicket(const RUdpTicket&);              // 断线或握手失败后换新票据，再 Start()
    [[nodiscard]] SendResult Send(SharedBuffer);
    ConnectionHandle handle() const;
};

// ---- framework/net：业务用，回调在 App 主循环 ----

struct MainLoopHandler {                            // 业务实现这个
    virtual void OnConnected(ConnectionHandle, const PeerInfo&) {}
    virtual void OnMessage(ConnectionHandle, SharedBuffer msg) = 0;              // 唯一必须实现的回调
    virtual void OnClosed(ConnectionHandle, CloseReason, int sys_errno) {}
};

class MainLoopExecutor {
  public:
    explicit MainLoopExecutor(App&, InboundLimits = {});  // 构造期必填；内部持有各 IO 线程的 SpscQueue，并调 Notify
    ConnectionHandler& Wrap(MainLoopHandler&);      // 交给 StreamServer / StreamClient 构造
    bool Drain(size_t limit);                       // 在主循环线程上调；ran<limit ⇒ 已空
    ExecutorStats GetStats() const;                 // 队列深度 / 峰值、在途字节、暂停次数
};

class NetModule : public Module, public IWaker {    // 装配，不含 IO 逻辑
  public:
    explicit NetModule(App&);                       // Init 时从 ConfigModule 读 net 段，DependsOn("config")
    NetModule(App&, NetModuleOptions);              // 直接给选项，不依赖 config
    Result<StreamServer*> AddServer(std::string_view endpoint, MainLoopHandler&, const FrameCodecFactory&);  // Init 之后、Start 之前
    Result<StreamClient*> AddClient(std::string_view endpoint, MainLoopHandler&, const FrameCodecFactory&);
    Result<RUdpServer*> AddRUdpServer(const RUdpEndpoint&, MainLoopHandler&);   // 随模块启动；udp:// 的 AddServer 也走它
    Result<RUdpClient*> AddRUdpClient(const RUdpEndpoint&, MainLoopHandler&);   // 不随模块启动：业务拿到票据后自己 Start()
    bool Wake() override;                           // = executor.Drain(wake_budget)
    void Shutdown();                                // main 在 App::Run 返回之后、同一线程调：group 优雅关闭，再把事件 Drain 到空
};
```

## 7. 不变量

1. `ConnectionHandle` 在其 group 存活期间、同槽 2^32 次复用内不会重复；group 销毁后其句柄作废（解析不到时返回 `Closed`；同编号的新 group 启动后不再保证，使用方须在销毁 group 前丢弃句柄）。过期句柄的任何操作都有明确返回，不静默。
2. 每条已回调过 `OnConnected` 的连接恰有一个 `OnClosed`，且在其最后一个 `OnMessage` 之后；同一连接事件全序。accept 后即被拒绝的连接不产生任何回调。
3. 事件投递不阻塞不丢；消息入口满则 `PauseRead`，不丢消息、不阻塞 IO 线程。内存上界：`framework` 层的入站事件有强制上限（每连接在途上限 + 全局入站预算）；`base` 层靠 `HighWaterMark`、`max_frame` 与 `max_connections_per_loop` 约束，最坏上界是它们与连接数的乘积，库内不设全局上限。
4. `Send` 不静默丢：`Ok`（已接收）或 `Closed`（已关闭/正在关闭，原因见 `OnClosed`）。
5. 断线即 `OnClosed`；连不上与不可重试错误都经 `StreamClientOptions::on_connect_failed` 通知，不静默；`StreamClient` 未连通时不暗中缓冲。
6. 解码错误即关闭，不重新同步。
7. 谁创建 IO 线程，谁在 `Shutdown`/析构里 join；`ConnectionHandler` 回调不得阻塞。
8. `FrameCodec` 每连接一个实例；`Connection&` 只在其 IO 线程使用。
9. `base/net` 不依赖主循环或 `framework`。
10. net 库内不抛、不 catch；建立期失败经 `Start()` 返回 errno 并回滚，编程错误 `LOG_FATAL`；`ConnectionHandler` 回调 `noexcept`。
11. `Connection` 在自己的回调里被关闭时延后销毁；`OnClosed` 之后不再有该连接的任何回调。
12. `Send` 与 `OnMessage` 对称，都只处理 payload；帧头由连接生成，payload 可被多条连接共享。
13. `OnMessage` 的 payload 视图只在回调内有效；跨线程保留必须拷贝（`MainLoopExecutor` 入队时）。

## 8. 不做与暂不做

**明确不做（属于应用层，库只留接口）**：群发/房间/订阅、鉴权与会话、限流与黑名单策略（经 `AcceptFilter`）、心跳内容与校验、客户端协议格式（魔数、序号、加密、压缩，经 `FrameCodec`）、慢消费者的细粒度策略。

**明确不做（其他）**：io_uring、TLS、fd 传递（SCM_RIGHTS）、WebSocket、DNS 解析、PROXY protocol、RPC 相关性/deadline/取消（上层）、Windows/IOCP、自动重试消息（重连只管连接）、有限次数重连（永远重连，由调用方 `Stop()`）、`Result`/`expected`/`error_code` 作为 net 库的返回类型。

**rudp 的不做 / 暂不做**（理由与替代见 §4.14）：加密与完整性（v1）、迁移、MTU 探测、`SO_REUSEPORT` 多 loop、按连接的 KCP 统计（重传率、RTT）、`net.proto` 的 rudp 段、Hello 限速。

**本阶段暂不做**：sidecar 转发面、写缓冲水位回调（`OnWriteBufferHigh/Low`）、`DropNewest` 溢出策略、IO 线程睡前自旋、帧级读超时（应用层按完整消息时间判定）、`StreamServer`/`StreamClient` 的停止完成通知（`on_stopped`，用于运行期动态增删对端）。

## 9. 性能目标与基线

以 muduo 为基线，同一台机器、同一组用例：

1. 裸 epoll echo（性能上限）
2. muduo echo
3. 本库 `ConnectionHandler` 直接回调

1 连接（延迟受限，波动大，不用于结论）：64B 为 93.0% [83–118]、1KB 为 94.8% [90–111]，范围跨过 100%。

**UDS**（muduo 不支持，只与 raw 比；视图版 `Send` 之后，5 轮交错，括号内为 `breeze-copy`）：64B×64 为 91%（87%），1KB×64 为 93%（88%），64B×10k 为 92%（87%），1KB×10k 为 91%（91%，raw 自身波动 ±16%）。
1 连接是延迟受限，各实现之间的差在噪声内，不用于比较实现。

**UDS 与 TCP**（breeze，同一二进制、同一天，WSL2 上的数字）：
- 1 连接 ping-pong：p50 为 UDS 26–27µs、TCP 96–101µs，p99 为 73–80µs 对 320–338µs，往返吞吐约 3.6–3.9 倍（64B 与 1KB 一致，raw 也一样）。
- 64 连接饱和：UDS 只比 TCP 快 4–10%（64B 为 1.10×，1KB 为 1.04×；raw 为 1.16× / 1.11×）。瓶颈是服务端线程每条消息的 CPU 成本，而不是传输的延迟。
- **10k 连接：UDS 反而比 TCP 慢约 23–24%**（0.77× / 0.76×；raw 同样是 0.79–0.80×，所以是内核或本环境的特性，不是本库的）。原因没有查。
  app ↔ sidecar 是少量连接，用不到这个区间。

**结论**：

1. **「3 不低于 2」成立**（echo 方案与 muduo 相同）：TCP 四个多连接配置里 breeze ÷ muduo 的逐轮中位数为 99.9 / 103.5 / 100.7 / 103.9%，**没有低于 muduo 的配置**，10k 连接下两组都是 5/5 轮胜。
   历史：视图版 `Send` 之前，1KB×64 曾稳定低 2–4%（96.3 / 96.5 / 98.1%），其余配置持平或略快。
   **该落后是 echo 回调里"先拷成 `SharedBuffer` 再发"造成的，不在框架路径上**：`breeze-fixed`（回复预先建好的固定 payload）当时就与 muduo 持平，改用视图版 `Send` 后落后消失（100.7%）。
   它只出现在 1024B、1000B 不出现，这一点的机制没有查清：曾怀疑 1040 字节的块越过 glibc tcache 的 1032 字节上限，
   但干预实验（`GLIBC_TUNABLES=glibc.malloc.tcache_max=4096`）没有改善（反而慢 3%），该假设已被推翻。
2. **10k 连接下 breeze 比 raw 低 4–5%，muduo 低 9–10%**：每连接对象带来的缓存占用是两者共有的代价，breeze 的"线程本地读缓冲优先"（§4.7）让它小一些。
3. **echo 里的分配与拷贝是可测量的代价**（此前"无可测量代价"的结论不对）：UDS 64 连接上，视图版比 `breeze-copy` 快约 5%（逐轮配对 104–108%、101–114%）；
   TCP 上 0–4%；UDS 10k 无明显差异（缓存占用占主导，且 raw 自身波动大）。视图版 `Send` 绕开了这笔代价（echo、小应答）；
   必须分配 `SharedBuffer` 的路径（序列化出新数据）仍要付，malloc 与 memcpy 各占多少没有分开测过。
4. **UDS 起初有 12–16% 的真实差距**，经 §9.2 的优化与视图版 `Send` 后为 91–93%，见下。

**验收标准：不低于 muduo（已定）**——结论 1 已满足。最初曾定"与裸 epoll 的差距 X = 8%"（吞吐 ≥ 92%、p99 ≤ 1.08 倍），后改为只要不低于 muduo 即可，裸 epoll 的差距降为参考。
下表仍按 X = 8% 的口径列出供参考（逐轮配对，5 轮交错，相对同一批轮次里的 raw）；UDS 没有 muduo 可比，只能与 raw 比：

| 配置 | breeze 相对 raw | 是否 ≥92%（参考） |
|---|---|---|
| TCP 64B×64 / 1KB×64 / 64B×10k / 1KB×10k | 97% / 99% / 96% / 95% | 是 |
| UDS 64B×64 / 1KB×64 / 64B×10k / 1KB×10k | 91% / 93% / 92% / 91% | 两项达到，两项差 1 个百分点，小于测量噪声（raw 波动 ±4–16%） |

p99 在 64 连接下与 raw 的差约 +4–5%，在 8% 内；但 p99 本身的波动就有 5–10%，8% 的 p99 门槛在这个测量精度下**无法判定**，吞吐是可靠指标，p99 只作参考。
UDS 余下约 7–9% 的差距：与 raw 同形状的系统调用加每连接状态约 3%（设计固有：帧头与 payload 分两个 iovec，以便多连接共享同一块 payload）、
框架自己的路径约 3–4%（`Send` / `DecodeAll` / `HandleRead` / `OnEvents` / `Decode` 十来个函数，剖面是平的，没有可单独拿掉的一块）。
再降需要把层次融合、去掉虚调用，会明显牺牲清晰度，而收益小于测量噪声（±4–8%），已无法验证，所以停在这里。

**测量环境的两个坑**（不是库的问题，但会让后来人踩）：本机 `ip_local_port_range` 只有 40525–44620（约 4000 个端口），
同一源地址连同一 `(目的IP, 目的端口)` 到不了 10k，bench 让 4 个压测线程分别连 `127.0.0.1…4` 才凑够；
UDS 的非阻塞 `connect` 在对端 accept 队列满时返回 `EAGAIN`（TCP 是 SYN 重传），压测客户端要重试。

### 9.2 UDS 路径的归因与优化（P2a 收尾）

方法：**先测量再改**。每一步都有数据，被数据排除的假设都没有动代码。

**被排除的假设**：
- 每轮 `RunOnce` 的固定开销（睡前 seq_cst 写、fence、空队列取、定时器与回收检查）：原生测得每轮处理 ~60 条消息（64 连接）、~1022 条（10k 连接，已到 `epoll_wait` 单次上限），
  `RunOnce` 自身只有 ~11 条指令/消息。
- 系统调用耗时：用 `rdtsc` 分阶段计时，`readv` / `sendmsg` 的周期数在各实现间相同（`sendmsg` 占约 70%，因为要唤醒对端）；差距全在"其余"一栏（用户态）。
- `EPOLLRDHUP`、epoll 存指针而非 fd：二分实验（给裸 epoll 一次加一个 breeze 的特征）里都没有可测量的影响。

**确认的原因与改动**：

| 改动 | 证据 | 效果 |
|---|---|---|
| `SharedBuffer` 分配改用普通 `operator new`（原先显式要求 16 字节对齐，走了 `posix_memalign`；glibc 默认就是 16 字节对齐） | callgrind：对齐分配链每条消息约 100 条指令 | 760 → 679 条指令/消息 |
| 读路径改为"线程本地缓冲优先，每连接只存半个帧"；`FrameCodec::Decode` 改吃 `span` | 二分实验：冷的每连接读缓冲约 2.5%；单 iovec 的 `read` 比 `readv` 便宜；每连接不再常驻 1KB | 见下 |
| `Send` 直写快路径：整帧写完时不构造 / 移动 `Pending` | callgrind | 679 → 612 条指令/消息（含上一项） |
| 线程检查用 `thread_local` 指针比较（muduo 同款），不再每次调 `pthread_self` | callgrind：每次 `Send` 省约 10 条 | |

在这个环境里（WSL2，系统调用返回后用户态代码是冷的），实测 IPC 只有 ~0.3，约 3.6 周期/条指令，所以降指令数确实有效，但**指令数与耗时的对应关系很弱**：
1KB 时分配加拷贝多 668 条指令，吞吐影响却只有 0–5%（straight-line 的 `memcpy` / `malloc` 代码 IPC 高），而框架里带分支的虚调用链每条指令更贵。
因此指令数只用来指方向，**取舍一律以配对吞吐为准**。

**教训**：压测客户端会逐字节核对每条连接的第一个回包——它抓到过我新写的诊断变体里的 bug（两个 iovec 重叠）。没有这个核对，一个回显错了的实现会被拿去比性能。
变异验证也抓到过一个测试缺口：拼接路径若漏了消耗已解的帧，旧帧会在下一次读时被重复分发，而原有用例在"拼完一个帧"之后就结束了。已补上"之后再发一帧，回包必须恰好是它"。

**诊断变体**（都在 `bench/net_bench.cpp`，`--impl` 取值）：`raw-iov`（裸 epoll，但系统调用形状与 breeze 相同）、`raw-iov+rdhup|cold|ptr|all`（再逐个加上 breeze 的特征）、
`breeze-fixed`（回复预先建好的固定 payload，不分配不拷贝，用来把框架开销与 echo 里的拷贝分开）。

### 9.3 P2b 对热路径的影响，与第 4 组基线（`MainLoopExecutor` 的代价）

**P2b 对热路径的影响**（改动后 ÷ 改动前，breeze 直接回调）：统计计数（每次 `read` / `Send` 各几次 load + store）、idle 钩子、每轮两次 `Clock::now()` 加起来每条消息十几条指令。

### 9.5 `Connection` 抽象成虚接口的成本（2026-10-31，实验，未并入代码）

为了决定"加 rudp 之前把 `Connection` 抽象成接口"值不值，在 `/tmp` 的副本里按抽象之后的样子改了一份：`Connection` 去掉 `final`，公开方法（两个 `Send`、`Close`、
`CloseGracefully`、`PauseRead`、`ResumeRead`）与事件循环执行任务用的方法（`SendFromTask`、`CloseFromTask`、`CloseIdle`）全部改成虚函数；反汇编确认 echo 回调里的 `Send` 是
`call *0x20(%rax)`，也就是真的间接调用。仓库里的代码没动。

- **内存**：`sizeof(Connection)` 改前改后都是 288。`Connection` 本来就继承了带虚函数的 `Pollable`，vptr 早就在了，新增的虚函数只是往同一张虚表后面追加，没有新增指针、热字段也没有挪动。
  虚表从 40 字节变成 112 字节，每个类只有一份。
- **单次调用**（`/tmp` 里的微基准，release）：非虚 0.33 ns；虚（单一动态类型，预测命中）0.82 ns，多约 0.5 ns；两种类型规律交替 0.76 ns；两种类型**随机**交替（分支预测失败的最坏情况）4.0 ns。
  一条消息多一次这样的调用（`OnMessage` 里的 `Send`；经 `ConnectionHandle` 投递的路径是任务执行时多一次 `SendFromTask`），而一条消息在 IO 线程上要花约 4–5 µs（单线程 20 万 msgs/s 上下），
  所以占 0.01%（预测命中）到 0.08%（最坏）。
- **`net_bench` A/B**：同一个 release 配置、绑核方案同 §9.1，**11 轮、每轮里两个二进制的先后顺序交错**，6 个配置（TCP / UDS、64B / 1KB、1 / 64 连接、`breeze` 与 `breeze-mainloop`）。
  各配置中位数差在 -5.6% 到 +3.2% 之间（正负都有，是噪声）；全部 66 组配对的平均差 +0.44%、标准误 0.66%，95% 置信区间约 [-0.85%, +1.72%]。
  **没有检出损失**；分辨不出 ±1% 以内的差别，所以结论是"不大于约 1%，理论值远小于它"。
- **这次实验没覆盖、实现时要盯住的一点**：抽象基类**不能放数据成员**。派生类的成员排在基类子对象之后，如果把对端信息、句柄、上下文这些冷字段搬进基类（约一百多字节），
  具体类里原来"热字段集中在前两条缓存行"的布局就整体后移，热字段会跨到第三条缓存行（见 `connection.h` 里的成员顺序注释与 §9.1 / §9.3：10 万连接时每连接多碰一条缓存行是可测量的代价）。
  所以接口只放虚函数，冷字段继续放在具体类的最后，再用 `sizeof` / `offsetof` 核对；真做的时候还要再跑一次这样的 A/B。

### 9.7 rudp 基线（2026-10-31）

本节是 rudp 刚实现、**优化之前**的第一份基线，保留来标出优化前的状态；**完整的一轮（含 UDS、muduo、内存、会话多活跃少，用最终代码）见 §9.9，数字以 §9.9 为准**。两轮之间没改过的 raw-udp / raw TCP 也整体高了约 8%–9%，是机器状态不同，不是优化的效果。

**方法**：同一个 `net_bench`（单 IO 线程、闭环 ping-pong、绑核、3 轮取中位数），加了 `--transport udp`：

| 实现 | 是什么 |
|---|---|
| `raw-udp` | 裸 UDP 回显：一个 socket、`recvmmsg` 批量收、`sendto` 回。没有会话、没有可靠性，是 UDP 的上限 |
| `rudp` | 本库 `RUdpServer`（1 个 IO 线程），echo 用视图版 `Send`，**`flush_on_send = true`**（每条回复立刻发出，低延迟配置） |
| `rudp-batched` | 同上，但用默认的批量配置（`flush_on_send = false`，回复等下一次 10ms 的 KCP 定时器） |

压测客户端：raw-udp 的每条连接是一个 connect 过的 UDP socket；rudp 的每条连接多一个 `KcpSession`（凭服务端签发的票据握手），每条消息 `Update + Send + Flush`，并逐字节核对每条连接的第一个回包。
**回环、没有加密、没有网络丢包**（过载区除外）；机器与绑核同 §9.1（服务端 cpu2，压测线程 4/6/8/10）。TCP 对照是同一轮里跑的 muduo 与 breeze。
复现：`TRANSPORTS="tcp udp" bench/run_baseline.sh`（原始数据与汇总表由脚本产出，下面是摘要）。

**怎么读这些数字**：衡量本库的开销，看 **rudp 相对 raw-udp**（同一个传输）。**回环上 UDP 的内核路径比 TCP 便宜**——raw-udp 比 raw TCP 在 64 连接下快 49%（283k 对 190k），
所以 rudp 比 TCP 上的 breeze / muduo 在 64 连接下快 31%–43%，是传输的差别，不是 KCP 更高效，**不要拿它当"rudp 比 TCP 快"的结论**。真实网络上 UDP 没有这个便宜，还要加上丢包重传与（将来的）加密。

| 消息 | 连接 | raw-udp | rudp | rudp / raw-udp | muduo(TCP) | breeze(TCP) | rudp / breeze |
|---|---|---|---|---|---|---|---|
| 64B | 1 | 33,851 | 32,888 | 97% | 31,274 | 31,636 | 104% |
| 64B | 64 | 283,537 | 227,838 | 80% | 161,223 | 159,088 | 143% |
| 1024B | 1 | 33,500 | 32,143 | 96% | 31,391 | 31,328 | 103% |
| 1024B | 64 | 267,895 | 214,961 | 80% | 163,504 | 155,140 | 139% |

（吞吐 msg/s，中位数。同一配置各次重复之间的波动：rudp 最大 9%，raw-udp 最大 23%，breeze 最大 17%；**差距小于它的不下结论**。）

- **单连接**是往返延迟主导（服务端线程只用 45% CPU）：p50 rudp 27–28µs，raw-udp 26–27µs，TCP 28–29µs，三者在噪声内；rudp 的 p99 94–99µs 与 raw-udp 的 88µs 也接近。
- **饱和时的每条消息服务端成本**（64 连接，服务端线程 100%）：raw-udp 3.56µs、**rudp 4.39µs（多 0.83µs，+23%）**、raw TCP 5.26µs、breeze TCP 6.29µs、muduo TCP 6.27µs。
  这 0.83µs 是 KCP（`ikcp_input` / `recv` / `send` / `flush`、每段一次 `malloc`）加会话逻辑（按来源找会话、积压记账）的总和；**没有拆开归因**（本机没有 `perf`，valgrind 太慢），哪一块占多少未知。
- **会话多、活跃少**（10000 个会话已建立，只有 64 条 ping-pong；**优化前**的数字，优化后见 §9.8 与 §9.9）：raw-udp 与 TCP 的各实现基本不受影响（±13% 在波动内），**rudp 掉 14%（64B）/ 12%（1024B），p99 从 568µs 涨到 1085µs**。
  原因是**我的实现**每个 interval（10ms）把所有会话逐个 `Tick`、每个都调一次 `Update`（这是实现的选择，不是 KCP 的要求：KCP 只在有事可做时才需要 `Update`，头文件里还给了 `ikcp_check` 来算下次该调的时刻）：空闲的 10000 个会话单独占服务端线程 **6.7% 的 CPU**（1000 个 0.85%，约 67ns 每会话每拍），而且是每 10ms 一次、每次连续约 0.67ms 的突发——正好对上 p99 的涨幅，
  热数据还被它挤出缓存。TCP 的空闲连接不占 CPU。这是优化前 rudp 在会话数上的真实代价，**已在 §9.8 优化掉**（只对有事可做的会话调 `Update`）。
- **内存**（每条空闲连接在服务端进程里的 RSS 增量；TCP 的内核缓冲不计入）：**rudp 约 5.5KB/会话**（大头是 `ikcp_setmtu` 按 `(mtu + 24) × 3` 分配的收发缓冲，mtu 1400 时约 4.3KB），breeze TCP 约 0.9–1.0KB，muduo 约 3.1KB。10000 个会话约 54MB。
- **`rudp-batched`（默认配置）**：闭环 ping-pong 下每条连接被钳在约 100 msg/s（p50 10.1ms ≈ `interval_ms`），64 连接约 6,000 msg/s。**默认配置不适合严格的请求–应答低延迟，要开 `flush_on_send`**；
  批量的价值（小消息合进一个数据报、少系统调用）在一条连接上连续发多条小消息的场景，**这里没有测开环负载**。
- **过载区**（10000 条全活跃的闭环）：UDP 没有背压，服务端接收缓冲被内核封顶在约 416KB，装不下的请求被丢（`RcvbufErrors` 每秒 4.6–6.2 万），靠重传补，rudp 的 p99 约 1 秒（KCP 重传的退避）。
  吞吐 156k–166k 只说明服务端一直是满的，**不是容量**；TCP 在同样负载下靠流控得到 91k–97k、延迟约 100ms 但不丢。这一行只用来说明 rudp 在过载时的行为（丢 + 重传，不崩、不乱序）。

**测量时踩的坑**：
- **本机内核上 `bind(端口 0)` 每次约 10ms 且随数量线性变慢**（2500 个要 25 秒），只 `connect` 让内核自动绑定则是瞬时的；压测客户端因此不显式 `bind`，否则 10000 连接的启动就要 100 秒。
- **闭环压测在 UDP 上会掩盖丢包**：最初重发时重置了发送时刻，停顿被藏在延迟之外（延迟 p50 1.2ms 与吞吐按 Little 定律对不上，才发现大部分连接其实在等重发）。现在延迟从第一次发出算起，并在结果里报 `drops_per_s`。
- 压测客户端自己也在这 4 个核上跑 KCP：rudp 的客户端比 TCP 的裸 `read` / `send` 贵，但服务端线程在 64 连接以上都是 100% 满载，瓶颈在服务端，比的仍是服务端。

**没测 / 限制**：回环无丢包（真实网络上的重传、乱序、拥塞没有量化，只有 §11.1 的正确性用例）；没有开环 / 批量吞吐；没有加密（上 AEAD 之后每条消息还要加一次加解密）；只测了单 IO 线程；
`SO_REUSEPORT` 多 loop 没做；没有 `perf` 级别的归因。

### 9.8 基于压测的优化（2026-10-31）

**证据**：用 callgrind 拆 §9.7 里 64 连接满载时服务端 IO 线程的用户态指令（每条消息约 2,840 条；内核部分与 raw-udp 相同）。**callgrind 下客户端的定时重发被放大**，所以只看比例，不看绝对次数：

| 占比（用户态指令） | 项 | 是否可省 |
|---|---|---|
| ~49% | KCP 自身（`ikcp_input` 20%、`ikcp_flush` 16%、`ikcp_recv` 7%、`ikcp_send` 6%） | 固有 |
| ~9% | 按来源地址查会话表（`std::unordered_map` + `std::hash<string_view>` 的 `_Hash_bytes` 就占 5.7%） | 我的代码，可省 |
| ~10% | `malloc` / `free`（KCP 每段一次，分散在 KCP 各函数里） | 要自定义分配器，没做 |
| 4–6% | `ReadBatch` 每批把 16 个 `mmsghdr` 整个重写一遍 | 可省 |
| ~4% | 每条消息约 4 次 `steady_clock::now` | 可缓存到每批一次，没做 |

加上 §9.7 的"会话多、活跃少"（10000 个空闲会话让活跃连接掉 12%–14%、p99 翻倍），做了三项：

1. **静止的会话不参与定时器**（真正有效的一项）：没有未确认的数据、没有待发的确认 / 窗口通告、对端窗口不为 0 的会话（`KcpSession::NeedsUpdate`）调 `Update` 只会白走一遍。
   现在服务端只维护"活跃表"：`Input` / `Send` / `ResumeRead` 打破静止时把会话放进去（`RUdpConnection::Wake`），`Tick` 返回 false 时摘掉；活跃表为空就不装定时器。
   `ikcp_update` 对隔了很久的第一次调用会自己重置内部时钟，所以跳过不会出问题。确认仍然在下一拍（≤ `interval_ms`）发出，延迟与以前一样。
2. 会话表换成 `FlatHashMap` + 带随机种子的便宜哈希（键只有 20 字节，两次 64 位乘法混合）。
3. `ReadBatch` 只在线程第一次进来时填 `mmsghdr` 的固定字段，每批只重置 `msg_namelen`。

**A/B**（旧 / 新两个二进制交替运行、每轮先后顺序轮换、逐轮配对，11 轮；`raw-udp` 是对照组，代码没变，用来量噪声；压测客户端是修正前的，但回环上往返不到 10ms，不受下面"确认包"问题影响）：

|---|---|---|---|---|---|

| rudp 64B × 1 | 31,722 | 31,719 | -0.0% | [-2.0%, +2.0%] | 88→88 |

| **rudp 64B × 10000 连接 / 64 活跃** | 212,727 | 237,538 | **+12.3%** | **[+9.6%, +15.0%]** | **1151→555** |

- **10000 会话 / 64 活跃**：吞吐 +12.3%，p99 从 1151µs 降到 555µs，与"只有 64 个会话"时一样（558µs），也就是**空闲会话的代价基本消掉了**（237.5k 对 235.6k）。
  **10000 个空闲会话占服务端线程的 CPU 从 8.8% 降到 0.00%**（`--mem-probe`，1000 个会话 0.93% → 0.00%）。
- **哈希与 `ReadBatch` 两项的收益小到测不出来**：64 连接全活跃 +1.5%（区间含 0）、1024B +1.7%（区间下沿刚好 0），都在噪声（对照组 ±2%）的边缘。
  它们是否各自有收益、各占多少，这次的 A/B 回答不了（三项是一起测的，`tick` 那一项在这两个配置里没有作用）；留着它们的理由是代码更简单（少一个 `std::hash` 调用、少一遍初始化），不是因为测到了收益。
- 内存没变（5.5KB/会话），单连接延迟没变。
- 活跃的会话仍是每拍被检查一次（下面的"再细一步"让没到点的会话直接跳过）。

**再细一步：到点才调 `Update`**（同日）。上面的活跃表之后，活跃会话仍然每拍（10ms）被 `Update` 一次，哪怕它只有在途的数据、最早的重传还在 200ms 之后。回环上 RTT 只有 100µs，会话几乎立刻静止，这一步看不出差别；
**往返时间长时**，每条消息的整个在途时间里会话都在活跃表里，10000 个会话几乎永远都在，这才是它起作用的场景。

- **做法**：`KcpSession::PlanUpdate(now)` 算出"下次什么时候需要 `Update`"——有待发的确认 / 窗口通告 / 排队的数据，或已有段到了重传时刻 → 下一拍（`Soon`）；只有在途的段 → 最早的 `resendts`（`At`，`IKCPSEG` 在 `ikcp.h` 里是公开的，直接遍历 `snd_buf`）；
  对端窗口为 0 → 下一次探测 `ts_probe`；都没有 → 静止。`RUdpConnection::Tick` 没到点就直接返回；新的 `Input` / `Send` / `ResumeRead` 会把会话提前到下一拍（`immediate_`），所以确认与排队的数据不会等到重传时刻。
  **不能直接用 `ikcp_check`**：它的返回值最多是"当前 + interval"，而且还受内部 `ts_flush` 限制，只能让会话更早醒、不能让它睡得更久。
- **测试**：本机没有 `netem` 的权限（`tc qdisc add` 被拒绝），所以在压测客户端里加了**延迟线**（`--delay-ms D`：收到的和要发出的数据报各排队 D 毫秒，往返 2D，没有抖动、没有丢包）；
  闭环下负载由往返时间决定（连接数 / 往返），与服务端快慢无关，所以可以在**相同负载下直接比服务端的 CPU**。各连接的起点要在一个往返内错开：同时起步的连接在固定延迟下会一直同相，每个往返冲来一波突发，把服务端的接收缓冲打爆，污染比较。
- **新增 `rudp_updates` 统计**（`NetStats`）：定时器真正去推进 KCP 的次数。没有它，"到点才调"只是个性能行为，功能测试里看不出来，也就没法验证。

- **往返越长、会话越多，收益越大**。闭环下负载由 连接数 / 往返 决定（10000 / 0.1s ≈ 20000 / 0.2s ≈ 10 万 msg/s）：10000 连接时两版都被往返钳在 98k 左右，**看不到吞吐差，只看到服务端 CPU 少了 13%**；
  20000 连接时 v2 的服务端撑不住（87k、每秒丢 2.8k 个包、p99 1.1 秒），v3 回到 99k（理论负载的 99%）、丢包 49/s、p99 203ms（= 往返 200ms + 3ms）。回环上没有回退。
- 吞吐的收益只在 v2 接近饱和的 20000 连接那一行出现；这些数字都是**客户端侧模拟的固定延迟**（没有抖动、没有网络丢包），不是真实 WAN；真实网络上会话在途的时间更长、抖动让重传时刻更乱，方向一致，量级要实测。

**"仍有丢包"的定位**（本节初版写的是"剩下的没有查清"，现已查清）。症状：v3 在 10000 / 20000 连接下仍每秒丢 2k 左右（raw-udp 只有 ~150），p99 在 0.6–1.1 秒量级。

1. **丢在哪**：逐个 socket 看 `/proc/net/udp` 的 `drops`（压测结果里的 `srv_sock_drops_per_s`），与系统的 `RcvbufErrors` 对得上，**全在服务端自己的接收缓冲**（回环没有别的丢法）。
2. **是不是定时器的突发**：给 `TickAll` 与 `OnEvents` 计时，`TickAll` 平均 282µs、最长 1.6ms，`OnEvents` 偶有 1.9ms 的长尾；再做对照——把定时器整个关掉，丢包只少了不到四分之一，**定时器不是主因**。
3. **数数据报**（`/proc/net/snmp` 的 `InDatagrams` / `OutDatagrams`，压测结果里的 `dgram_in_per_msg`）：rudp 每条消息 **3.15 个**数据报，raw-udp 只有 2.08，多出的 1.15 个是**压测客户端**发的纯确认包。
   原因：客户端每条消息先 `Update` 再 `Send`；往返超过 KCP 的 10ms 门限后，`Update` 每次都把待发的确认单独发一个数据报。服务端的包率翻倍，而小包在内核里按 `truesize` 记账，约 416KB 的接收缓冲只放得下两三百个，于是溢出。
   回环上两次发送的间隔不到 10ms，过不了门限，所以一直没暴露。
4. **修掉之后**（客户端改成只 `Send` 再 `Flush`，不先 `Update`）：每条消息 **2.07 个**数据报（raw-udp 是 2.06），服务端 socket 丢包 5–28/s（raw-udp 约 160/s），p99 回到 102.7ms。

所以**这是压测工具的问题，不是库的**；但定位过程中抓到了库里一个真缺陷：

- **`KcpSession::Flush()` 不刷新 KCP 的内部时钟**。`ikcp_flush` 用内部的"当前时间"（`kcp->current`）给段打时间戳、算重传时刻，而它只在 `Update` / `Input` 里更新。`flush_on_send` 路径上，会话静止很久之后再发一条，
  时间戳是很久以前的，重传时刻 = 很久以前 + RTO 早已过去，**下一拍白白重传一次**；对端确认时算出的 RTT 还包含整段静止时间，RTO 被拉到几十秒，之后真丢了包要等很久。
  这个缺陷是前面"静止的会话不参与定时器"放大的（以前每 10ms 都有一次 `Update` 顺手刷新时钟，静止的间隙短）。现在 `Flush(now)` 必须传当前时刻（`kcp_session.h`），`RUdpConnection::SendImpl` 传 `KcpNowMs()`。
  测试与变异验证见 §11.1。

**测量时踩的坑（补充）**：
- **自己的压测客户端会改变被测流量**：判断"丢包是不是库的问题"之前，先数每条消息的数据报个数（和裸 UDP 对比），再谈别的。
- **闭环、回环下的"没问题"可能只是时间尺度没到**：KCP 的 10ms 门限在 RTT 100µs 的回环上根本触发不了，必须加延迟（`--delay-ms`）才能走到那条路径。
- 数字都是**客户端侧模拟的固定延迟**（没有抖动、没有网络丢包），不是真实 WAN；真实网络上会话在途的时间更长、抖动会让重传时刻更乱，方向一致，量级要实测。

**没做、与它们的预期收益**（需要时的顺序）：
1. **`SO_REUSEPORT` 多 loop**：这是唯一能提高容量上限的办法——服务端线程从 64 连接起就是 100% 满载（rudp 约 23 万 msg/s，TCP 那边 `EventLoopGroup` 已经能把连接分到多个 loop）。
   内核按四元组哈希把一个客户端固定在一个 loop 上，正好适合"按来源固定会话"；工作量是每个 loop 一个 socket、一份会话表与定时器，共用 `TicketTable`；端口填 0 时要先 bind 一个再让其余的绑同一端口。
2. **KCP 的段分配走自定义分配器**（`ikcp_allocator` + 线程本地空闲链表）：`malloc` / `free` 约占用户态指令的 10%，估计能省 2–3% 的吞吐，要处理跨线程释放（会话在回收时由 loop 线程释放，基本都在同一线程）。
3. **每批只取一次时钟**：每条消息约 4 次 `steady_clock::now`（vDSO，约 20ns 一次），估计 1–2%。
4. **每会话 5.5KB 里的 4.3KB 是 `ikcp_setmtu` 一次分配的收发缓冲**，不改 KCP 缩不下来；`mtu` 调小可以按比例省，但每个数据报装的数据也少了。
5. **开环 / 批量吞吐没测**：一条连接连续发多条小消息时，批量配置（`flush_on_send = false`）能把它们合进一个数据报；输出路径上可能还有 `sendmmsg` 这一类的收益，需要先有这个负载的基线。

### 9.9 完整压测与数据整理（2026-10-31）

**摘要（先看这个）**：回环、单 IO 线程、64B echo、没有业务逻辑。**有代表性的负载是定速的**：每条连接按固定间隔发送（均匀的开环节拍，纳秒精度），
总负载 5 万 msg/s——各实现都在满载以下——所以比的是**同一负载下的延迟与服务端 CPU**；连接数从 1000 到 10 万的完整结果见 §9.10。
延迟单位 µs，格式 p50 / p99；CPU 是服务端 IO 线程占一个核的百分比（括号里是主循环线程）；"最高达标负载"是 10000 连接下实际吞吐 ≥ 设定的 99% 且 p99 ≤ 5ms 的最高负载（扫描 2.5 万到 20 万 msg/s，每点 2 轮）；
内存是每条空闲连接在服务端进程里的 RSS 增量（最大连接数下）。1 连接 p50 来自闭环 ping-pong（看往返延迟下限，见下面的"1 连接 / 64 连接"）。
原生 TCP / UDS / UDP（不用任何框架的裸 epoll / 裸 UDP，压测里叫 `raw` / `raw-udp`）是基准；"IO 线程直接处理"是业务回调在 IO 线程里跑（不能碰主循环的数据），
"投递主线程处理"是游戏服务实际的用法。表 3 里 breeze 框架的 UDP 是 rudp（`flush_on_send`）。UDP 最多测到 2.5 万连接（本机限制，见 §9.10）。

**完整数据**（下面是全部实现的明细，含 `breeze`（直接回调）、`breeze-fixed`、`rudp-batched` 等对照与诊断用的实现）：


§9.1–§9.6 是 TCP / UDS 的历史基线与 A/B，§9.7–§9.8 是 rudp 的基线与优化；这一节用**最终代码**把 TCP、UDS、UDP 一次性重跑并整理。

**范围**：
- tcp：`raw`（裸 epoll）、`muduo`、`breeze`（`ConnectionHandler` 直接回调，echo 用视图版 `Send`）、`breeze-fixed`（回固定 payload，不分配不拷贝）、`breeze-mainloop`（经 `MainLoopExecutor` 回投主循环，真实的 `App::Run` + `NetModule`）；
- uds：同上去掉 `muduo`（它不支持 UDS）；

**怎么读**：

1. **TCP**：`breeze` 在 64 连接下是 raw 的 93%（64B）/ 88%（1024B），**与 muduo 持平或略快**（103% / 100%）；1 连接下所有实现在 ±3% 内（往返延迟主导，服务端线程只用 46% CPU）。
   10000 连接全活跃是满载排队的区间（p50 ≈ 100ms ≈ 10000 ÷ 吞吐），各实现吞吐都在 raw 的 91%–100%。`breeze-mainloop` 多一次跨线程往返：1 连接下延迟翻倍（p50 56µs 对 30µs，吞吐约一半），64 连接起被饱和的 IO 线程掩盖（92%）。结论与 §9.3 一致。
2. **UDS**：`breeze` 在 64 连接下是 raw 的 94%（64B）/ 92%（1024B），`breeze-mainloop` 97% / 91%；`breeze-fixed` 比 `breeze` 还低是噪声（见下面的波动，四分位距 11%–14%），**不是结论**。
   10000 连接全活跃时 `breeze` 是 raw 的 95%–97%，**`breeze-mainloop` 却是 raw 的 160%–164%（p50 45–48ms 对 72ms）——没有查原因**，且 64B 这一行 raw 自己的四分位距就有 14%，
   它是排队的过载区，**不要当成"主循环回投比直连快"的结论**。
3. **UDP**：`rudp` 在 64 连接下是 `raw-udp` 的 79%（64B）/ 80%（1024B），1 连接下 97% / 96%（p50 28µs 对 28µs）。每条消息多花约 0.87–0.93µs（4,238 对 3,367；4,685 对 3,758）——KCP 加会话逻辑的总和，**没有拆开归因**（没有 `perf`）。
   `rudp-batched`（默认配置）闭环下每条连接被钳在约 100 msg/s（p50 ≈ `interval_ms`），**默认配置不适合请求–应答，要开 `flush_on_send`**；批量的价值在一条连接连续发多条小消息的场景，这里没有测开环负载。
4. **TCP 对 UDP**：64 连接下 `rudp` 是 `breeze` 的 129%（64B）/ 124%（1024B）、`muduo` 的 133% / 125%。这是回环上 UDP 的内核路径便宜（`raw-udp` 比 raw TCP 快 51% / 36%），不是 KCP 比 TCP 高效；
   真实网络上没有这个便宜，还要加丢包重传与（将来的）加密。**衡量本库开销看 `rudp` 相对 `raw-udp`。**
5. **会话多、活跃少**：TCP 与 UDP 各实现的变化都在 ±5% 内（噪声内）；**`rudp` 是 -1%（64B）/ +4%（1024B）**，空闲会话不再拖累活跃连接（优化前掉 14% / 12%，§9.7；§9.8 的优化）。
6. **内存**：`rudp` 约 5.5KB/会话（大头是 `ikcp_setmtu` 分配的 4.3KB 收发缓冲），是 `breeze` TCP（约 0.8–1.0KB）的 6 倍、muduo（约 3.1KB）的 1.8 倍；10000 个会话约 54MB。**所有实现的空闲 CPU 都测不出来**（rudp 在 §9.8 之前不是）。
7. **过载区**（10000 条全活跃）：UDP 没有背压，rudp 每秒丢约 4.8–5.3 万个数据报、p99 约 0.9 秒（重传），`raw-udp` 在这一行丢得更多（每秒约 9 万个、p99 0.5–0.8 秒）；
   这两行的吞吐只说明服务端一直是满的，**不是容量，也不可互相比**；TCP 靠流控不丢，p50 ≈ 100ms。

**稳定性**：四分位距 ÷ 中位数只对做了 8 轮的 UDS 算得出（3 轮没有意义）：最大 14%（`uds 64B × 10000 raw`、`uds 64B × 64 breeze-fixed`），`breeze` 11%、`raw` 10%，其余 ≤ 8%。
**极差**要大得多：UDS 与 raw 偶尔出现整轮被拉低的情形（`uds 64B × 10000 breeze-mainloop` 的 8 轮里有 1 轮是 128k，其余 202k–247k）。
各实现的（最大 − 最小）÷ 中位数的最大值：raw 88%、muduo 15%、breeze 57%、breeze-fixed 55%、breeze-mainloop 56%、raw-udp 28%、rudp 15%、rudp-batched 8%。所以：
**UDS 要 8 轮取中位数；3 轮的配置，差距小于该实现的极差不下结论**（`raw` 与 breeze 的 UDS 配置波动最大，muduo、rudp 最小）。

**没测 / 限制**：
- 回环无丢包、无加密，真实网络上的重传 / 乱序 / 拥塞没有量化（§9.8 的延迟线只模拟固定延迟）；
- 定速只测了 64B；真实游戏的包长与频率分布没有，1000 以下的连接数没有单独测；10 万连接只有 TCP / UDS 测了（UDP 的限制见 §9.10）；
- 单 IO 线程，`SO_REUSEPORT` 多 loop 没做，容量上限（rudp 约 22–25 万 msg/s）就是单 loop 的；
- 没有 `perf` 级别的归因，rudp 的每条消息多出的 0.9µs 没有拆开；
- 没有开环 / 批量吞吐；没有在真机上跑；TSAN 没跑（§11.2）；
- 压测客户端与服务端在同一进程、同一台机器上，客户端占 4 个核；服务端线程在 64 连接以上都是满载，瓶颈在服务端，比的仍是服务端，但客户端的开销（尤其 KCP）也在这些数字里。

### 9.10 连接规模：1000 / 5000 / 10000 / 100000（2026-10-31）

按业界对网络库 / 网关的常见做法，把性能拆成四组指标，规模取 1000、5000、10000、100000 条连接（UDP 最多 25000）。回环、单 IO 线程、64B echo、没有业务逻辑，
实现与绑核同 §9.9。复现：`bench/run_scale.sh`（`SUMMARIZE_ONLY=1 RAW=… RAW_MEM=…` 只重新汇总）。

| 指标 | 回答什么问题 | 怎么测 |
|---|---|---|
| 建连耗时与速率 | 网关重启后十万玩家一起重连要多久 | 压测客户端 4 个线程顺序 connect，量建立 N 条连接的总耗时 |
| 每连接内存、空闲 CPU | 十万连接要占多少内存、空着会不会烧 CPU | `--mem-probe N`：服务端进程 RSS 增量 ÷ N；连接全建好后空闲 3 秒的服务端线程 CPU |
| 同负载下连接数的影响 | 连接多了，同样的流量会不会变慢、变费 CPU | 总负载固定 5 万 msg/s，连接数 1000 → 10 万，每条连接按固定间隔发（均匀开环节拍） |
| 负载扫描 / 拐点 | 单个 IO 线程最多扛多少流量而不劣化 | 10000 连接，总负载 2.5 万 → 20 万 msg/s，找实际吞吐 ≥ 99% 且 p99 ≤ 5ms 的最高负载 |

**方法说明**：
- **均匀开环节拍**：每条连接按固定间隔发送，各连接的起点在一个周期内均匀错开，发送时刻按到期时刻累加（晚了不让速率往下漂），纳秒精度的定时（`epoll_pwait2`，定时器松弛降到 1ns）。
  延迟从实际发出的时刻算起，**没有补偿"客户端自己晚发"的部分**（不是严格意义上避开了 coordinated omission，但客户端线程只占 10%–40% CPU，没有积压）。
- **为什么不用闭环全速测延迟**：闭环下的延迟只是排队（p50 ≈ 连接数 ÷ 吞吐）；而且回环上闭环会让客户端 / 服务端成批处理，吞吐比均匀到达高得多（见 §9.9 的"1000 / 10000 连接全速"）。
- **前一版的节拍有缺陷**（按毫秒取整的定时）：同一毫秒到期的发送攒成突发，实际速率只有设定的 94%（每条连接每秒 100 条时），UDP 的接收缓冲被突发打爆、p99.9 里混进约 100ms 的重传。已改掉并整套重跑，旧数据作废。
- 每组 3 轮取中位数（负载扫描每点 2 轮）；**p99 / p99.9 在这样的轮数下噪声很大**，下结论看 p50 与 CPU。

**怎么读**：

1. **建连**：10 万 TCP 连接，原生 1.7 秒（约 6 万/s），muduo 5.6 秒、breeze 直接处理 4.5 秒，**breeze 投递主线程 12.8 秒（约 7800/s）**；UDS 都在 1 秒以内。10000 连接时 muduo / breeze 的 1.2 秒几乎是常数，
   **推测**是 accept 队列（`somaxconn` 4096）溢出后客户端等了一次 SYN 重传（1 秒），没有抓包验证；所以它量的是"客户端一次性涌入时服务端排空 accept 队列的速度"，不是纯 accept 速率，且客户端每线程顺序 connect 也限制了上限。
   **投递主线程时 10 万连接的建立明显更慢，原因没查**（连接事件要经主循环登记，主循环每轮的 `wake_budget` 是 1024，是否在这里限速没验证）。rudp 25000 会话 0.5 秒（握手），主循环版 0.7 秒。
2. **内存**：每连接 TCP / UDS 的 breeze 约 0.9–1.0KB，muduo 约 3.1KB，原生几乎为 0（只有内核缓冲）；rudp 约 5.6KB（大头是 KCP 的收发缓冲）。10 万条 breeze TCP 连接约 90–100MB，25000 个 rudp 会话约 140MB。
   **空闲 CPU 全部测不出来**（0.00%–0.01%），包括 10 万条空闲连接和 25000 个 rudp 会话。
3. **同负载下连接数的影响**：各实现的 p50 与 CPU 在 1000 → 10 万连接间几乎不变（TCP 原生 CPU 60% → 67%，breeze 66% → 68%，投递主线程 76% → 77%；UDS 与 UDP 也是），连接数本身不是瓶颈。
   p99 随连接数略涨（TCP 原生 200 → 708µs，breeze 248 → 1086µs，UDS 基本不变），大概是连接多了之后缓存命中变差，**没有做归因**。
4. **每条消息的 CPU 成本**：均匀到达 5 万 msg/s 下，TCP 的 IO 线程占 66%（每条约 13µs），UDS 55%（约 11µs），原生 UDP 58%，rudp 72%；闭环全速下成批处理，每条只有约 3.4–5.9µs。
   所以**同一台机器上，"容量"取决于到达模式**：成批到达（突发 / 压测）下 19–27 万 msg/s，均匀到达下拐点只有 7.5–12.5 万（框架）。真实流量介于两者之间，规划容量按拐点算更稳。
5. **拐点（10000 连接）**：TCP 原生约 10 万 msg/s，muduo / breeze 直接处理 / 投递主线程都在 7.5 万（差别在噪声内）；UDS 原生 ≥ 20 万，breeze 两种用法 12.5 万；UDP 原生 ≥ 20 万，rudp 直接处理 12.5 万，投递主线程 10 万。
   过了拐点 IO 线程满载，延迟迅速升到几十到一百多毫秒（TCP）或几百毫秒（rudp，丢包后靠重传）。拐点之下的 p99 都在 2 毫秒以内。
6. **投递主线程的代价**（稳态，同负载）：p50 多约 23–29µs（TCP 47 → 74，UDS 42 → 69，rudp 40 → 65），IO 线程 CPU 多 7–15 个百分点，主循环线程另占 15%–18%；拐点 TCP、UDS 与直接处理持平，rudp 低 20%（12.5 万 → 10 万）。

**没测 / 限制**：
- **UDP 做不到 2.5 万以上**：服务端按来源 ip:port 固定会话，每条连接要一个独一无二的来源地址，内核自动选端口只有约 2.8 万个；显式 `bind` 在本机每次固定约 10ms 且全局串行（多线程不重叠，换 IPv6、`SO_REUSEADDR` / `SO_REUSEPORT` 都一样，
  像是沙箱对 `bind` 的限制），10 万条要 1000 秒以上；改连不同的回环目的地址也不行（回环上源地址永远是 127.0.0.1）。**10 万 rudp 会话的内存与稳态延迟没有实测**，要到真机上、多个源 IP 上测。
- **业界常测但这里没做的**：服务端主动推送 / 广播（游戏状态同步的主流量，不是请求–应答）、长时间稳定性（浸泡，内存增长与延迟漂移）、连接抖动（持续的断开 / 重连）、慢消费者下的背压行为。其中推送 / 广播是下一步最值得补的。
- 回环、WSL2：睡眠线程的唤醒偏慢，均匀到达下的 CPU 与拐点比裸 Linux 悲观；客户端与服务端在同一进程、同一台机器，客户端的开销在数字里。
- 只测了 64B；真实游戏的平均包长更接近 100–200B，同一负载下预期 CPU 略高，没有测。

### 10.2 待基准决定项

正文只写默认做法；下表各项在对应阶段的基准里定案，接口不因此改变。

| 项 | 默认 | 何时切换 |
|---|---|---|
| 读触发方式 | 水平触发，每次就绪读一次 | 边缘触发在 P3 基准里吞吐/延迟明显更优，且不出现同 loop 饿死 |
| 跨线程直写（调用线程在出队列为空且抢到写权限时直接 `write()`，不走任务队列与唤醒；与"IO 线程直写"是两件事） | 关闭 | UDS ping-pong p99 明显受益；并发正确性需 TSAN 全覆盖 |
| 消息缓冲 | IO 线程路径给视图（零拷贝）；`MainLoopExecutor` 入队时拷贝成 `SharedBuffer` | 基准显示该拷贝成为瓶颈，新增块链类型（与 `SharedBuffer` 并存，为 `Send` 增加重载），不改 `SharedBuffer` 的名字与签名 |
| `SharedBuffer` 分配 | 通用分配器（视图版 `Send` 已让 echo 这类回包免分配；必须分配 `SharedBuffer` 的路径在 UDS 小消息上实测约 5% 的分配拷贝成本，malloc 与 memcpy 各占多少未分开测，见 §9.1） | 出现可证明的分配热点，再造池（需跨线程归还通道） |
| 队列实现 | moodycamel | 互斥+整批 swap 仅在 `net_bench` 作对照，不进库；接口不变 |
| `PickLoop` | 选连接数最少的 loop（muduo 为 round-robin） | 实现成本或竞争过高时退回轮询 |
| 发送侧总量上限 `max_pending_bytes_per_loop`（按 loop 计数，超限关 pending 最大的连接） | 不做（等价于不限） | 出现真实 OOM 风险或应用层需要时再加，默认 0 = 不限 |
| 主线程内联跑 `EventLoop` | 不做 | 两次线程跳转的延迟不可接受时评估（`RunOnce` 已保留，届时公开 `EventLoop`） |

**消息缓冲**保持"入队时拷成 `SharedBuffer`"（64B / 1KB 下不是瓶颈，§9.3）；`SharedBuffer` 分配、队列实现不变；`PickLoop` 的"最少连接"实测分布均匀（`stream_server_test` `TestConnectionsSpreadAcrossLoops`），不退回轮询。

## 11. 验证

测试沿用仓库做法：自带 `main` + `add_test`，不引 gtest。

- **队列**：单线程语义、MPSC 每生产者内部顺序、`TryDequeueBulk` 契约、move-only 类型、压力测试；SPSC、MPSC 各用 TSAN 跑一遍（带 `tsan.supp`，见 §3）。
- **单测（`ctest`）**：`Buffer`/`LengthPrefixCodec`（分片、超长、半包）；`Endpoint` 解析（含非法字符串返回空）；`ConnectionTable` generation 校验与槽对齐；`GroupRegistry`（group 销毁后 `Send` 返回 `Closed`、`loop`/`slot` 越界返回 `Closed`、注册表满返回 `ENOSPC`）；`EventLoop` 跨线程 `Post` 与定时器（假时钟）；唤醒协议不丢唤醒且 `eventfd` 读空后不空转（多生产者长压力，带超时断言）。
- **连接行为**：TCP 与 UDS 同用例 echo；过载拒绝（连接表满、`AcceptFilter` 拒绝、`EMFILE`）不产生回调且按原因计数；慢读方触发水位 → `Send` 返回 `Closed` → `SlowConsumer` 关闭；对端 RST/半关闭的 `CloseReason`；`EPOLLHUP`/`EPOLLERR` 的关闭原因与 `sys_errno`；回调内 `Close` 自己不崩且 `OnClosed` 只一次；对端永不关闭时 `CloseGracefully` 超时强关且不丢最后一条；同一块 `SharedBuffer` 发送到多条连接不拷贝数据且各连接帧头独立；`OnMessage` 视图在回调返回后不被依赖（ASAN）；`PauseRead/ResumeRead` 不丢消息不乱序；10k 连接冒烟。
- **空闲**：被 `PauseRead` 暂停的连接不被 idle 扫描误杀，`ResumeRead` 后刷新 `last_active_time`。
- **重连**：退避序列；断线 fail-fast；TCP self-connect 被识别并重试；UDS `ENOENT`/`ECONNREFUSED` 按退避重试；黑名单以外的错误（如 `ETIMEDOUT`）会重试；`connect_timeout` 对黑洞地址生效；`on_connect_failed` 按预期触发，不可重试错误时 `will_retry=false`、状态回到 `Idle` 且回调内 `Start()` 合法；`Running` 下重复 `Start()` 报编程错误；`Stop()` 关闭当前连接且其 `OnClosed` 只触发一次、之后无回调，先 `Stop` 再 `Start` 不会并存两条连接；句柄 raw 为 0 恒为无效。
- **资源与退出**：`bind` 冲突返回 `EADDRINUSE`、UDS 路径超长返回 `ENAMETOOLONG`、选项越界（`io_threads`、`max_connections_per_loop`）返回 `EINVAL`；`setrlimit(RLIMIT_NOFILE)` 制造 `EMFILE`、`RLIMIT_NPROC` 制造线程创建失败，验证 `EventLoopGroup::Start()` 中途失败后已起线程全部 join、fd 无泄漏；`accept` 遇 `EMFILE` 不死循环；`epoll_ctl(ADD)` 失败只关该连接；`Shutdown(deadline)` 在有积压时收敛；`NetModule::Start()` 失败后 `App::Run` 返回错误、进程以正常退出码退出。
- **集成**：`NetModule` 挂进 `App`，`Wake()` 预算耗尽返回 true 能续跑；析构时 IO 线程全部 join（TSAN/ASAN 各跑一遍）。
- **约定检查**：对 `base/net`、`base/buffer`、`base/thread`、`framework/net` grep `throw/try/catch`。
- **基准**：`net_bench` 产出 §9 的对比表，并给出 §10.2 各项的结论。

写测试时踩过的坑（后来人别再踩）：
- **本机临时端口只有几千个**：连接风暴类用例让客户端用 `SO_LINGER{1,0}` 关闭（RST，不留 `TIME_WAIT`），否则攒多了拖累后面的用例。
- **黑洞 connect 的造法**：监听 socket `listen(fd, 0)` 且不 accept、再连几条把 accept 队列填满，之后的 SYN 被内核丢弃，客户端 connect 挂在 `SYN_SENT`。用例先探测，内核不这么做就跳过。
- **`EACCES` 的造法**：root 绕过文件权限，所以 fork + exec 本程序、在新进程的 main 里降权到 nobody 再连一个进不去的 UDS 路径（exec 之前降权就读不到本程序了）；降不了权则跳过。
- **回调里引用的局部变量要比 group 活得久**：IO 线程到 group 析构才停，钩子捕获的变量声明在 group 之后会先于它销毁（ASAN 的 use-after-scope）。
- **多 loop 下 `OnConnected` 的回调顺序不等于客户端的创建顺序**，不要用 `WaitConnected(i)` 去对应第 i 个客户端。
- **独立审查**：并发路径没有 TSAN，所以找了一个不看作者结论的 reviewer 只读代码、专找并发与生命周期缺陷。它指出的问题里 6 个成立并已修（过期 `ResumeRead` 旁路背压、全局预算落在低 / 高水位之间时漏排队、
  停机宽限期入站无背压、`state_` 非原子且停机期间 `Start()` 会 `LOG_FATAL`、`Shutdown` 快路径丢连接、`Stop`→`Start` 在表满时误报 `ENOMEM`），1 个记为已知（`Stop` 与析构跨线程的乱序，§4.12）。

- **变异验证**：对关键判断逐个改坏再跑，确认测试会失败。第一轮有 4 个变异存活，都是测试偏弱（idle 的时间点没排到"刷新与否结果不同"、grace 定时器没覆盖到悬空、

  所以 **P2b 新增的并发路径只在 debug 与 asan+ubsan 下跑过**：停机钩子与 `BeginShutdown`、`EventLoop::CallSync`、`Connector` 的状态机与句柄发布、跨线程的 `PauseRead` / `ResumeRead` / `CloseGracefully`、统计计数。
  真机上：必要时先 `sudo sysctl vm.mmap_rnd_bits=28`，然后 `cmake --preset tsan && cmake --build ../../build/cpp-tsan && ctest --preset tsan`
  （`breeze_net_test` / `breeze_net_module_test` 已带 `tsan.supp`，只压制 moodycamel 的 fence 误报）。**失败时先看是不是误报，再看是不是本文 §4.5 / §4.12 / §5.1 的内存序假设被打破。**
- **P3 要重点看的**：`MainLoopExecutor` 里 `paused` 的 exchange 仲裁与"IO 线程暂停之后重查"（窗口只有几纳秒——主线程恰好在 IO 线程两步之间把积压消费光，测试里造不出来，
  变异验证里去掉这一步的变异存活，只能靠推理与压力用例）、`waiters_` 的排队 / 摘除、事件队列的懒创建与发布（`active_count_` 的 release / acquire）、`NetModule::Shutdown` 与 SPSC 单消费线程的约束。
- **rudp 的并发路径同样没跑过 TSAN**：`TicketTable` 的互斥锁（控制面线程签发、IO 线程取用）、`RUdpClient::SetTicket` 的互斥锁、`RUdpServer::live` 与 `RUdpClient::awaiting_closed`
  这两个"析构要等回调走完"的原子标志、客户端 `handle_` 的原子发布、跨线程 `ConnectionHandle::Send` 对 `pending_bytes` 的累加与 IO 线程按段数释放。
- **rudp 没有在真实网络上验证过**：只在回环（含代理模拟的丢包 / 乱序 / 黑洞）上测过；NAT 重绑定、真实的 MTU 分片、多网卡通配绑定的回包源地址问题（§4.14）、公网上的 ICMP 行为都没试过。
  性能基线只在回环、无丢包下测过（§9.7 / §9.9），真实网络上的重传、乱序、拥塞没有量化。
- **没有 TSAN 也跑过的**：debug 与 asan+ubsan 全部通过；`net_*` 与 `main_loop_executor_test` 在 debug / release 下各循环 10–80 遍无偶发失败。
