# 网络库设计：`base/queue` + `base/net` + `framework/net`

本文是 `breeze` C++ 网络库的设计基线：**结论、约束、代价、不变量**。

实现前先读本文。若发现本文与源码/测试冲突，以源码和测试为准，并回来改本文。
本文不写"怎么做"的细节实现，只写代码读不出的东西——为什么这样、代价是什么、失败模式是什么。

**状态**：P0（`base/queue`）与 P1（`base/net` 基础件：`Endpoint`、`PeerInfo`、`SharedBuffer`、`Buffer`、`FrameCodec`/`LengthPrefixCodec`、`Thread`、`Socket`）
已实现；P2a（`EventLoop`、`Connection`、`Acceptor`、单 loop 的 `LoopServer`，TCP / UDS / 抽象名同一份代码）
已实现并有基线数据与优化记录（§9.1 / §9.2）：验收标准"不低于 muduo"已满足（TCP 99.9–103.9%，见 §9.1）；与裸 epoll 的差距只作参考（TCP 95–99%，UDS 91–93%）。均在 debug / tsan / asan 下测试通过。`ConnectionHandle` 及以后（P2b 起）尚未实现。
**先例**：muduo（Reactor、`Connector`、`TcpClient`）、brpc（`SocketId` 句柄、写路径水位）、Netty、gRPC。
下文凡与先例不同之处，都写明了原因。

**评审准则**：发现问题先判断实际会不会发生，再看同类开源库是否处理，有先例且会发生才加机制。
理论上能发生、实际发生不了的情形，只记一句"已知且接受"，不加机制（例：§4.3 的 `pending_bytes` 偏差）。

## 0. 结论速查

### 要做

1. Reactor 线程池，one loop per thread；回调默认在 IO 线程，业务经 `MainLoopExecutor` 回投 app 主循环，保持「主循环单线程、业务无锁」。
2. 一个 `Connection` 同时承载 TCP 与 UDS，差异只在建立时，热路径没有 `if tcp`。
3. 连接生命周期只有一套机制：`ConnectionHandle`（generation）+ 延后回收，不叠加引用计数或 weak 句柄。
4. 背压用 `PauseRead`，不阻塞 IO 线程；写缓冲靠 `HighWaterMark` 兜底。
5. 断线 fail-fast：断开立即 `OnClosed`；`NetClient` 未连通时 `Send` 立即失败，不暗中缓冲。
6. 错误走 errno 返回值，库内不抛、不 catch。

### 不做（理由见 §8）

io_uring、TLS、UDP/KCP、WebSocket、DNS 解析、RPC 相关性/deadline/取消、有限次数重连；
群发、鉴权、限流策略、心跳内容、客户端协议格式一律留给应用层；sidecar 转发面暂不做。

### 不变量（见 §7，改设计前先看）

句柄不串话；每连接恰一个 `OnClosed` 且在最后一个 `OnMessage` 之后；`Send` 只有 `Ok`/`Closed` 两种结果；
解码错误即关闭；`Connection&` 只在其 IO 线程使用；`base/net` 不依赖主循环；回调 `noexcept`；net 库内不抛不 catch。

## 1. 背景与范围

### 1.1 要承载的四类链路

| 链路 | 传输 | 特点 |
|---|---|---|
| 客户端 ↔ 服务器（gate 接入） | TCP | 连接数多（1e4~1e5），慢消费者、半开连接、恶意包 |
| app ↔ sidecar | UDS | 同机、低延迟、可校验 peer 身份，sidecar 崩溃要让 app 立刻知道 |
| sidecar ↔ sidecar | TCP | 少量长连接，需自动重连 |
| 服务内部 | TCP/UDS | 同上 |

现状：`src/cpp/framework/app` 已有单线程主循环 + `IWaker`/`Notify()`。
网络库在传输层落实「主循环单线程、业务无锁」「断线 fail-fast」「句柄不串话」等约束。

### 1.2 范围与边界

- Reactor 线程池（one loop per thread）；回调默认在 IO 线程，可经 `MainLoopExecutor` 投递回 app 主循环。
- Linux epoll；`EventLoop` 直接使用 epoll，不设 poller 抽象。
- 传输层 + 可插拔 `FrameCodec`；RPC 相关性、deadline、取消属于上层。
- 无锁队列独立成 `base/queue` 公共库，基于 moodycamel，业务层同样可用。
- `base/net` 不认识主循环：回投主循环的事件队列、`Notify`、`Drain` 只在 `framework/net`。
- 本阶段只做基础库，不做 sidecar 转发面。

### 1.3 设计准则

- 每个公开类型都要能指向本文某条需求，否则不加；概念多少由需求决定。
- 连接生命周期只有一套机制：`ConnectionHandle`（generation）+ 延后回收。
- 每个行为都能用一句话规则说清，说不清就是设计有问题。

## 2. 命名约定

名字取自 muduo / Netty / asio / gRPC / brpc 的既有术语，风格与仓库一致：类型与方法 PascalCase，成员 `name_`，枚举 `enum class` + PascalCase。

| 概念 | 名字 |
|---|---|
| IO 线程上的事件循环 | `EventLoop`（内部类型，不公开） |
| 一组 `EventLoop` + 线程 | `EventLoopGroup` |
| 进程级 group 注册表 | `GroupRegistry`（内部） |
| 监听一个 endpoint | `NetServer`（内部用 `Acceptor`） |
| 连接一个对端并重连 | `NetClient`（内部用 `Connector`），选项 `ClientOptions`（`on_connect_failed`、`connect_timeout`） |
| 一条已建立的连接 | `Connection`（只在 IO 线程使用） |
| 跨线程安全的连接句柄 | `ConnectionHandle`（8 字节、可平凡复制，`group:4 \| loop:8 \| slot:20 \| generation:32`） |
| 回调接口 | `ConnectionHandler`：`OnConnected / OnMessage / OnClosed` |
| 在主循环上执行回调 | `MainLoopExecutor`，业务回调接口 `MainLoopHandler` |
| 分帧编解码 | `FrameCodec`、`LengthPrefixCodec`、`FrameCodecFactory` |
| 读缓冲 | `Buffer` |
| 引用计数的不可变字节块 | `SharedBuffer`（`(block, offset, len)` 切片值，最终名字） |
| 对端信息 | `PeerInfo{endpoint, credentials}`（两者都可空：UDS 客户端通常未命名，credentials 只有 UDS 有）、`PeerCredentials{uid,gid,pid}` |
| 每连接用户数据 | `ConnectionContext`（带虚析构的基类） |
| 接受前过滤 | `AcceptFilter`（`NetServer` 选项） |
| 暂停/恢复读 | `PauseRead / ResumeRead` |
| 发送水位 | `HighWaterMark`（发送侧） |
| 发送结果 | `SendResult{Ok, Closed}` |
| 慢消费者关闭原因 | `CloseReason::SlowConsumer` |
| 优雅关闭单个连接 | `CloseGracefully(timeout)` |
| 整组停机 | `EventLoopGroup::Shutdown(deadline)`；`NetServer::Stop()` 只停 accept；`NetClient::Stop()` 停重连并关闭当前连接 |
| 统计 | `GetStats() -> NetStats` |
| 跨线程投递到 loop | `EventLoop::Post` |
| 断言当前在 loop 线程 | `EventLoop::AssertInLoopThread()` |
| 线程封装 | `Thread`（`pthread_create`） |
| 空闲超时 | `idle_timeout`（默认 0 = 关闭）、`last_active_time` |
| 队列 | `SpscQueue / MpscQueue`、`Enqueue / TryEnqueue / TryDequeueBulk`、`ProducerToken`、`SizeApprox` |
| 重连退避 | `ReconnectPolicy{initial_delay, max_delay, multiplier, jitter}` |

`NetServer` / `NetClient` 不带 `Tcp` 前缀（不限 TCP），也不叫 `Server` / `Client`（避免与上层 RPC 层冲突）。

## 3. `base/queue`：通用无锁队列库

业务层也会用，所以是 `base/` 下的独立公共库。

- `breeze_queue` 为 `INTERFACE` 库，链接 `concurrentqueue::concurrentqueue` 与 `readerwriterqueue::readerwriterqueue`
  （模板必须在头文件里，所以依赖经 target 传递）。
- 用 `<moodycamel/concurrentqueue.h>` 与 `<readerwriterqueue.h>`，不用已 deprecated 的 `unofficial-concurrentqueue`。
  vcpkg 端口 `concurrentqueue` 1.0.5、`readerwriterqueue` 1.0.7 均在 manifest baseline 内；两个端口都没有 `usage` 文件，
  target 名 `concurrentqueue::concurrentqueue`、`readerwriterqueue::readerwriterqueue` 已按安装后的 `*Targets.cmake` 核实。
- **TSAN 对 `ConcurrentQueue` 有误报**：它用 `atomic_thread_fence` 同步（如 `Block::is_empty`），TSAN 不建模 fence，
  会报"生产者复用已读完的槽位"的数据竞争（作者在 `concurrentqueue.h` 里承认，`ReaderWriterQueue` 则整体标了 `no_sanitize`）。
  用 `src/cpp/tsan.supp` 只压制带 `moodycamel::ConcurrentQueue` 帧的报告，ctest 在 `tsan` 预设下自动带上；自己代码里的竞态照常报出。
- **对外 API 不暴露 moodycamel 任何类型**（含令牌），以后换实现业务代码不动。

| 类 | 约束 | 接口 |
|---|---|---|
| `SpscQueue<T>` | 恰一个生产线程、一个消费线程 | `Enqueue`（无界，不失败）、`TryEnqueue`（不分配，失败返回 false）、`TryDequeue`、`TryDequeueBulk(out, limit) -> n` |
| `MpscQueue<T>` | 多生产线程、一个消费线程 | 同上；另有 `MakeProducerToken()` 返回 RAII `ProducerToken` |

契约（写进头文件注释）：

- `TryDequeueBulk` 返回 `n < limit` ⇒ 队列已空。
- MPSC 只保证**每个生产者内部有序**，跨生产者无全局顺序。
- `TryEnqueue` 失败 = 没有预分配空间，**不是容量上限**；需要硬上限的调用方自带计数。
- 队列不负责唤醒；不提供阻塞版本。
- Debug 构建记录首个生产者/消费者线程 id，违反线程角色即断言。
- `SizeApprox()`；峰值由消费者在每次批量出队前采样，生产者路径零额外开销。

## 4. `base/net`

### 4.1 组件划分

| 本库 | muduo 对应 | 持有什么 | 职责 |
|---|---|---|---|
| `EventLoopGroup` | `EventLoopThreadPool` | N 个 `EventLoop`、N 个线程 | `Start/Shutdown`（启动时登记、结束时注销 `GroupRegistry`）；私有的 `PickLoop`；汇总 `GetStats`。不路由 `Send/Close` |
| `EventLoop` | `EventLoop` | epoll fd、eventfd 与 `sleeping` 标志、任务队列、`ConnectionTable`、本 loop 的 `Connection`、最小堆定时器、统计计数 | 一个线程上的全部 IO；idle 扫描；`Post` |
| `NetServer` | `TcpServer` | `Acceptor`、`Endpoint`、选项（含 `AcceptFilter`）、`ConnectionHandler&`、`FrameCodecFactory&` | 一个对象一个 endpoint；accept 后选 loop、把 fd 交过去 |
| `NetClient` | `TcpClient` | `Connector`、当前连接句柄（`std::atomic<uint64_t>`）、`ReconnectPolicy`、`ConnectionHandler&`、`FrameCodecFactory&` | 一个对象一个对端；固定在一个 loop 上（重连定时器也在这里）；自己不建线程 |
| `Connection` | `TcpConnection` | socket、读 `Buffer`、写队列、`FrameCodec` 实例、`ConnectionContext` | 一条连接的全部读写、水位、半关闭 |
| `ConnectionHandle` | — | 64 位 id（不含指针） | 可复制的值；`Send/Close/CloseGracefully/PauseRead/ResumeRead` 经 `GroupRegistry` 找到所属 loop，校验后 `Post` |

- gate 要同时监听 TCP 与 UDS：建两个 `NetServer`，共用一个 `EventLoopGroup`；需要不同线程数的链路用不同的 group。
- `NetServer`/`NetClient` 只持有 handler 与 `FrameCodecFactory` 的引用，调用方保证它们比 `Shutdown` 活得久（`Shutdown` 之后不再有回调）。
- **`NetServer`/`NetClient` 对象自己的生命周期必须覆盖到 `EventLoopGroup::Shutdown` 返回之后**：`Stop()` 是异步的，loop 上可能仍有引用 `this` 的任务和定时器。
  运行期按服务发现动态增删对端所需要的"停止完成通知"（如 `on_stopped`）暂不做，见 §8。
- 启动顺序：`NetServer`/`NetClient` 的 `Start()` 之前必须已 `EventLoopGroup::Start()` 成功，否则按编程错误处理。

### 4.2 一个 `Connection`，不分 TCP / UDS

差异只在建立时，不在热路径。

- `Endpoint` 值类型：`Tcp(ip,port) | Unix(path) | UnixAbstract(name)`，可从 `tcp://h:p`、`unix:///p`、`unix-abstract://n` 解析
  （配置里直接写字符串，走 `config/schema`），解析返回 `std::optional<Endpoint>`。**只接 IP 字面量，不做 DNS**：`getaddrinfo` 阻塞，不能在 IO 线程跑。
- `Endpoint` 的构造约束（三个工厂函数与 `Parse` 都返回 `std::optional`，拿到手的一定合法）：IP 规范化后保存（`::1` 与 `0:0:0:0:0:0:0:1` 相等）；
  v6 必须写方括号、方括号里必须是 v6（避免 `::1:80` 的歧义）；`Unix` 路径必须是绝对路径（相对路径依赖进程工作目录）；
  路径与抽象名都不能含 `'\0'`（`inet_pton` 遇到内嵌 `'\0'` 会悄悄截断成合法地址）。
- 建立连接时按 Endpoint 分支设选项（TCP：`NODELAY`、keepalive；UDS：取 `SO_PEERCRED` 填进 `PeerCredentials`）。`Connection` 以上不出现 `if tcp`，无传输层虚函数。
- UDS 契约：路径 ≤107 字节，超长报错；bind 前对残留 socket 文件做 connect 探测，无人监听才 unlink，有人监听报 `EADDRINUSE`。

### 4.3 `ConnectionHandle`：generation 与 group 注册表

`ConnectionHandle` = 64 位 `[group:4 | loop:8 | slot:20 | generation:32]`
（限制：每进程 ≤16 个 group、每 group ≤256 个 loop、每 loop ≤2^20 个连接）。8 字节、可平凡复制，提供 `==` 与 `std::hash`，可直接作 map 的键；日志打印为 `g<group>.l<loop>#<slot>.<generation>`。
**raw == 0 恒为无效句柄**：generation 从 1 起（2^32 次复用不可达，不处理回绕），所以 `NetClient` 的 `atomic<uint64_t>` 可用 0 表示无连接。
**位宽校验**：`EventLoopGroup::Start()` 校验 `io_threads` 在 1 到 256、`max_connections_per_loop` 在 1 到 2^20，否则返回 `EINVAL`。

与 brpc 的 `SocketId`（32 位 version + 32 位 slot，全局解析）同构；区别是多一层 `GroupRegistry`，且不用引用计数。

**连接表**

- `ConnectionTable` 是 generational slot map，每个 `EventLoop` 一张，按 `max_connections_per_loop` 预分配。
- 每槽有原子的 `generation / state / pending_bytes`（热字段，槽按 64 字节对齐 `alignas(64)`，避免主线程与 IO 线程更新相邻槽造成伪共享）。
- 发送侧：`generation` 不符 → `Closed`；`pending_bytes.fetch_add(len)` 后超过 `HighWaterMark` → 慢消费者（返回 `Closed` 并投递 Close）。
  校验与累加不是原子的，**不处理**：要在两者之间槽被回收并被新连接占用，而空闲槽按 FIFO 复用（要转完整条空闲链）；即使发生，也只是新连接的 `pending_bytes` 偏差一条消息的字节数。
  brpc 的 `_unwritten_bytes` 同样在检查之后累加，水位本就是软上限。
- IO 线程写完后 `fetch_sub(len)`；回收槽时 `generation + 1`、`pending_bytes` 清零。
- **任务在 loop 线程上执行时必须再校验一次 `generation`**，不符则丢弃并释放 `SharedBuffer`——这是"迟到的消息/事件不会串到新连接"的第二道保证。
- `last_active_time` 放在**单独的连续数组**里（只有所属 IO 线程访问），idle 扫描不碰 `Connection` 对象。
- 空闲槽按 FIFO 复用，拉长同一槽的复用间隔。连接状态（`Connecting | Connected | Disconnecting | Disconnected`）是槽里的原子量。
- `EventLoopGroup::PickLoop()` 选当前连接数最少的 loop，避免"某个 loop 满了总量没满却拒绝 accept"（muduo 为 round-robin，见 §10.2）。

**注册表**

- 进程级 `GroupRegistry`：固定 16 项的原子指针数组。`EventLoopGroup::Start()` 分配第一个空位作为 group 编号（使用方不指定），16 项用满返回 `ENOSPC`；`Shutdown`/析构末尾注销。
- 任意线程 `ConnectionHandle::Send` 的解析顺序：按 `group` 位取 group（空 → `Closed`）→ 校验 `loop`、`slot` 是否越界（越界 → `Closed`）→ 校验槽的 `generation` 并累加 `pending_bytes`（不符 → `Closed`）→ `Post` 给所属 loop。
- **group 销毁后其句柄作废**：解析不到时返回 `Closed`；若同一编号已被新 group 占用则不再保证；使用方须在销毁 group 前丢弃其句柄，并保证销毁时没有线程仍在 `Send`。
- 重连得到新句柄，迟到的消息/事件带旧句柄，不会串到新连接。

### 4.4 回调模型：`ConnectionHandler`

`base/net` 里只有一种回调，在连接所属 `EventLoop` 的 IO 线程上执行。

```cpp
struct ConnectionHandler {                      // 回调都在 IO 线程，必须非阻塞、noexcept
    virtual void OnConnected(Connection&) noexcept {}
    virtual void OnMessage(Connection&, std::span<const std::byte> payload) noexcept = 0;  // 视图，仅回调内有效；唯一必须实现的回调
    virtual void OnClosed(Connection&, CloseReason, int sys_errno) noexcept {}  // 每连接恰一次，且在最后一个 OnMessage 之后
};
```

- `Connection&`（只在 IO 线程有效，不可复制）提供 `handle()`、`Send`、`Close`、`CloseGracefully`、`PauseRead/ResumeRead`、`GetContext/SetContext`、`peer()`。
- **每连接上下文**放 `ConnectionContext`：基类带虚析构，`SetContext(std::unique_ptr<ConnectionContext>)`，`GetContext<T>()` 在 Release 下 `static_cast`、Debug 下 `dynamic_cast` 校验；避免业务按句柄再查一次哈希表。
- **接受前过滤**是 `NetServer` 选项里的 `AcceptFilter`（`bool(const PeerInfo&) noexcept`，在 IO 线程运行）；不放进 `ConnectionHandler`，因为 `NetClient` 也用它。
- `PauseRead/ResumeRead` 是正式的流控接口：`MainLoopExecutor` 用它做入口背压，业务也可用于自己的限流。
- **消息所有权**：`OnMessage` 的 payload 是读缓冲上的视图，只在回调内有效，要保留就自己拷贝。IO 线程路径因此零分配；拷贝只发生在真正需要跨线程的地方——`MainLoopExecutor` 入队时。
  在回调里立即回包不需要先拷：用 `Send(std::span<const std::byte>)`（见 §4.6），它直接从视图写出，写不完的部分才由库拷走。
- IO 线程回调适用于不需要业务状态的前置处理与低延迟路径，具体做什么由应用层实现。
- 默认给业务用的是 `framework/net` 的 `MainLoopExecutor`（见 §5），它自己实现一个 `ConnectionHandler`。两种用法共享同一个 `Connection`；回调线程由"给 `NetServer/NetClient` 传哪个 handler"决定，是它们构造时的必填参数。
- **`FrameCodec` 每连接一个实例**：`NetServer/NetClient` 构造时收 `FrameCodecFactory`，连接建立时创建。分帧器有状态（半包、序号），不能被多线程共享。

### 4.5 `EventLoop`：任务队列与唤醒

- 提供阻塞的 `Run()` 与 `RunOnce(timeout)`，**不在内部创建线程**；线程由 `EventLoopGroup` 创建并持有。loop 可独立存在，便于测试，也为"主线程内联跑"留口子。
- **`EventLoop` 不是公开类型**：放在 `base/net/internal/`，`ConnectionHandle` 不指向它；`NetServer`/`NetClient` 的公开头只前置声明；测试以私有 include 路径直接使用，不需要 `friend`。将来做主线程内联模式时再公开。
- 每个 `EventLoop` 一条 `MpscQueue` 任务队列（主线程与其他 IO 线程生产），**隐式生产者**，`TryDequeueBulk` 批量取。
  任务是小的带标签结构体 `{op, handle, SharedBuffer}`（`op` ∈ Send/Close/CloseGracefully/PauseRead/ResumeRead 等），**不用 `std::function`**，避免每次 `Send` 多一次堆分配。
  P2a 只有 `Call`（通用投递：`unique_ptr` 持有可调用对象，这一次分配只发生在通用投递上）与 `Quit` 两个 op；`Send` 等热路径 op 随 `ConnectionHandle` 在 P2b 加入。
  每轮最多处理 4 批（每批 64 个）任务，剩下的留给下一轮：下一轮睡前复查会取到它们，所以既不会在还有任务时睡着，也不会让"任务里再投递任务"的链饿死 IO。
- **不缓存 `ProducerToken`**：按 `EventLoop` 在 `thread_local` 缓存令牌，group 销毁重建后地址可能复用而拿到失效令牌，线程退出时令牌析构也会碰已销毁的队列。基准显示成为瓶颈再引入，且令牌生命周期须随 `EventLoop` 实例管理。
- 每轮顺序：`epoll_wait` → 分发就绪事件 → 处理任务队列。处理任务期间新入队的任务（含本线程投递的）必须在下一次睡眠前被看到。`epoll_wait` 的超时取最近的定时器与 idle 扫描时间。
- 少量定时器（重连退避、`connect_timeout`、`CloseGracefully` 超时）用 loop 内最小堆；时钟由 loop 注入，测试可用假时钟。

**唤醒协议**

- 无锁队列无法精确判断"空→非空"，不能靠它决定要不要唤醒。
- 消费者维护原子标志 `sleeping`：睡前置 true，再复查一次队列再睡；生产者入队后 `if (sleeping.exchange(false))` 才写 `eventfd`（只有一个生产者会写）。消费者**无论被什么事件唤醒，醒来后先 `sleeping.store(false)`，再把 `eventfd` 读空**，否则水平触发会空转。消费者忙时零系统调用，也不丢唤醒；"不丢唤醒"测试以此为断言对象。
- **内存序全部用 `seq_cst`**：这是 Dekker 式握手，两侧都需要 StoreLoad 屏障——生产者「入队 → `atomic_thread_fence(seq_cst)` → `exchange(sleeping, seq_cst)`」，消费者「`sleeping.store(true, seq_cst)` → `atomic_thread_fence(seq_cst)` → 复查队列 → 再睡」。丢唤醒是逻辑错误而非数据竞争，TSAN 与 x86 都抓不到，所以靠规格写死，并加带超时断言的长时间压力测试。
- **所有需要唤醒 loop 的状态变化都必须走任务队列，不能只改一个标志位**：标志位不受"睡前复查队列"保护，改完到进入睡眠之间会丢唤醒。
  `Quit()` 因此也是一个 `Quit` 任务；`quit_` 只在 loop 线程上读写。

### 4.6 写路径

- `Send` 返回 `SendResult{Ok, Closed}`：`Ok` 只表示网络层已接收，**不表示送达**；`Closed` 表示连接已关闭或正在关闭（句柄过期、状态非 `Connected`、或本次发送触发了慢消费者关闭），原因由 `OnClosed` 告知。
  用枚举而不是 `bool`：调用点可读，将来若要非关闭式背压，新增枚举值即可，不改签名。
- **`HighWaterMark`**（默认 256KB，内部链路按需调大）：`pending_bytes` 超过它 → 本次 `Send` 返回 `Closed`，并关闭连接（`CloseReason::SlowConsumer`）。
  这是**唯一的内建策略，作为内存安全兜底**；更细的策略（丢弃、降级、通知上游）属于应用层，留待将来的 `OnWriteBufferHigh` 钩子。
  **与先例不同**：brpc 超限返回 `EOVERCROWDED` 但保留连接，muduo/Netty 只通知应用。这里选择关闭，因为库内没有应用层策略钩子时，关闭是写缓冲有上界的唯一手段。
  检查与投递不是原子的，并发 `Send` 可能略超水位，水位是软上限。库内不设发送侧全局上限：最坏占用为连接数 × `HighWaterMark`（10 万连接约 25GB）；`pending_bytes` 对共享 payload 按每条连接各算一次，会高估实际占用。
- **`CloseGracefully(timeout)`**：连接转入 `Disconnecting`，发送队列排空后 `shutdown(SHUT_WR)`，同时启动 `timeout` 定时器，对端未在期限内关闭则强关。`Close()` 立即关。
- 出队列的每条消息是「内联帧头 + 共享的 `SharedBuffer` payload」，`writev` 一次最多 64 个 iovec（一条消息占两个），部分写记偏移；`EPOLLOUT` 仅在队列非空时注册。同一 loop 一轮内对同一连接的多次 `Send` 合并成一次 `writev`。
- **`SharedBuffer`**：引用计数的不可变块上的 `(block, offset, len)` 切片值。同一块 payload 可被多条连接同时持有，发送时不拷贝数据；应用层做群发时自己持有一组句柄循环 `Send` 即可受益。用通用分配器，不自建池（`SharedBuffer` 在 IO 线程分配、主线程释放，自建池需要跨线程归还通道）。
- **`Send` 与 `OnMessage` 对称，都只处理 payload**：帧头由该连接的 `FrameCodec::EncodeHeader(payload_len, header_out)` 生成。接口允许帧头带魔数、序号等字段，但这些属于应用协议，库不定义；逐连接加密 payload 无法让多条连接共享同一块 payload，若将来需要，放在 codec 之上并接受每条连接各一份的代价。序列化直接写进 `SharedBuffer::Create(size)`。
- **IO 线程直写**（默认开启）：IO 线程内的 `Connection::Send` 先尝试直接 `write`（写队列为空且未注册 `EPOLLOUT`），写不完才入队并注册 `EPOLLOUT`；跨线程的 `ConnectionHandle::Send` 经任务队列。
- **`Send` 有两个重载**：`Send(SharedBuffer)` 与 `Send(std::span<const std::byte>)`。
  - 视图版**不拿走所有权**：写队列为空时直接从视图写出，整帧写完就一次分配、一次拷贝都没有；写不完的部分、或前面已有积压必须排队保序时，才把内容拷成 `SharedBuffer` 入队。
    所以**返回之后视图指向的内存可以立刻改写或释放**（测试里返回后立刻把 3MB 原内存整个毁掉，客户端收到的仍是原内容）。
  - 用法：在 IO 线程里立即回包的 handler（echo、小的应答、栈上拼出来的响应）用视图版；已经有 `SharedBuffer`、要跨连接共享或要入队时用 `SharedBuffer` 版。
  - 先例：muduo 的 `send(const void*, int)` 同样是"能直接写就不拷贝，写不完才进输出缓冲"。P2a 最初只有 `SharedBuffer` 版，echo 回调手里只有仅在回调内有效的视图，只能先 `CopyFrom` 再发，
    每条消息白白多一次分配和拷贝，与 muduo 的 echo（`send(Buffer*)` 直接交换数据）并不对等（§9.1）。
- **用 `sendmsg(MSG_NOSIGNAL)` 而不是 `writev`**：对端已关闭时 `writev` 会向进程发 `SIGPIPE`，库不该替使用方改信号处置。
- **`Send` 的 payload 超过 codec 上限**（`EncodeHeader` 返回 0）：记 ERROR、以 `ProtocolError` 关闭连接并返回 `Closed`。
  对端按同样的上限会判协议错误并断开，不如本端先关，别让它带着错位的流继续跑。
- **读缓冲：线程本地优先，每连接只存半个帧**。`read` 进一块线程本地的 64KB 缓冲（所有连接共用，IO 线程一次只服务一条连接，回调里也不会再进入读路径），
  直接从它分帧；只有尾部不完整的半个帧才拷进每连接的 `Buffer`，下次读到的数据拼在它后面再解。每连接的 `Buffer` 初始容量为 0（空闲连接不占读缓冲内存），
  读空后若已长到 4KB 以上就释放（带滞后，避免稳定的跨读帧流量反复分配释放）。
  依据（P2a 基线分析，§9.1）：原先"每连接 1KB 缓冲 + 线程本地溢出缓冲"的写法，冷的每连接缓冲约让 UDS 小消息吞吐低 2.5%，且 10 万连接常驻 100MB。

### 4.7 读路径、分帧、空闲与半开检测

- 读：**水平触发，每次就绪只 `read` 一次**（最多 64KB），不循环读到 `EAGAIN`：一个灌包连接不会饿死同 loop 的其他连接。`accept` 同理。
- **事件分发顺序**：`EPOLLHUP` 且无 `EPOLLIN` → 关闭；`EPOLLERR` → 读 `SO_ERROR` 记入 `sys_errno`；`EPOLLIN`/`EPOLLRDHUP` → 读（读到 0 字节即对端关闭）；`EPOLLOUT` → 写。
- **`FrameCodec`**（每连接一个实例，有状态）：解码 `Decode(span data, sink, size_t& used) → NeedMore | Ok | Error`，sink 收到 `data` 内部的 payload 视图；编码 `EncodeHeader(payload_len, header_out) -> n`，只生成帧头（≤16 字节）。
  **`Decode` 一次最多解一帧**：`Ok` = 解出一帧并已交给 sink，`used` 是这一帧占的字节数，调用方据此推进并继续调用——这样才能在两帧之间检查连接是否已在回调里被关闭；
  `NeedMore` / `Error` 时 `used = 0`，`Error` 由调用方关闭连接。sink 是 `std::function_ref`（不分配），视图只在 sink 调用期间有效。
  接口只吃 `span`、不碰 `Buffer`，所以调用方可以直接从线程本地读缓冲分帧，只有半个帧才需要拷进每连接的缓冲。
  `EncodeHeader` 在 payload 超过上限时返回 0。`FrameCodecFactory::Create` 会被多个 loop 的线程并发调用（accept 在一个 loop，连接可能落在另一个 loop），实现必须线程安全。
  库只内置 `LengthPrefixCodec`（`u32` 长度 + `max_frame`），用于内部链路与测试；客户端协议由应用层实现自己的 `FrameCodec`。**解码错误/超长 = 关闭连接，不重新同步。**
  `max_frame` 默认值要小（如 64KB），它同时是读 `Buffer` 的上界。
- **idle timeout**：每个 loop 周期性分批扫自己的 `last_active_time` 数组（如每 100ms 扫 1/10），精度 ≤ 1s。**默认关闭**（`idle_timeout = 0`）；"活跃"= 收到任何字节，是库唯一的定义，更严格的判定（必须收到合法心跳，或按"上次完整消息时间"关闭滴灌式慢速连接）由应用层实现：`OnMessage` 只在完整帧到达时触发。
- **暂停期间不计空闲**：被 `PauseRead` 暂停的连接，idle 扫描跳过；`ResumeRead` 时刷新 `last_active_time`。
  否则后端过载、连接被长时间暂停时，开启了 idle 的连接会在过载期间被集体误杀。
- **半开连接（TCP）**：选项 `keepalive_idle / keepalive_interval / keepalive_count`（库默认 60s / 10s / 3，约 90s 发现对端消失）与 `tcp_user_timeout`；只开 `SO_KEEPALIVE` 而不设参数时内核默认 7200s，等于没开。UDS 不适用。
- 库内这类策略值默认保持中立（idle 超时默认关闭）；**生产默认值由 `framework/net` 的 `net.proto` 给出**。

### 4.8 重连、断线与停机

**`NetClient` 状态**：`Idle ⇄ Running`。`Start()` 在 `Idle` 下合法，在 `Running` 下重复调用是编程错误；`Stop()` 回到 `Idle`。
`Start()`/`Stop()` 可在任意线程调用，**都 `Post` 到所属 loop 串行处理**，状态机只在 loop 线程上推进：先 `Stop` 再 `Start` 的顺序由队列 FIFO 保证，`Running` 下重复 `Start` 的编程错误在 loop 线程上检测。因此 `Start()` 只返回参数类错误（如 UDS 路径过长 `ENAMETOOLONG`、端点非法 `EINVAL`），连接建立失败走 `on_connect_failed`；group 未启动是编程错误，不走返回值。
`Stop()` 停止重连并**关闭当前连接**（等价 `Close()`；要优雅关闭，业务先对句柄调 `CloseGracefully`）。该连接的 `OnClosed` 仍会且仅会触发一次，在它之后该 client 不再有任何回调；`Stop()` 本身不等待。
遇到不可重试错误时，状态先回到 `Idle`，再回调 `on_connect_failed(sys_errno, will_retry=false)`（IO 线程），回调内可直接调用 `Start()`。当前连接句柄是 `std::atomic<uint64_t>`（0 = 无连接）：IO 线程在连接/断开时写，任意线程的 `NetClient::Send` 读。

- `Connector` 持有 `ReconnectPolicy`（指数退避 + jitter、上限），**无限重试**，要停由调用方 `Stop()`；**断开立即发 `OnClosed(reason)`**。退避默认从 500ms 起翻倍、上限 30s，**连接成功后重置**。
- `NetClient` 未连通时 `Send` 立即返回 `Closed`，**不暗中缓冲**。
- **连接失败可观测**：`OnClosed` 只在连接建立之后才有，所以 `ClientOptions` 带可选回调（IO 线程，`noexcept`）——`on_connect_failed(sys_errno, will_retry)`（每次尝试失败；遇到不可重试错误时 `will_retry = false`，此后不再尝试，需调用方显式 `Start()` 重来）。放在 `ClientOptions` 而不是 `ConnectionHandler`，因为服务端也用后者。
- **`connect()` 的 errno 分类用黑名单**：不可重试 = `EACCES`、`EPERM`、`EAFNOSUPPORT`、`EBADF`、`EFAULT`、`ENOTSOCK`、`EINVAL`、`ENAMETOOLONG`；其余一律按退避重试——含跨机常见的 `ETIMEDOUT`、`EHOSTUNREACH`、`ECONNRESET`、`ENETDOWN`，以及 `EAGAIN`、`ECONNREFUSED`、`ENETUNREACH`、`EADDRNOTAVAIL`、`EADDRINUSE`、UDS 的 `ENOENT`（sidecar 尚未创建 socket 文件）。非阻塞 connect 以 `EPOLLOUT` 就绪后读 `SO_ERROR` 判定。
  与 muduo `Connector` 同构（它对 `handleWrite` 里任何非零 `SO_ERROR` 也一律重试）；这里改成黑名单，避免白名单漏掉跨机常见的 errno。
- **`connect_timeout`**（默认几秒）：非阻塞 connect 启动时挂定时器，超时按失败重试；否则连到黑洞地址要等内核 SYN 重试约 2 分钟。muduo 没有这一项。
- TCP 连接建立后检测 **self-connect**（本地与对端的地址、端口相同），按失败处理并重试。
- **连接的销毁延后**：`Connection` 在自己的回调里被 `Close` 时不立即销毁——标记关闭、投递 `OnClosed`，fd 关闭与槽释放（generation 自增）放进本轮事件分发之后的回收列表，保证回调栈内对象仍然有效；`OnClosed` 同样在回收时回调，不在 `Close()` 的调用栈里（回调里 `Close()` 之后的代码照常跑完）；`OnClosed` 之后不再有该连接的回调。
- `CloseReason`：`PeerClosed | LocalClose | IdleTimeout | ProtocolError | SlowConsumer | IoError(errno)`。
- **`EventLoopGroup::Shutdown(deadline)`**：拒绝新的 `Start`；各 loop 停掉自己的 `Acceptor`/`Connector` → 对所有连接 `CloseGracefully` → 等各 `ConnectionTable` 变空或到 deadline，到点强关 → 停 loop、join 线程。`App` 只管启动不管停机，所以这条由网络库自己提供；析构只做兜底。`NetServer::Stop()` 只停 accept，已接受的连接继续服务，由 `Shutdown` 收尾；`NetClient::Stop()` 见上；两者都不影响 group。

### 4.9 可观测性

每 loop 一份 relaxed 原子计数：accept/close（按 reason）、连接拒绝数（按原因：filter / 满载 / fd 耗尽）、字节/消息、`Send` 返回 `Closed` 的次数（按原因）、**event loop lag**（单轮最大耗时）、`PauseRead` 中的连接数。`EventLoopGroup::GetStats()` 累加成普通结构体 `NetStats`。
事件队列深度/峰值与全局入站预算占用由 `MainLoopExecutor` 统计。

### 4.10 日志

`base/net` 只依赖 `breeze_logger`，不依赖 framework。热路径不打日志；只记连接建立/关闭（带 `CloseReason`）、重连、协议错误等状态变化，逐消息日志一律不要。
部署建议（进程配置，不是库的约束）：日志 `Overflow` 默认 `Block`，磁盘变慢会卡住 IO 线程，网络库所在进程建议配 `DropOldest`，写进 `NetModule` 的部署说明。

### 4.11 错误与异常处理（只约束 net 库）

适用范围：`base/net` 与 `framework/net`。`base/queue` 等其他库不受此约束。

**net 库内不 `throw`、不 `try/catch`，不引入 `Result` / `expected` / `error_code` 作为返回类型。** 按错误性质分类：

| 类别 | 例子 | 处理 |
|---|---|---|
| 建立期失败（环境/配置原因） | `epoll_create1` / `eventfd` / `socket` / `bind`（`EADDRINUSE`、`EACCES`、`ENAMETOOLONG`）/ `listen` / 创建线程 / group 注册表已满 / 选项越界（`EINVAL`） | `Start()` 返回 errno（0 = 成功），**已获取的资源自行回滚**；`NetModule` 转成框架 `Result<>`，带上 endpoint 与 `strerror`，`App` 干净退出 |
| 运行中不可恢复的系统调用失败 | 对**已注册 fd** 的 `epoll_ctl`（MOD/DEL）失败、`eventfd` 写失败 | `LOG_FATAL` |
| 资源耗尽 | 新连接 `epoll_ctl(ADD)` 遇 `ENOSPC`/`ENOMEM` | 记日志并计数，只关闭这一条新连接，进程继续（同样不产生回调） |
| 过载拒绝 | 所有 loop 的 `ConnectionTable` 都满；`AcceptFilter` 拒绝；`accept` 遇 `EMFILE`/`ENFILE` | accept 后立即关闭，**不产生 `OnConnected`/`OnClosed`**，按原因计数（filter / 满载 / fd 耗尽），日志限频 |
| 编程错误 | 错线程使用 `Connection&`、在 `Running` 状态重复 `Start`、`Connection` 状态非法 | `LOG_FATAL`（`EventLoop::AssertInLoopThread()`） |
| 运行期可恢复错误 | `accept` / `read` / `write` / `connect` 失败、对端 RST | 记日志；关闭该连接，经 `OnClosed(conn, CloseReason, sys_errno)` 告知上层；`NetClient` 按 `ReconnectPolicy` 重连 |
| 内存耗尽 | `bad_alloc` | 不处理，进程终止 |

细则：

- **返回约定**：`int`，0 成功，非 0 为 `errno` 值，不另造错误类型；net 库特有的失败也映射到现有 errno（路径过长 → `ENAMETOOLONG`，端点非法 → `EINVAL`）。返回它的函数标 `[[nodiscard]]`。
- **全有或全无**：`EventLoopGroup::Start()` 中途失败（如第 3 个线程创建失败）要先 join 已起的线程、关闭已开的 fd 再返回；`EventLoop` 构造函数不做系统调用，fd 在 `Init()` 里创建并返回 errno；`Shutdown` 对没有成功 `Start` 的对象是安全的空操作。
- `NetModule::Start()` 遵守 `Module::Start` 的约定（`framework/app/module.h`：返回错误的模块必须自清理）：任一步失败，先停掉已启动的 `NetServer`/`NetClient` 并 `Shutdown` group，再返回错误。
- **线程用 pthread 封装的 `Thread`**，`Thread::Start()` 返回 errno；不用 `std::thread` / `std::jthread`，因为它们失败时抛 `std::system_error`。
- **`Acceptor` 预留一个空闲 fd**（打开 `/dev/null`）：`accept` 遇到 `EMFILE` 时先关掉它，接受并立即关闭这条连接，再重新打开，避免水平触发下 accept 死循环。
- **`ConnectionHandler` 的回调声明 `noexcept`**：派生类必须同样声明，回调里抛异常即 `std::terminate`，标准库默认的 terminate 处理器会打印异常类型与 `what()`，库里不需要 `catch`。`MainLoopHandler` 跑在 App 主循环上，沿用 App 的惯例。
- **`Endpoint` 解析**失败返回空 `optional`；`NetModule` 在边界处转成框架的 `Result<>`（带上原字符串）。
- **机械检查**：`ctest` 里加一个用例，对 `base/net`、`framework/net` 下的源码 grep `throw` / `try` / `catch`，出现即失败。

## 5. `framework/net`：回投主循环

```
IO 线程 N ──ConnectionHandler──▶ MainLoopExecutor（IO 侧）：事件入 SpscQueue ──▶ 主循环 Drain 后回调业务
```

- `MainLoopExecutor` 实现一个 `ConnectionHandler`，在 IO 线程里把事件塞进该 IO 线程专属的 `SpscQueue`（`OnMessage` 的 payload 视图在此处拷贝成 `SharedBuffer`），主循环 `Drain` 后调用业务的 `MainLoopHandler`；业务回调拿到的是 `ConnectionHandle`。
- 事件队列每个 IO 线程一条。`Connected → Message* → Closed` **走同一条**，不分两道（分道会让 `Closed` 超车）。`Enqueue` 无界、不阻塞。
- **入口背压 = `PauseRead`，不是阻塞线程**：IO 线程服务成千上万连接，阻塞它等于全体停摆。
  - 每连接在途上限（条数+字节，原子计数，主循环消费时递减）：超限摘掉该连接的 `EPOLLIN`；消费到低水位时 `ResumeRead`；高低水位之间留滞后区间，避免来回 `epoll_ctl`。
  - **全局入站字节预算，强制生效**（计数与策略都在 `MainLoopExecutor`）：超出则对所有连接 `PauseRead`。每连接默认值要小（如 64KB），否则 10 万连接 × 256KB ≈ 25GB。
- 事件总量因此被"连接数 × 每连接上限"与全局预算双重约束。
- `NetModule : Module, IWaker`：持有一个 `EventLoopGroup`、若干 `NetServer`/`NetClient` 与 `MainLoopExecutor`（装配，不含 IO 逻辑）。`Wake()` = `Drain(budget)`，返回 true 表示仍有积压；IO 线程入队后调 `App::Notify()`。
- 配置走 `config/schema` 新增 `net.proto`（io_threads、max_connections_per_loop、每连接在途上限、全局入站预算、idle_timeout、keepalive 等的生产默认值），写法照 `framework/kernel/log_module.cpp`。

```cpp
// ---- base/net：回调在 IO 线程 ----

class EventLoopGroup {
  public:
    explicit EventLoopGroup(EventLoopGroupOptions); // io_threads、max_connections_per_loop…
    [[nodiscard]] int Start();                      // 0 成功，否则 errno（ENOSPC：注册表已满；EINVAL：选项越界）；失败已回滚
    void Shutdown(std::chrono::milliseconds deadline);
    NetStats   GetStats() const;

  private:
    friend class NetServer;
    friend class NetClient;
    EventLoop& PickLoop();                          // EventLoop 是内部类型，公开头只前置声明
};

enum class SendResult { Ok, Closed };

class ConnectionHandle {                            // 8 字节、可平凡复制：[group:4|loop:8|slot:20|generation:32]
  public:
    uint64_t raw() const;                           // 日志/哈希用
    [[nodiscard]] SendResult Send(SharedBuffer payload) const;  // 线程安全；帧头由连接的 codec 生成
    void       Close() const;
    void       CloseGracefully(std::chrono::milliseconds timeout) const;
    void       PauseRead() const;
    void       ResumeRead() const;
};
// group 销毁后其句柄作废；解析不到时 Send 返回 Closed。使用方保证销毁 group 前丢弃句柄、且无线程仍在 Send。

class NetServer {                                   // 一个对象一个 endpoint
  public:
    NetServer(EventLoopGroup&, const Endpoint&, ServerOptions,   // 水位、idle_timeout、max_frame、AcceptFilter…
              ConnectionHandler&, FrameCodecFactory&);           // 必填
    [[nodiscard]] int Start();                      // 0 成功，否则 errno（EADDRINUSE 等）；失败已回滚
    void Stop();                                    // 只停 accept
};

class NetClient {                                   // 固定在一个 loop 上；状态 Idle ⇄ Running
  public:
    NetClient(EventLoopGroup&, const Endpoint&,                  // 只收 IP 字面量
              ClientOptions, ReconnectPolicy,                    // ClientOptions 含 on_connect_failed / connect_timeout
              ConnectionHandler&, FrameCodecFactory&);
    [[nodiscard]] int Start();                      // 任意线程，Post 到所属 loop；Idle 下合法，Running 下重复是编程错误
    void       Stop();                              // 任意线程；停止重连并关闭当前连接，回到 Idle；不等待
    [[nodiscard]] SendResult Send(SharedBuffer payload);  // 未连通 → Closed，不暗中缓冲
};

// ---- framework/net：业务用，回调在 App 主循环 ----

struct MainLoopHandler {                            // 业务实现这个
    virtual void OnConnected(ConnectionHandle, const PeerInfo&) {}
    virtual void OnMessage(ConnectionHandle, SharedBuffer msg) = 0;              // 唯一必须实现的回调
    virtual void OnClosed(ConnectionHandle, CloseReason, int sys_errno) {}
};

class MainLoopExecutor {
  public:
    explicit MainLoopExecutor(App&);                // 构造期必填；内部持有各 IO 线程的 SpscQueue，并调 Notify
    ConnectionHandler& Wrap(MainLoopHandler&);      // 交给 NetServer / NetClient 构造
    bool Drain(size_t limit);                       // ran<limit ⇒ 已空
};
```

## 7. 不变量

1. `ConnectionHandle` 在其 group 存活期间、同槽 2^32 次复用内不会重复；group 销毁后其句柄作废（解析不到时返回 `Closed`；同编号的新 group 启动后不再保证，使用方须在销毁 group 前丢弃句柄）。过期句柄的任何操作都有明确返回，不静默。
2. 每条已回调过 `OnConnected` 的连接恰有一个 `OnClosed`，且在其最后一个 `OnMessage` 之后；同一连接事件全序。accept 后即被拒绝的连接不产生任何回调。
3. 事件投递不阻塞不丢；消息入口满则 `PauseRead`，不丢消息、不阻塞 IO 线程。内存上界：`framework` 层的入站事件有强制上限（每连接在途上限 + 全局入站预算）；`base` 层靠 `HighWaterMark`、`max_frame` 与 `max_connections_per_loop` 约束，最坏上界是它们与连接数的乘积，库内不设全局上限。
4. `Send` 不静默丢：`Ok`（已接收）或 `Closed`（已关闭/正在关闭，原因见 `OnClosed`）。
5. 断线即 `OnClosed`；连不上与不可重试错误都经 `ClientOptions::on_connect_failed` 通知，不静默；`NetClient` 未连通时不暗中缓冲。
6. 解码错误即关闭，不重新同步。
7. 谁创建 IO 线程，谁在 `Shutdown`/析构里 join；`ConnectionHandler` 回调不得阻塞。
8. `FrameCodec` 每连接一个实例；`Connection&` 只在其 IO 线程使用。
9. `base/net` 不依赖主循环或 `framework`。
10. net 库内不抛、不 catch；建立期失败经 `Start()` 返回 errno 并回滚，编程错误 `LOG_FATAL`；`ConnectionHandler` 回调 `noexcept`。
11. `Connection` 在自己的回调里被关闭时延后销毁；`OnClosed` 之后不再有该连接的任何回调。
12. `Send` 与 `OnMessage` 对称，都只处理 payload；帧头由连接生成，payload 可被多条连接共享。
13. `OnMessage` 的 payload 视图只在回调内有效；跨线程保留必须拷贝（`MainLoopExecutor` 入队时）。

## 8. 不做与暂不做

**明确不做（属于应用层，库只留接口）**：群发/房间/订阅、鉴权与会话、限流与黑名单策略（经 `AcceptFilter`）、心跳内容与校验、客户端协议格式（魔数、序号、加密、压缩，经 `FrameCodec`）、慢消费者的细粒度策略。

**明确不做（其他）**：io_uring、TLS、UDP/KCP、fd 传递（SCM_RIGHTS）、WebSocket、DNS 解析、PROXY protocol、RPC 相关性/deadline/取消（上层）、Windows/IOCP、自动重试消息（重连只管连接）、有限次数重连（永远重连，由调用方 `Stop()`）、`Result`/`expected`/`error_code` 作为 net 库的返回类型。

**本阶段暂不做**：sidecar 转发面、写缓冲水位回调（`OnWriteBufferHigh/Low`）、`DropNewest` 溢出策略、IO 线程睡前自旋、帧级读超时（应用层按完整消息时间判定）、`NetServer`/`NetClient` 的停止完成通知（`on_stopped`，用于运行期动态增删对端）。

## 9. 性能目标与基线

以 muduo 为基线，同一台机器、同一组用例：

1. 裸 epoll echo（性能上限）
2. muduo echo
3. 本库 `ConnectionHandler` 直接回调
4. 本库 `MainLoopExecutor` 回投主循环

目标：3 不低于 2，**验收以"不低于 muduo"为准**（2026-10-29 定）；与 1（裸 epoll）的差距只作参考指标记录，不设门槛（最初定过 X = 8%，见 §9.1）；4 的额外延迟与吞吐损耗量化到数字；另测 UDS ping-pong p50/p99、10 万空闲连接的内存、64B/1KB 消息在 1/64/10k 连接下的吞吐。

### 9.1 P2a 实测基线（2026-10-29）

1. **「3 不低于 2」成立**（echo 方案与 muduo 相同）：TCP 四个多连接配置里 breeze ÷ muduo 的逐轮中位数为 99.9 / 103.5 / 100.7 / 103.9%，**没有低于 muduo 的配置**，10k 连接下两组都是 5/5 轮胜。
   历史：视图版 `Send` 之前，1KB×64 曾稳定低 2–4%（96.3 / 96.5 / 98.1%），其余配置持平或略快。
   **该落后是 echo 回调里"先拷成 `SharedBuffer` 再发"造成的，不在框架路径上**：`breeze-fixed`（回复预先建好的固定 payload）当时就与 muduo 持平，改用视图版 `Send` 后落后消失（100.7%）。
   它只出现在 1024B、1000B 不出现，这一点的机制没有查清：曾怀疑 1040 字节的块越过 glibc tcache 的 1032 字节上限，
   但干预实验（`GLIBC_TUNABLES=glibc.malloc.tcache_max=4096`）没有改善（反而慢 3%），该假设已被推翻。
2. **10k 连接下 breeze 比 raw 低 4–5%，muduo 低 9–10%**：每连接对象带来的缓存占用是两者共有的代价，breeze 的"线程本地读缓冲优先"（§4.7）让它小一些。
3. **echo 里的分配与拷贝是可测量的代价**（此前"无可测量代价"的结论不对）：UDS 64 连接上，视图版比 `breeze-copy` 快约 5%（逐轮配对 104–108%、101–114%）；
   TCP 上 0–4%；UDS 10k 无明显差异（缓存占用占主导，且 raw 自身波动大）。视图版 `Send` 绕开了这笔代价（echo、小应答）；
   必须分配 `SharedBuffer` 的路径（序列化出新数据）仍要付，malloc 与 memcpy 各占多少没有分开测过。
4. **UDS 起初有 12–16% 的真实差距**，经 §9.2 的优化与视图版 `Send` 后为 91–93%，见下。

**验收标准：不低于 muduo（已定）**——结论 1 已满足。最初曾定"与裸 epoll 的差距 X = 8%"（吞吐 ≥ 92%、p99 ≤ 1.08 倍），后改为只要不低于 muduo 即可，裸 epoll 的差距降为参考。
下表仍按 X = 8% 的口径列出供参考（逐轮配对，5 轮交错，相对同一批轮次里的 raw）；UDS 没有 muduo 可比，只能与 raw 比：

| 配置 | breeze 相对 raw | 是否 ≥92%（参考） |
|---|---|---|
| TCP 64B×64 / 1KB×64 / 64B×10k / 1KB×10k | 97% / 99% / 96% / 95% | 是 |
| UDS 64B×64 / 1KB×64 / 64B×10k / 1KB×10k | 91% / 93% / 92% / 91% | 两项达到，两项差 1 个百分点，小于测量噪声（raw 波动 ±4–16%） |

p99 在 64 连接下与 raw 的差约 +4–5%，在 8% 内；但 p99 本身的波动就有 5–10%，8% 的 p99 门槛在这个测量精度下**无法判定**，吞吐是可靠指标，p99 只作参考。
UDS 余下约 7–9% 的差距：与 raw 同形状的系统调用加每连接状态约 3%（设计固有：帧头与 payload 分两个 iovec，以便多连接共享同一块 payload）、

再降需要把层次融合、去掉虚调用，会明显牺牲清晰度，而收益小于测量噪声（±4–8%），已无法验证，所以停在这里。

**测量环境的两个坑**（不是库的问题，但会让后来人踩）：本机 `ip_local_port_range` 只有 40525–44620（约 4000 个端口），
同一源地址连同一 `(目的IP, 目的端口)` 到不了 10k，bench 让 4 个压测线程分别连 `127.0.0.1…4` 才凑够；

### 9.2 UDS 路径的归因与优化（P2a 收尾）

方法：**先测量再改**。每一步都有数据，被数据排除的假设都没有动代码。

**被排除的假设**：
- 每轮 `RunOnce` 的固定开销（睡前 seq_cst 写、fence、空队列取、定时器与回收检查）：原生测得每轮处理 ~60 条消息（64 连接）、~1022 条（10k 连接，已到 `epoll_wait` 单次上限），
  `RunOnce` 自身只有 ~11 条指令/消息。
- 系统调用耗时：用 `rdtsc` 分阶段计时，`readv` / `sendmsg` 的周期数在各实现间相同（`sendmsg` 占约 70%，因为要唤醒对端）；差距全在"其余"一栏（用户态）。
- `EPOLLRDHUP`、epoll 存指针而非 fd：二分实验（给裸 epoll 一次加一个 breeze 的特征）里都没有可测量的影响。

**确认的原因与改动**：

| 改动 | 证据 | 效果 |
|---|---|---|
| `SharedBuffer` 分配改用普通 `operator new`（原先显式要求 16 字节对齐，走了 `posix_memalign`；glibc 默认就是 16 字节对齐） | callgrind：对齐分配链每条消息约 100 条指令 | 760 → 679 条指令/消息 |
| 读路径改为"线程本地缓冲优先，每连接只存半个帧"；`FrameCodec::Decode` 改吃 `span` | 二分实验：冷的每连接读缓冲约 2.5%；单 iovec 的 `read` 比 `readv` 便宜；每连接不再常驻 1KB | 见下 |
| `Send` 直写快路径：整帧写完时不构造 / 移动 `Pending` | callgrind | 679 → 612 条指令/消息（含上一项） |
| 线程检查用 `thread_local` 指针比较（muduo 同款），不再每次调 `pthread_self` | callgrind：每次 `Send` 省约 10 条 | |

在这个环境里（WSL2，系统调用返回后用户态代码是冷的），实测 IPC 只有 ~0.3，约 3.6 周期/条指令，所以降指令数确实有效，但**指令数与耗时的对应关系很弱**：
1KB 时分配加拷贝多 668 条指令，吞吐影响却只有 0–5%（straight-line 的 `memcpy` / `malloc` 代码 IPC 高），而框架里带分支的虚调用链每条指令更贵。
因此指令数只用来指方向，**取舍一律以配对吞吐为准**。

**教训**：压测客户端会逐字节核对每条连接的第一个回包——它抓到过我新写的诊断变体里的 bug（两个 iovec 重叠）。没有这个核对，一个回显错了的实现会被拿去比性能。
变异验证也抓到过一个测试缺口：拼接路径若漏了消耗已解的帧，旧帧会在下一次读时被重复分发，而原有用例在"拼完一个帧"之后就结束了。已补上"之后再发一帧，回包必须恰好是它"。

**诊断变体**（都在 `bench/net_bench.cpp`，`--impl` 取值）：`raw-iov`（裸 epoll，但系统调用形状与 breeze 相同）、`raw-iov+rdhup|cold|ptr|all`（再逐个加上 breeze 的特征）、
`breeze-fixed`（回复预先建好的固定 payload，不分配不拷贝，用来把框架开销与 echo 里的拷贝分开）。

## 10. 落地路线

### 10.1 阶段

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0** | `base/queue` + vcpkg 依赖 + 测试（含 TSAN） | 契约测试通过；两个 port 经 `vcpkg.json` 能解析并链接；clang 23 + cmake + ninja + vcpkg preset 可构建 |
| **P1** | `Endpoint`+解析、`Socket` 封装、`Thread`、`Buffer`、`SharedBuffer`、`LengthPrefixCodec`（`Decode` + `EncodeHeader`）/`FrameCodecFactory`，纯单测 | `Endpoint` 统一解析 TCP/UDS；codec 逐字节喂入结果与整块喂入一致；`EncodeHeader` 与 `Decode` 往返一致 |
| **P2a** | 单 loop 垂直切片：`EventLoop`（epoll、`Post`、唤醒协议、注入时钟、`RunOnce`）+ `Connection`（状态机、IO 线程直写、事件分发顺序、延后销毁）+ `Acceptor`（含空闲 fd）+ `Thread`；UDS/TCP echo；`net_bench` 对 muduo 基线 | 同一份代码跑通 TCP 与 UDS echo；`ConnectionHandler` 路径不低于 muduo 基线；回调内自关闭不崩；**复盘**：哪些概念可合并或删除，再定 P2b |
| **P2b** | `ConnectionTable`/`ConnectionHandle`/`GroupRegistry`、`EventLoopGroup`（`Start/Shutdown`、`PickLoop`）、`NetServer`/`NetClient`/`Connector`、`CloseGracefully`、idle 扫描、`PauseRead/ResumeRead` | 慢消费者与断线各有唯一、有序的终态；`Start()` 失败（端口/UDS 路径被占、fd 耗尽）返回对应 errno 且无 fd/线程泄漏；sidecar 重启后 UDS 重连成功 |
| **P3** | `framework/net`：`MainLoopExecutor`（事件 `SpscQueue`、入口背压、全局入站预算）+ `MainLoopHandler` + `NetModule` 接 `IWaker` + `net.proto`；`net_bench` 补第 4 组基线 | 量化出 `MainLoopExecutor` 的额外代价；§10.2 各项定案 |

### 10.2 待基准决定项

正文只写默认做法；下表各项在对应阶段的基准里定案，接口不因此改变。

| 项 | 默认 | 何时切换 |
|---|---|---|
| 读触发方式 | 水平触发，每次就绪读一次 | 边缘触发在 P3 基准里吞吐/延迟明显更优，且不出现同 loop 饿死 |
| 跨线程直写（调用线程在出队列为空且抢到写权限时直接 `write()`，不走任务队列与唤醒；与"IO 线程直写"是两件事） | 关闭 | UDS ping-pong p99 明显受益；并发正确性需 TSAN 全覆盖 |
| 消息缓冲 | IO 线程路径给视图（零拷贝）；`MainLoopExecutor` 入队时拷贝成 `SharedBuffer` | 基准显示该拷贝成为瓶颈，新增块链类型（与 `SharedBuffer` 并存，为 `Send` 增加重载），不改 `SharedBuffer` 的名字与签名 |
| `SharedBuffer` 分配 | 通用分配器（视图版 `Send` 已让 echo 这类回包免分配；必须分配 `SharedBuffer` 的路径在 UDS 小消息上实测约 5% 的分配拷贝成本，malloc 与 memcpy 各占多少未分开测，见 §9.1） | 出现可证明的分配热点，再造池（需跨线程归还通道） |
| 队列实现 | moodycamel | 互斥+整批 swap 仅在 `net_bench` 作对照，不进库；接口不变 |
| `PickLoop` | 选连接数最少的 loop（muduo 为 round-robin） | 实现成本或竞争过高时退回轮询 |
| 发送侧总量上限 `max_pending_bytes_per_loop`（按 loop 计数，超限关 pending 最大的连接） | 不做（等价于不限） | 出现真实 OOM 风险或应用层需要时再加，默认 0 = 不限 |
| 主线程内联跑 `EventLoop` | 不做 | 两次线程跳转的延迟不可接受时评估（`RunOnce` 已保留，届时公开 `EventLoop`） |

### 10.3 未决项

- **`framework/net` 的停机排空**：`framework/app` 只管启动、不管停机（`app.h`：没有 Stop/Shutdown），`Run` 在 stop_token 触发后立即返回，收尾在 `~App`。
  若 `EventLoopGroup::Shutdown` 放在 `~App` 里调用，主循环已退出，各 IO 线程 `SpscQueue` 里的 `OnClosed` 无人 Drain，业务侧违反不变量 2。
  P3 前二选一：由 `main` 在 `Run` 返回后显式 `Shutdown` 并 Drain 到空；或给 App 加模块停机阶段。不影响 P0 到 P2b。

## 11. 验证

测试沿用仓库做法：自带 `main` + `add_test`，不引 gtest。

- **队列**：单线程语义、MPSC 每生产者内部顺序、`TryDequeueBulk` 契约、move-only 类型、压力测试；SPSC、MPSC 各用 TSAN 跑一遍（带 `tsan.supp`，见 §3）。
- **单测（`ctest`）**：`Buffer`/`LengthPrefixCodec`（分片、超长、半包）；`Endpoint` 解析（含非法字符串返回空）；`ConnectionTable` generation 校验与槽对齐；`GroupRegistry`（group 销毁后 `Send` 返回 `Closed`、`loop`/`slot` 越界返回 `Closed`、注册表满返回 `ENOSPC`）；`EventLoop` 跨线程 `Post` 与定时器（假时钟）；唤醒协议不丢唤醒且 `eventfd` 读空后不空转（多生产者长压力，带超时断言）。
- **连接行为**：TCP 与 UDS 同用例 echo；过载拒绝（连接表满、`AcceptFilter` 拒绝、`EMFILE`）不产生回调且按原因计数；慢读方触发水位 → `Send` 返回 `Closed` → `SlowConsumer` 关闭；对端 RST/半关闭的 `CloseReason`；`EPOLLHUP`/`EPOLLERR` 的关闭原因与 `sys_errno`；回调内 `Close` 自己不崩且 `OnClosed` 只一次；对端永不关闭时 `CloseGracefully` 超时强关且不丢最后一条；同一块 `SharedBuffer` 发送到多条连接不拷贝数据且各连接帧头独立；`OnMessage` 视图在回调返回后不被依赖（ASAN）；`PauseRead/ResumeRead` 不丢消息不乱序；10k 连接冒烟。
- **空闲**：被 `PauseRead` 暂停的连接不被 idle 扫描误杀，`ResumeRead` 后刷新 `last_active_time`。
- **重连**：退避序列；断线 fail-fast；TCP self-connect 被识别并重试；UDS `ENOENT`/`ECONNREFUSED` 按退避重试；黑名单以外的错误（如 `ETIMEDOUT`）会重试；`connect_timeout` 对黑洞地址生效；`on_connect_failed` 按预期触发，不可重试错误时 `will_retry=false`、状态回到 `Idle` 且回调内 `Start()` 合法；`Running` 下重复 `Start()` 报编程错误；`Stop()` 关闭当前连接且其 `OnClosed` 只触发一次、之后无回调，先 `Stop` 再 `Start` 不会并存两条连接；句柄 raw 为 0 恒为无效。
- **资源与退出**：`bind` 冲突返回 `EADDRINUSE`、UDS 路径超长返回 `ENAMETOOLONG`、选项越界（`io_threads`、`max_connections_per_loop`）返回 `EINVAL`；`setrlimit(RLIMIT_NOFILE)` 制造 `EMFILE`、`RLIMIT_NPROC` 制造线程创建失败，验证 `EventLoopGroup::Start()` 中途失败后已起线程全部 join、fd 无泄漏；`accept` 遇 `EMFILE` 不死循环；`epoll_ctl(ADD)` 失败只关该连接；`Shutdown(deadline)` 在有积压时收敛；`NetModule::Start()` 失败后 `App::Run` 返回错误、进程以正常退出码退出。
- **集成**：`NetModule` 挂进 `App`，`Wake()` 预算耗尽返回 true 能续跑；析构时 IO 线程全部 join（TSAN/ASAN 各跑一遍）。
- **约定检查**：对 `base/net`、`framework/net` grep `throw/try/catch`。
- **基准**：`net_bench` 产出 §9 的对比表，并给出 §10.2 各项的结论。
