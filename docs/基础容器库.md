# 基础容器库：`base/container`

`FlatHashMap` / `FlatHashSet`（Swiss table 开放寻址）与 `LinkedHashMap` / `LinkedHashSet`（保持插入顺序，可当 LRU）。只有头文件，只依赖标准库，不限平台
（x86 上用 SSE2，没有 SSE2 的平台自动退到可移植的 SWAR；只支持小端）。CMake 里是 `breeze_container`（INTERFACE）。

本文记录**为什么是这个样子**：前身来自 `cpp-game-server-main`（`flat_hash_map.h` / `flat_hash_set.h` / `linked_hash_map.h` / `linked_hash_set.h` / `detail/swiss_table.h`），
合并时做了哪些取舍、修了哪些 bug。API 的细节与约束写在头文件注释里，本文不重复。

**状态**：debug / release / asan+ubsan 下全部测试通过；对关键判断逐个改坏做过变异验证（§6）；SSE2 与强制 SWAR 两条路径各跑一份同样的测试。
容器本身不是线程安全的（同 `std::unordered_map`），所以没有并发要验证的东西，tsan 不适用。

## 1. 用哪个

| | `std::unordered_map` | `FlatHashMap` | `LinkedHashMap` |
|---|---|---|---|
| 查找 / 插入 / 删除 | 节点式，每个元素一次堆分配 | 一块连续内存，一般只碰一两个缓存行 | 紧凑数组 + 下标链 |
| 遍历顺序 | 不定 | 不定，插入 / 扩容后会变 | **插入顺序**（也可倒序） |
| 迭代器 / 引用失效 | rehash 时迭代器失效，**引用与指针不失效** | **插入可能让全部失效**，删除只影响被删的 | 插入可能全部失效；删除影响被删的与"原来最后插入的" |
| 内存 / 元素（8 字节键值） | 约 40 字节 | 约 22–36 字节 | 约 50–63 字节 |
| 特点 | 地址稳定 | 最快；`reserve(n)` 后放 n 个以内不搬动 | LRU：`move_to_back` + `pop_front`；任意位置 O(1) 删除 |

- **要地址稳定**（把 `&it->second` 存起来过一会儿再用）：存 `unique_ptr<T>`，或者继续用 `std::unordered_map`。
- **默认选 `FlatHashMap`**。需要稳定的遍历顺序、先进先出的去重、LRU 缓存时选 `LinkedHashMap`。
- `FlatHashSet` / `LinkedHashSet` 同理。

两者共同的约束（`static_assert` 或头文件注释里都写了）：键与值的**移动构造函数必须 `noexcept`**（扩容 / 删除时要搬元素，搬到一半抛出没法回滚）；没有自定义分配器；
没有 `extract` / `merge` / bucket 接口；`at()` 找不到键直接 `abort`（库不抛异常，要"找不到就算了"用 `find`）。

**没有哈希洪泛防护**：键来自不可信输入（玩家名、请求参数）又被故意构造碰撞时，用带随机种子的哈希。哈希器是容器里存着的对象，可以带状态（旧实现每次调用都默认构造一个，只能是无状态的）。

**为什么没有直接用 abseil**：vcpkg 里有 `abseil`，如果依赖策略允许，生产里直接用 `absl::flat_hash_map` 更稳（按表的随机种子、更完整的 API、经过更多人的验证）。
这套是为了不加第三方依赖、与 `base` 里其它库统一的约定（不抛异常、`noexcept` 要求），算法与它是同一个（Swiss table）。**没有和 abseil 比过性能**（本机没装）。

## 2. 在原代码里发现并处理的问题

三代前身：`cpp-wind-server`（2026-03-28，v0.1，只有 SWAR，`FlatHashMap` / `LinkedHashMap` / `LinkedHashSet`，没有 `FlatHashSet`）→ `cpp-game-server-cpp`（2026-04-05 的未完成快照，`flat_hash_set.h` 是空文件）→ `cpp-game-server-main`（v0.2，SSE2 + SWAR，四个容器齐全）。
**以 game-server-main 为底**；前两代是同一结构的早期版本，只扫了接口与关键函数，没有逐行读。

### `FlatHashMap` / `FlatHashSet`

- **先扩容再查重**：`try_emplace` 先检查装载、必要时 `rehash`，再去找键。键已经存在时也会在装载边界上白白搬一遍所有元素、让全部迭代器失效。现在先查，查不到才决定要不要扩容（`flat_hash_test` `TestExistingKeyInsertNeverRehashes`：表在装载上限时，对已存在的键做 `try_emplace` / `insert` / `emplace` / `insert_or_assign` / `operator[]`，容量不变、元素地址不变）。
- **哈希器每次调用都默认构造**（`hasher{}(key)`）：只能是无状态的，带种子的哈希器会得到错误的结果。现在存在容器里，拷贝 / 移动 / 交换 / 赋值都带着走，扩容也用同一个（`TestStatefulHasher`）。
- **存储用 `new uint8_t[]`**：对齐只有默认的 16。槽类型对齐更大（`alignas(64)` 的值）时元素地址会错位。现在用带 `align_val_t` 的 `operator new`（`TestOverAlignedSlots`）。
- **删除永远留墓碑**：删/插交替的负载（连接表、会话表）墓碑越攒越多，装载余量被耗光后就要整表重建。现在照 Abseil 的做法：被删槽的前后各有一组大小的窗口里有空位、且连续的满槽不足一组，就说明没有任何探测序列越过过它，直接置空并归还装载余量（`TestEraseInSparseTableLeavesNoTombstones`：25%–50% 装载下几乎不留墓碑；`TestTombstoneChurn`：150 万次"删一个插一个"，容量不超过稳态的 2 倍）。
- **装载余量用完后的处理**：旧实现 `size >= max_load` 才翻倍，否则原容量重建，重建后余量可能只剩一两个，下一次又重建；按代码推演，稳态元素数接近上限的"删一个插一个"负载下每次插入可能都是整表重建（O(n)）。现在按 Abseil 的规则：实际元素不到容量的 25/32 才原容量清墓碑，否则翻倍；放进墓碑本身不消耗余量（`TestReinsertAfterEraseAtFullLoadNeverGrows`）。
- **`insert(value_type&&)` 用 `const_cast` 移走常量键**：如果被插入的对象本来就是 `const` 的，是未定义行为。现在键拷贝、值移动（`try_emplace(v.first, std::move(v.second))`，`TestInsertRvaluePairMovesTheValue`）。
- **`at()` 抛异常**：库内不抛，改成 abort（`TestAtMissingAborts`）。
- **构造抛异常会让表损坏**：先构造元素、再改控制字节与计数；拷贝整个表中途抛，用守卫销毁已拷好的并释放存储（`TestConstructionThrowing`，asan 下查泄漏）。
- **接口补全**：异构查找覆盖 `find` / `contains` / `count` / `erase` / `at`（旧版只有 `find` / `contains` / `count`）；`erase(first, last)`、`erase_if`、`operator==`、`shrink_to_fit`、`reserve` 保证"之后放 n 个以内不扩容"（`TestReserveGuaranteesNoRehash`）；集合的元素对外永远是 const（改了键就破坏哈希位置；共用核心之后要靠策略保证，`static_assert` 守着）。
- **`FlatHashSet` 与 `FlatHashMap` 是两份结构相同的实现**（各约 500–650 行，改一处要记得改另一处）：现在共用 `detail/raw_hash_table.h`，差别只在 `detail/slot_policy.h` 里的槽策略，两者行为一致；`LinkedHashMap` / `LinkedHashSet` 同理共用 `detail/linked_hash_table.h`。
- 哈希搅拌：murmur 终结器换成折叠乘法（一条乘法指令）；`std::hash<int>` 是恒等函数，规律性的键（2 的幂的倍数、连续 id）靠它才不扎堆（`TestDifferentialPatternedKeys`）。
- 遍历：紧挨着的下一个槽是满的就不读整组（装载高时最常见），迭代速度约快一倍。

### `LinkedHashMap` / `LinkedHashSet`

- **被移走的表是坏的**：默认的移动只搬走了数组与桶，链头 / 链尾 `head_` / `tail_` 仍是旧值——被移走的表 `begin() != end()`，遍历读到空数组，再插入就越界。现在被移走的表回到完整的"空表"状态（`linked_hash_test` `TestMovedFromIsFullyEmpty`）。
- **`reinterpret_cast<pair<const K, V>&>(pair<K, V>)`**：严格别名上是未定义的。现在与 `FlatHashMap` 一样用联合做类型双关（GCC / Clang 明确支持），`static_assert` 两种 pair 的大小与对齐一致。
- **哈希 `& (桶数 - 1)` 前没有搅拌**：恒等哈希的规律性键扎堆；现在搅拌后再取桶，并把完整哈希值存在条目里（扩容桶数组不重算、比较时先比哈希值）。
- **先扩容再查重**：同 `FlatHashMap`；现在先查。
- 链接下标 `size_t` → `uint32_t`（每个元素的链接开销从 40 字节降到 24 字节；最多约 42 亿个元素，超过直接 abort）。
- 迭代器从 forward 改成 **bidirectional**（有 `rbegin` / `rend`、`--end()`）。
- 补了 LRU 要用的：`front` / `back` / `pop_front` / `pop_back` / `move_to_back` / `move_to_front`（O(1)，不让迭代器与引用失效）；`erase(first, last)`。
- 与旧版相同、已经正确的：swap-and-pop 删除 + 双向的冲突链 / 顺序链，`erase` 是 O(1)；`erase(iterator)` 返回的"下一个"在被搬动的元素恰好是它的后继时要修正（旧版有，`TestEraseReturnsCorrectNext` 专门覆盖，并新增了区间删除时区间末端被搬动的同类情形，`TestEraseRangeWhenEndIsMoved`）。

## 3. `FlatHashMap` 的设计（Swiss table）

- **布局**：一块内存 = 控制字节（`capacity + 一组` 个）+ 槽数组。每个槽一个控制字节：满（存哈希低 7 位 H2，非负）/ 空（-128）/ 墓碑（-2）。控制字节数组末尾复制了开头的"一组 - 1"个，这样从任意位置读一整组都不会越界，也不用处理回绕。
- **查找**：哈希高位（H1）定位到一组（16 个，SWAR 下 8 个），用一条 SIMD 指令同时比较一组的 H2，只对命中的槽调 `key_equal`；组内有"空"就说明这条探测序列上不会再有它了。探测按三角数步进（每次比上次多走一组），访问到所有组。
- **容量是 2 的幂**，最小一组；最大装载 7/8；空槽至少 `capacity/8` 个，所以任何探测序列都会终止（`InvariantsHold` 里检查"空槽数 = capacity - max_load + growth_left"这个恒等式）。
- **删除的"从未满过"判断**：见 §2。`LeadingZeros` / `TrailingZeros` 在 SWAR 掩码里要按 8 位一槽换算（`BitMask` 的 `Shift` 参数）。
- **元素的搬动**：扩容 / 重建时新分配一块、把满槽逐个搬过去、释放旧的（所以重建之后元素地址一定变，测试靠这个判断"有没有发生重建"）。元素的移动构造必须 `noexcept`。
- **槽类型**：`map` 的槽是 `{const K, V}` 与 `{K, V}` 的联合：对外暴露带 const 键的 pair（键不能被改），搬动时把键当可移动的用。
- **诊断接口**：`InvariantsHold()`（控制字节镜像、满槽数、装载余量、每个元素可被查到，O(容量)）、`tombstones()`，给测试与排障用。

## 4. `LinkedHashMap` 的设计

- **结构**：元素存在一个紧凑数组里（`Entry` = 元素 + 哈希值 + 四个 32 位下标：冲突链的前后、顺序链的前后）；哈希桶是一个下标数组（装载因子 ≤ 0.75，2 的幂）。
- 插入追加到数组末尾，挂到冲突链头与顺序链尾；数组扩容只搬数组、下标不变，所以链不用重建（桶数组扩容才重建冲突链）。
- 删除：从两条链上摘下来，再把数组最后一个元素搬到空位（swap-and-pop）并修补它邻居的下标，数组始终紧凑。
- 遍历沿顺序链走；没有删除过时元素在数组里就是按顺序排的，遍历是顺序读。
- **失效规则**：插入可能让全部迭代器 / 引用失效（数组扩容）；删除一个元素让它自己、以及被搬到它位置上的那个"原来最后插入的元素"失效，其它不受影响。
- **顺序规则**：新键追加到末尾；对已有的键重复插入 / `insert_or_assign` / `operator[]` 不改变它的位置；要换位置用 `move_to_back` / `move_to_front`。相等比较不看顺序（同 `std::unordered_map`）。

怎么读：

- **随机键与字符串键**：`FlatHashMap` 在几乎所有项上都明显更快、更省内存（1M 个随机 `uint64`：插入 26 vs 179 ns、命中 9.9 vs 17.6、未命中 3.5 vs 29、遍历 3.8 vs 36、删除 22 vs 58、删一个插一个 87 vs 500）。未命中特别快：一次 SIMD 比较就能确定"这一组里没有"。
- **连续 id、按插入顺序访问**是 `std::unordered_map` 的最好情形：恒等哈希让桶号连续、节点按插入顺序分配，访问有极好的局部性，命中查找 1–2 ns，**比 `FlatHashMap` 还快**（我们搅了哈希，换来的是任意键分布下都不扎堆，代价是丢掉了这种局部性）。一旦访问顺序是随机的（真实的玩家 / 对象访问就是随机的），1M 个元素时两者命中查找就拉平（9.8 vs 10.4），删除仍是 `FlatHashMap` 快得多（22 vs 60）。
- **`LinkedHashMap`** 比 `FlatHashMap` 慢（多一次下标间接、条目更大）、占内存更多（50–63 字节 / 元素），但比 `std::unordered_map` 在多数项上仍然快（连续 id 按插入顺序访问的情形除外）。整数键时插入比 `FlatHashMap` 慢；字符串键且元素很多时反而更快（1M 个：85 vs 200 ns）——它是追加写，而 `FlatHashMap` 每次插入落在随机位置、扩容还要搬字符串。遍历快（沿紧凑数组的顺序链走）。
- 遍历：`FlatHashMap` 约 1.5–4 ns / 元素（稀疏时按组跳过空槽）；`std::unordered_map` 在表小、节点连续时是 1 ns，表大了（节点散落在堆里）会掉到 30–70 ns。
- 没有和 abseil 比（本机没装）。

## 6. 验证

- `flat_hash_test`（SSE2）、`flat_hash_swar_test`（同一份源码强制 SWAR，断言 `kGroupWidth == 8`）、`linked_hash_test`，debug / release / asan+ubsan 都过。
- **与标准库的随机对照**：`FlatHashMap` 对 `std::unordered_map`、`FlatHashSet` 对 `std::unordered_set`、`LinkedHashMap` 对"`std::list` + `unordered_map`"的经典实现，随机操作序列（插入的各种形式 / 删除 / 迭代器删除 / 区间删除 / `reserve` / `rehash` / `shrink_to_fit` / `clear` / 拷贝 / 移动 / 交换 / `move_to_back`……），键用 `int`、`std::string`（跨 SSO 边界）、恒等哈希的规律性键（`k * 1024`、`k << 40`）、**全部同值的哈希**、**只有低 7 位有区别的哈希**；每一步比较返回值，周期性全量比对并调 `InvariantsHold()`。
- 其它：带状态的哈希器、对齐、移动语义、对象生命周期计数（扩容只移动不拷贝、构造 / 析构配平）、异构查找（用"构造了几个临时键"的计数证明没有构造）、LRU 与独立实现对照 10 万次操作、30 万 / 20 万元素的大规模用例。
- **变异验证**（在 `/tmp` 里的隔离副本上逐个改坏关键判断，要求至少一个测试失败）：`FlatHashMap` 40 个、`LinkedHashMap` 28 个。没被杀死的都逐个确认过：
  - 行为等价、只影响效率：H2 取更少的位（只是假阳性更多）；SWAR 的 `LeadingZeros` 不换算槽宽（只是更保守地留墓碑，在 25%–50% 装载的测试里被杀死）；`was_never_full` 里 `empty_before &&` / `empty_after &&`（掩码为零时 `LeadingZeros` / `TrailingZeros` 本来就是一组的宽度，条件自然不成立）。
  - 一开始没被杀死、后来补了用例的真缺口：墓碑进出的装载余量、`reserve` 在余量足够时不该重新分配、`insert(value_type&&)` 应该移动值、"先构造再登记"的顺序（需要拷贝会抛的类型）、SWAR 的 `TrailingZeros`、删除优化在中等装载下的命中率。
  - 编译期杀死：用拷贝代替移动的变异在 `unique_ptr` 值上编译失败。
- **没验证的**：tsan（容器不是线程安全的，不适用）；aarch64 的 NEON（没写，走 SWAR；SWAR 路径在 x86 上用 `BREEZE_CONTAINER_FORCE_SWAR` 测过，但没有在真的 ARM 上跑过）；大端（`static_assert` 拒绝）；GCC（本机只有 clang）；与 abseil 的性能对比。
