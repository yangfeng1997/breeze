# 线程基础库：`base/thread`

`Thread`、`this_thread`（当前线程信息）、`WaitGroup`、`SpinLock`、`ThreadPool`。只支持 Linux（pthread 命名与亲和性、`gettid`），与网络库同一个构建开关。
`breeze_net` 以 PUBLIC 链接 `breeze_thread`（`EventLoopGroup` 用 `Thread`）；业务代码也直接用。

本文记录**为什么是这个样子**：这些组件有三代前身（见下），合并时做了哪些取舍、修了哪些 bug、哪些没搬。API 的细节与约束写在头文件注释里，本文不重复。

**状态**：debug / release / asan+ubsan 下全部测试通过，各用例循环跑过 25–30 遍无偶发失败；对关键判断逐个改坏做过变异验证（15 个变异全部被杀死）。
**tsan 没有在本机跑过**（环境原因，见 `网络库设计.md` §11.2），`ThreadPool` 的锁与唤醒逻辑、`Thread` 的 tid 握手上真机前不要当作已验证。

---

## 1. 来源与取舍

前身来自同一位作者的三个目录（`cpp-game-server-cpp` 与 `cpp-game-server-main` 的 `thread/` 完全相同，所以实际是三代）：
`cpp-game-server` 最新 → `cpp-wind-server` 较早 → `cpp-wind-server_back-cpp` 最早。三代里 Thread / WaitGroup（CountDownLatch）/ SpinLock / ThreadPool / CurrentThread 各有一份，互相是演进关系。

| 组件 | 来源 | 取舍 |
|---|---|---|
| `Thread` | 本仓库原有的 `net` 内部 `Thread` + game-server 的 `Thread` + wind-server 的 `prctl` 命名 | **以本仓库原有的为底**（创建失败返回 errno、不抛异常、`move_only_function`、析构时未 Join 即 FATAL），并入 game-server 的"`Start` 阻塞到 tid 就绪""绑核""未命名自动编号"，线程名用截断而不是失败（见 §2） |
| `this_thread` | game-server 的 `current_thread` | 保留 TLS 缓存 tid、fork 安全、`IsMainThread` 不发系统调用；线程名改成线程局部的定长缓冲；去掉 `SleepUs` / `Yield` / `TidString`（见 §2、§3） |
| `WaitGroup` | game-server 的 `wait_group.h`（语义对标 Go） | 保留 `WaitFor` / `WaitUntil`；计数为负由抛异常改成 `LOG_FATAL`（库内不抛） |
| `SpinLock` | game-server / wind-server 的 `spin_lock.h` | 改成先读后抢（TTAS）+ 指数退避 + `sched_yield` 兜底；去掉自带的 Guard 与宏（见 §2） |
| `ThreadPool` | game-server / wind-server 的 `thread_pool` | **重新设计**，见 §4 |
| `Mutex` / `Condition` | back-cpp 的 `Mutex.h` / `Condition.*` | **没搬**：比 `std::mutex` / `std::condition_variable` 差（见 §2） |
| `CountDownLatch` | wind-server | **没搬**：`std::latch`（计数固定、只等一次）与 `WaitGroup`（计数可增）已经覆盖 |

## 2. 在原代码里发现并处理的问题

- **`WaitGroup::Done` 无符号回绕**（back-cpp）：`std::max<uint32_t>(count_ - 1, 0)`，`count_` 为 0 时 `count_ - 1` 回绕成 4294967295，`max` 毫无作用，之后 `Wait` 永远不返回。现在计数是有符号的，降到负数即 FATAL（`wait_group_test` `TestNegativeCountIsFatal`）。
- **`Condition::WaitForSeconds` 用墙上时钟**（back-cpp）：`CLOCK_REALTIME`，系统改时间会让超时提前或延后；返回值是"是否超时"，和惯例相反；没有谓词循环（虚假唤醒会让调用方误判）。直接用 `std::condition_variable`（`wait_for` / `wait_until` 带谓词，steady 时钟）。
- **`SleepUs` 声称"不受信号中断影响"，实际没处理 `EINTR`**（game-server、wind-server）：`nanosleep` 被信号打断就提前返回。没有自己包一层，用 `std::this_thread::sleep_for`（libstdc++ 内部循环处理 `EINTR`）。
- **`~Thread` 未 Join 就静默 detach**（三代都一样；wind-server 的注释甚至写着"自动 join"，与代码相反）：线程继续运行，可能访问已经销毁的对象。现在析构时仍未 Join 是编程错误，FATAL（`thread_test` `TestMisuseIsFatal`）。
- **线程名超过 15 个字符时整个设置失败**（game-server 用 `pthread_setname_np` 且不检查返回值）：内核限制 15 个字符，超了返回 `ERANGE` 且一个字也不设，线程名就是创建者的名字。现在先截断再设（`thread_test` `TestName`）。wind-server 用的 `prctl(PR_SET_NAME)` 倒是会静默截断。
- **`catch` 之后再 `abort`，丢了现场**（三代都有）：进到 `catch` 时栈已经展开，之后打印的 backtrace 看不到抛出点。线程函数里不 catch，没有 handler 时直接 `std::terminate`，默认处理器会打印异常类型与 `what()`，core 里能看到抛出点。（库内不抛、不 catch 本来也是 `网络库设计.md` §4.11 的约定。）
- **未命名的线程继承创建者的名字**：`top` / `gdb` 里分不清谁是谁。现在自动命名 `Thread-N`（game-server 的做法，保留）。
- **线程名存成 `const char*`，指向线程数据里的 `std::string`**（game-server、back-cpp）：线程数据在线程结束时释放，之后指针悬空。现在存在线程局部的定长缓冲里。
- **`SpinLock` 纯忙等**：等待时每轮都 `test_and_set`（把缓存行在核间抢来抢去），没有退让——线程数多于核数、或持锁线程被调度出去时，会把整个时间片烧光，而持锁者恰恰拿不到 CPU 去释放锁。`spin_lock_test` `TestOversubscribed`（128 个线程、持锁时被换出）里去掉 `sched_yield` 兜底，30 秒内做不完。另外 `ATOMIC_FLAG_INIT` 在 C++20 已废弃，`CPU_PAUSE` 是未加前缀的宏。
- **`ThreadPool`**：见 §4。

## 3. 没搬的东西与原因

- **`Mutex` / `Condition`**：见 §1。如果以后要 clang 的线程安全注解（`-Wthread-safety`，`GUARDED_BY` 这类），那是给 `std::mutex` 包一层带 capability 注解的类型，是另一件事，不是这个 `Mutex.h`（它没有注解、不检查错误码）。
- **`CountDownLatch`**：见 §1。
- **`SleepUs` / `Yield`**：`std::this_thread::sleep_for` / `yield`。
- **`TidString` / `TidStringLen` 与导出的 TLS 字符串**：是作者自己的日志系统为了热路径格式化设计的；本仓库的 `base/logger` 不用它。`this_thread::Tid()` 的快路径仍然内联（`detail::t_tid` 是 `__thread`），需要字符串的调用方自己格式化。
- **`SpinLockGuard`**：`std::lock_guard<SpinLock>` / `std::scoped_lock` 就是。

## 4. `ThreadPool` 的设计

无 key 的任务进共享队列（`Post` / `Submit`），哪个线程空闲谁取；有 key 的任务进 `key % 线程数` 对应线程的专属队列（`PostKey` / `SubmitKey`），同 key 在同一线程按提交顺序串行（Actor 模式）。`Post` 不建 future，`Submit` 才返回 future。

**为什么不沿用"每线程一个自旋锁队列 + sleeping 标志"**
以下三条都在旧实现上实测复现过（把旧 `ThreadPool` 单独编出来跑）：
- 老实现把无 key 任务按轮询塞进某个线程的队列，那个线程被长任务占着时，队列里的后续任务就干等，别的线程却空闲——"自动负载均衡"其实是盲分配。2 个线程、一个被阻塞任务占住，再提交 100 个任务：1 秒后只完成了 50 个，另一半在被占线程的队列里（`thread_pool_test` `TestSharedQueueIsNotBlockedByBusyWorker`，把"盲分配"改回去会失败）。
- 老实现在 `Start` 之前或 `Stop` 之后提交会对 `workers_.size()` 即 0 取模：两种情形进程都以 SIGFPE（整数除零）退出。
- 老实现 `Stop` 排空时，任务里再投递的任务可能落到已经退出的线程的队列里，永远不执行（future 变 `broken_promise`）。4 个线程、每一跳换一个线程的 400 跳链，提交后立刻 `Stop`：200 次里 200 次丢了任务（期望执行 401 个，实际 1 个）。
- 唤醒靠"自旋锁 + `sleeping` 原子标志 + 睡前复查 + mutex/cv"三层配合，正确性依赖自旋锁的内存序恰好构成 Dekker 握手——能写对，但没有 TSAN 时我无法让人放心。

**现在的做法**：一把互斥锁保护全部队列与状态（共享队列、每线程的专属队列、空闲线程掩码、计数、状态机），每个线程一个条件变量。所有"该不该睡、该叫醒谁"的判断都在锁里，没有 Dekker，不存在丢唤醒。
- 空闲线程用一个 64 位掩码记录（所以最多 64 个线程）。无 key 任务入队时取最低的空闲位、清掉并唤醒它；同时到的另一个提交会挑下一个，不会重复叫醒同一个。有 key 任务只在它的线程空闲时才唤醒。忙着的线程做完手上的任务会回到循环顶部看队列，所以不需要唤醒。
- 线程先取自己的专属队列（只有它能做），再取共享队列。
- notify 在持锁时发出：`Stop` 的 join 要等工作线程拿到这把锁，所以被唤醒的线程对象一定还活着。

**停机语义**（状态机 Idle → Running → Stopping → Stopped）：`Stop` 之后外部的新提交被拒绝，但已经排队的、以及**运行中的任务再投递的**（本池工作线程里的提交，由 `thread_local` 识别）都会执行完；线程只在"状态是 Stopping、没有排队的、也没有运行中的任务"时退出——运行中的任务才可能再投递，所以要等它们做完。`outstanding_` = 排队 + 运行中，全在锁里计数，没有分布式终止判断的竞态。`thread_pool_test` `TestStopAllowsRepostFromTasks`（5000 深的链与 2047 个任务的扇出）与 `TestStopDrainsQueuedTasks` 覆盖。
- 被拒绝（没 Start、正在 / 已经 Stop、队列满）返回 `false` / 空 `optional`，任务当场销毁（不泄漏）。可选的 `max_pending` 给队列上限，由调用方决定丢弃、降级还是重试。
- `Stop` / `WaitIdle` 不能在本池的工作线程里调用（会 join / 等自己），FATAL。`Stop` 没有超时：任务必须会结束。

**已知局限**
- **不是无锁的**：所有提交与取任务经过同一把锁。下面的数据显示这对"微秒以上的业务任务"绰绰有余，但如果有每秒千万级的空任务，要用别的东西（每线程独立的无锁队列，或事件循环 + `base/queue`）。
- 没有工作窃取、没有优先级、没有动态伸缩线程数。有 key 任务堵在某个线程上时，那个线程的共享队列份额也被占着（共享队列里的任务会被别的线程取走，不受影响）。
- 同一 key 的串行只在同一个池、同一个线程数下成立（`key % 线程数`）。

## 5. 吞吐

空任务 200 万个，4 个工作线程，计时从开始提交到全部执行完；旧的是 `cpp-game-server-cpp` 的 `ThreadPool`（单独编出来对比）。i9-14900KF、WSL2、clang 23 Release，3 轮，下面是区间。单位 M task/s。

| 场景 | 旧：1 生产者 | 旧：4 生产者 | 新：1 生产者 | 新：4 生产者 |
|---|---|---|---|---|
| 无 key + future（旧 `Submit` 轮询 / 新 `Submit` 共享队列） | 0.14–0.16 | 0.93–1.77 | 0.33–0.36 | 1.6–1.8 |
| 无 key，不带 future（新 `Post`） | — | — | 1.6–1.9 | 3.8–4.1 |
| 有 key + future，key 随机分布（旧 `SubmitHash` / 新 `SubmitKey`） | 0.15–0.16 | 0.50–0.88 | 0.55–0.58 | 1.5–1.6 |
| 有 key，不带 future，key 随机分布（新 `PostKey`） | — | — | 2.1–2.3 | 3.3–3.4 |
| 有 key + future，**每个生产者恰好只碰一个线程的队列**（旧 `SubmitHash` / 新 `SubmitKey`） | 0.15–0.16 | **6.1–7.4** | 0.6 | 2.2 |
| 有 key，不带 future，同上（新 `PostKey`） | — | — | 2.3–2.5 | 4.6–4.8 |

怎么读：
- **真实用法（key 随机、多个生产者）新的比旧的快 2–3 倍**：旧实现每个线程的队列被多个生产者争抢同一个自旋锁。单生产者时旧实现每个任务都要唤醒一次休眠的线程（futex 系统调用），新的好 3–10 倍。
- **唯一旧实现更快的场景是"每个生产者恰好只碰一个线程的队列"**（旧 6–7M，新 4.6M）——每线程独立队列在没有任何争抢时确实更快，但这是 benchmark 排布出来的理想情形（`key = i`、4 个生产者按 `i += 4` 分配）。真实场景里 key 是玩家 ID 之类，不会恰好按生产者分区。
- 带 future 比不带慢 2–6 倍：future 的共享状态分配与同步，调用方不需要结果就用 `Post` / `PostKey`。
- 复现：`thread_pool_test --bench` 测新实现自己的吞吐；新旧对比用的是一个一次性的对比程序（把旧版本的源码拷出来与新版本编进同一个二进制），没有放进仓库。

## 6. 验证

测试在 `base/thread/`：`thread_test`（启停、tid 握手、命名与截断、绑核、创建失败、误用 FATAL）、`current_thread_test`（含 fork 后重置）、`spin_lock_test`（含线程数多于核数）、`wait_group_test`（含"等完立刻销毁"的循环）、`thread_pool_test`（key 串行、共享队列不被堵、队列上限、停机排空、多生产者压力、误用 FATAL）。
"必须 abort"的断言用 `fork` + `waitpid` 检查 `SIGABRT`（`thread_test_util.h`），要求调用时进程里没有别的线程。

**未验证**：TSAN（见开头）。上真机后重点看 `ThreadPool` 的 `mu_` 保护的各个字段（`state_` 另有无锁读）、`Thread::Start` 与新线程之间通过 `tid_` 的 `wait` / `notify`。
**没有测的**：线程创建失败（`RLIMIT_NPROC`）——本机是 root，不受限制，用例会跳过；`ThreadPool::Start` 中途失败的回滚路径因此也没有被执行过，只有代码审查。
