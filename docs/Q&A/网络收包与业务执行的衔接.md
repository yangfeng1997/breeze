# 网络收包与业务执行如何衔接？

## 问题

> 网络 IO 线程解析出完整的 payload 后，是在本 IO 线程执行，还是投递到业务线程池，还是开协程、每协程一个 handler？一些服务器框架或 RPC 框架都是怎么处理的？这个衔接是不是需要有一个抽象组件？

讨论以底层网络库的职责边界为起点，不以 `framework/` 下的现有实现作为设计前提。

## 简答

- 当前底层网络库解出完整消息后，**在接收消息的 IO 线程同步调用 `IConnectionHandler::OnMessage`**。
- 回调之后直接处理、投递到业务线程，还是创建协程，取决于接入方；网络库不自动做这些调度。
- **需要一个职责明确的衔接组件，但不一定需要通用执行器接口。** 当前 `IConnectionHandler` 已经提供了可替换边界，上层可以用一个实现该接口的网络事件投递器完成交接。
- 对本项目，建议业务状态和 handler 归主循环，阻塞操作与重计算才投线程池；网络库不内置业务线程池或协程运行时。

## 1. 完整消息不等于业务对象

假设线上格式是：

```text
[4 字节长度][业务 MsgHead][业务 Body]
```

内置 `LengthPrefixCodec` 负责检查长度、等待整帧完整，然后去掉 4 字节长度头，将剩余字节交给回调：

```text
OnMessage(connection, [业务 MsgHead][业务 Body])
```

这里的 `payload` 是**网络帧的 payload**，仍然可以包含业务消息头。网络库不自动识别 `msg_id`、`request_id`，也不自动将 Body 反序列化为 protobuf 对象。

业务协议可以集中在上层解析和派发，不必让每个业务 handler 重复拆头。自定义 codec 也可以承担 magic、版本等协议字段的校验，但当前通用 codec 的输出仍是一段字节，不是结构化的 `MsgHead + Body`。

代码：[LengthPrefixCodec::Decode](../../src/cpp/base/net/codec/length_prefix_codec.cpp)、[IFrameCodec](../../src/cpp/base/net/codec/frame_codec_interface.h)。

## 2. 常见执行模型

### 2.1 直接在 IO 线程执行

```text
IO 线程：收包 → 分帧 → 业务 handler → 继续处理 IO
```

muduo 的默认消息回调、Netty 未指定额外执行器的普通入站 handler，属于这一类。

- **优点**：没有额外的业务排队和线程切换，延迟低，消息所有权简单。
- **限制**：handler 不能阻塞或长时间计算，否则会拖住该 IO 线程上的其他连接。
- **适用**：协议网关、路由转发、轻量内存操作；复杂业务通常还要自行投递。

### 2.2 投递到业务线程池

```text
IO 线程：收包 → 分帧 → 请求任务入队
                              ↓
业务线程池：              执行 handler → 回包
```

很多 RPC 框架采用网络与业务执行分离的方式。例如，gRPC C++ 同步服务端由框架管理处理线程，不要求用户在底层 socket IO 回调里执行业务；Netty 也可以为指定 handler 配置额外的执行器组。具体排队与串行规则取决于框架和配置，不能把它们都等同于任意并发的普通线程池。

- **优点**：业务耗时不直接卡住网络读写，可以利用多核。
- **代价**：排队、线程间交接、请求对象生命周期，以及业务并发安全。

**同一连接按顺序收到 A、B，不代表投到普通线程池后，A、B 仍按顺序执行或完成。** 如果它们都修改同一个玩家状态，还需要串行队列、固定归属线程或锁。

### 2.3 投递到固定业务事件循环

```text
多个 IO 线程 → 消息队列 → 固定业务线程串行执行 handler
```

游戏服务器常采用这种方式：业务状态归一个执行线程所有，网络线程只负责输入输出。

- **优点**：业务状态不需要到处加锁，顺序与状态归属清晰。
- **限制**：不能在业务循环里阻塞；阻塞操作和重计算要另行 offload，再将结果投回来。

行业中也有多个独立业务执行域的设计，但线程数增加不等于可以任意并发操作同一份状态。**本项目不采用进程内多 Shard，扩容靠多进程或多服务实例。**

### 2.4 按连接或按请求使用协程

```text
收包 → 建立或唤醒协程 → 执行 handler
                         ↓ 等待异步操作时挂起
                       完成后恢复
```

需要区分两种粒度：

- **每连接一个协程**：通常循环读请求，不必然让同一连接内的请求并发。
- **每请求一个协程**：允许多个请求同时在途，顺序和共享状态需要另外管理。

例如，Go `net/http` 的 HTTP/1.x 服务通常由连接 goroutine 读请求并调用 handler；HTTP/2 则允许不同 stream 的 handler 并发执行。brpc 常见的服务处理路径使用 bthread 这种用户态调度任务，而不是每个请求创建一个 OS 线程。

**协程与“在哪个线程执行”不是互斥选项。** 协程仍然需要线程执行，可以调度到 IO 线程、业务线程池或固定业务线程。C++ 协程本身不会自动把阻塞调用变成异步，也不会自动解决数据竞争；计算耗时同样会占住承载它的线程。

以上是框架常见用法的对照，不表示这些框架只有一种执行模式。

## 3. 衔接组件要管什么？

可以称为“网络事件投递器”或“消息入口适配器”，核心不是替业务写一个 `thread_pool.Post(handler)`，而是明确以下契约：

| 职责 | 必须明确的规则 |
|---|---|
| 执行位置 | 留在 IO 线程，还是投到哪个业务线程 |
| 消息所有权 | 回调返回后消息是否仍有效，是否需要复制 |
| 顺序 | 按连接、玩家或其他 key 保序，还是允许并发 |
| 背压 | 队列满了暂停读、拒绝请求，还是关闭连接 |
| 生命周期 | 连接已关闭而任务仍排队时怎么办；停机时如何排空或取消 |

对当前网络库有两个直接约束：

1. `OnMessage` 的 `span` **只在回调期间有效**。只要延后执行，即使仍在同一 IO 线程上稍后执行，也不能直接保留这个视图，必须复制或转为有所有权的消息。
2. `IConnection&` 只能在所属 IO 线程使用；跨线程操作连接应使用 `ConnectionHandle`，不能把连接引用捕获进业务任务。

连接建立、消息、连接关闭也需要一起考虑。若承诺每连接保序，就必须避免关闭通知越过此前排队的消息；关闭是否取消未执行请求则是另一项需要显式规定的策略。

接口契约：[IConnectionHandler](../../src/cpp/base/net/connection/connection_handler_interface.h)。

## 4. 调度和消息派发是两个职责

- **调度**回答：在哪里、什么时候执行？
- **派发**回答：这是什么消息、交给哪个函数？

一种组织方式是：

```text
完整二进制消息
  → 执行位置与所有权交接
  → 解析 MsgHead，按 msg_id 找 handler
  → 解码 Body
  → 执行业务
```

这不是唯一顺序。如果选目标队列需要消息头里的路由 key，就要先提取它；轻量头部校验、消息号查找也可以在 IO 线程完成，而业务体反序列化留到目标线程。

**关键是区分“查到哪个 handler”和“立即执行这个 handler”。** IO 线程可以查表并投递，不代表允许它操作业务状态。

## 5. 本项目建议的边界

```text
base/net
  收包 → 分帧 → IConnectionHandler
                       │
                       ▼
网络事件投递器（实现 IConnectionHandler）
  取得消息所有权 → 背压 → 入主循环队列 → 唤醒
                       │
                       ▼
业务主循环
  消息协议解析 / msg_id 派发 → handler
                       │
                       └─ 阻塞或重计算 → ThreadPool
                                          ↓
                                      结果回主循环
```

上图强调执行边界，不强制所有协议解析都放在主循环。按项目设计，信封解析和消息号查表也可在 IO 侧完成，但业务 handler 仍由主循环执行。

- **底层网络库**：只承诺完整消息回调、回调所在 IO 线程和字节视图生命周期，不内置业务调度策略。
- **网络事件投递器**：负责网络事件的所有权、每连接顺序、入口背压和投递生命周期。
- **消息派发组件**：负责消息协议、消息号登记和 handler 查找，不因此拥有业务线程。
- **业务主循环**：拥有业务状态，执行 handler；线程池任务不直接修改模块或实体状态。

`IConnectionHandler` 已经是可替换接入点。当前只需要一个职责明确的具体投递器，**不需要为了兼容 IO 直跑、任意线程池和任意协程运行时，再增加通用的 `IExecutor` / `IExecutorProvider`**。

这里的主循环、消息派发和 offload 分层是设计建议与项目既定方向，不表示相关运行时均已实现。设计状态与约束见 [Actor与线程模型设计](../Actor与线程模型设计.md) §2～§4、§7，消息与 RPC 分层见 [RPC与IDL设计](../RPC与IDL设计.md)。
