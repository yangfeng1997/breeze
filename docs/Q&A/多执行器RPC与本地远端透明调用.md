# 多执行器下，消息解析、RPC 与本地远端透明调用如何配合？

## 问题

> 那是不是要在网络 IO 线程就要把消息解出来？然后按消息的 ID 派发到对应的执行器上然后执行，那 RPC 回包那些应该是多个执行器共用一个 RPC 组件吗？消息解析到底是在 IO 线程还是在业务线程？和 RPC 组件又该怎么配合？还有你上面说“如果以后确实出现多个非网络子系统也需要统一提交普通任务，再考虑下沉成通用任务执行接口”，这个通用的任务执行接口又是什么？如果需要支持不同执行器之间也能以 RPC 进行提交和通信，支持远端和本地透明，是不是就是这种场景？

前置讨论见 [网络收包与业务执行的衔接](网络收包与业务执行的衔接.md)。

**状态：讨论方案，未落地，也未替代现有设计基线。** 当前 [Actor与线程模型设计](../Actor与线程模型设计.md) 与 [RPC与IDL设计](../RPC与IDL设计.md) 规定业务 handler 在主循环执行，工作线程只做 offload，不引入通用执行器。本文讨论扩大需求后可以采用的结构；真正落地前需要同步修订线程归属、保序、RPC 完成与生命周期契约。

## 简答

需求已经不只是“网络消息转投业务线程”，而是“多种执行环境之间的异步 RPC 运行时”。在这个前提下，引入一个小而明确的执行器接口是合理的。

需要分开三个概念：

1. **消息协议**：这是什么消息，是请求还是响应？
2. **RPC 语义**：请求对应哪个响应，谁负责超时、取消和完成？
3. **执行调度**：handler 和完成回调分别在哪里执行？

建议逻辑上共用一套 RPC 运行时。网络入口解析用于路由的头部，业务 Body 在最终处理它的执行环境解码；请求按服务方法选择执行器，响应按挂起调用选择完成执行器。本地与远端统一由 RPC 路由层实现，而不是把执行器变成远程执行器。

## 1. 消息解析分三层

| 层次 | 解析什么 | 建议位置 |
|---|---|---|
| 网络分帧 | 长度、完整帧、传输协议字段 | IO 线程 |
| 消息信封 / RPC 头 | Request/Response、方法 ID、调用 ID、状态、超时信息等 | 接收入口；网络路径通常在 IO 线程 |
| 业务 Body | protobuf 请求或响应对象 | 最终处理该消息的执行器 |

```text
IO 线程
  读数据 → 分帧 → 校验信封并解析 RPC 头
                         │
                         ├─ Request → 找到服务方法及其执行目标
                         │               ↓
                         │           投递到目标执行器
                         │               ↓
                         │           解码 Body → handler
                         │
                         └─ Response → 交给 RPC 完成处理
```

“在 IO 线程先解出来”需要明确解到哪一层：

- **解出用于路由的头部：是。**
- **把整个 protobuf 业务对象也解出来：通常不需要。**

如果路由依赖 Body 里的字段，可以通过生成的轻量提取逻辑或额外解析获得；不应默认在 IO 线程进行完整业务解码。

跨线程交接前，消息必须取得独立所有权，不能继续引用 IO 读缓冲。当前底层回调提供的临时视图契约见 [IConnectionHandler](../../src/cpp/base/net/connection/connection_handler_interface.h)。本地入口不经过网络 IO 线程，但应复用后续派发规则。

## 2. 请求与响应走不同的派发逻辑

### 2.1 请求按服务方法找执行器

服务注册表可以是：

```text
method_id → {
    请求处理入口,
    请求/响应 codec,
    执行器
}
```

例如：

```text
Move      → 主循环执行器
Compress  → 计算线程池执行器
Query     → 查询线程池执行器
```

目标由服务端注册信息决定，不让网络对端任意指定本地执行器。服务表在启动前冻结，接收线程只读查表。

### 2.2 响应按调用 ID 找挂起调用

```text
call_id → {
    超时与取消状态,
    响应解码入口,
    完成回调,
    完成回调执行器
}
```

**响应不能简单按 `method_id` 再派发到服务端 handler 的执行器。** 同一个方法可能由主循环、线程池中的多个请求并发调用，每次调用的响应接收位置可能不同。

调用身份和匹配规则还应结合调用源、会话代次等信息，避免不同调用者或旧连接的调用 ID 冲突。网络对端提供的关联字段也必须与合法的来源和挂起状态核对。

## 3. 多个执行器可以共用一个 RPC 运行时

**推荐逻辑上共用一套 `RpcRuntime`，但不要让所有线程随意读写同一张挂起表。** 共用组件不等于内部所有状态都并发访问。

第一版可以采用“一个状态归属线程 + 可跨线程调用的入口”：

```text
RpcRuntime
  ├─ 冻结后只读的服务方法表
  ├─ 可跨线程调用的 Call / Complete / Cancel 入口
  └─ owner 线程独占：
       挂起表、调用 ID 分配、超时定时器、终态仲裁
```

owner 初期可以就是主循环，不必额外创建线程。

- 工作线程调用 `Call()`：入口把操作投给 owner，owner 登记挂起项后才发送请求。
- 工作线程调用 `ReplyHandle::Complete()`：通过安全入口交接应答，不直接操作 owner 的可变状态。
- owner 处理响应、超时和取消的竞争，每次调用只产生一个最终结果。

这样可以避免一开始就做带锁的全局挂起表或复杂分片。

**owner 只做轻量控制操作，不执行业务 handler，也不做大 Body 的反序列化。** 调用入口的接纳额度应覆盖尚未进入挂起表的调用，不能在 owner 前面再建立一条无界队列。

这条路径会让 owner 成为所有 RPC 完成的调度依赖；如果主循环阻塞，超时处理和响应交付也会延迟。以后测出瓶颈时，可以调整内部状态归属，不必改变业务调用 API。

## 4. 一次完整调用的流转

假设主循环 A 调用在线程池 B 执行的服务：

```text
A 发起 Call
  → 编码请求
  → RpcRuntime owner 登记挂起项
      保存：完成回调 + A 的执行器
  → 路由到 B
  → B 解码请求，执行 handler
  → B 调用 ReplyHandle::Complete
  → 响应进入 RpcRuntime owner
  → 匹配 call_id，仲裁响应/超时/取消
  → 把完成任务投给 A 的执行器
  → A 解码响应，执行完成回调
```

这里有三个不同的位置：

| 位置 | 谁决定 |
|---|---|
| 被调用方法在哪里执行 | 服务注册时指定的执行器 |
| RPC 状态在哪里修改 | `RpcRuntime` 的状态归属 |
| 调用结束后在哪里继续 | 此次调用指定的完成执行器 |

三者可以不同。工作线程中的 handler 也可以继续发起异步 RPC，但必须明确完成回调的执行目标，不能笼统地说“回原线程”：

- 主循环是固定线程，可以明确回去。
- 普通线程池不是固定线程，回到同一线程池不代表回到同一工作线程。
- 需要串行状态归属时，应指定串行执行环境，不能依赖普通线程池的调度结果。

线程池 handler 不得因此直接访问主循环拥有的实体、模块或 Lua 状态。即使是同一个执行器，异步等待期间也可能执行其他任务，不能把串行任务执行误认为整个异步调用不可交错。

**不要在线程池中阻塞等待另一个 RPC。** 池中线程全部等待同池后续任务时会产生死锁或饥饿。

## 5. 通用任务执行接口是什么？

它只回答一个问题：**把一段本地代码交给某个执行环境，稍后执行。**

以下仅为接口示意，不是现有 API：

```cpp
using Task = std::move_only_function<void()>;

class IExecutor
{
public:
    virtual ~IExecutor() = default;

    virtual PostResult TryPost(Task task) noexcept = 0;
};
```

具体适配器可以是：

```text
主循环适配器 → 入主循环任务队列并唤醒
线程池适配器 → 投递到已有线程池
```

`IExecutor` 不认识消息 ID、protobuf、远端节点、RPC 调用 ID，也不认识请求和响应。

它可以同时供网络入口、RPC 完成处理、文件读取完成通知等使用，因此称为“通用任务执行接口”。它只统一投递能力，不统一主循环、线程池和协程运行时的全部管理接口。

第一版应明确以下契约：

- `TryPost` 可跨线程调用，不等待队列空位。
- **不在调用栈内直接执行任务**，避免本地路径产生意外重入。
- 返回已接受、过载、停止等明确结果。
- 调用即转移任务所有权，拒绝时任务被销毁。
- 已接受任务在停机时执行还是取消，必须有明确规则；需要取消通知的上层不能只依赖静默销毁闭包。
- 通用接口不承诺串行、固定线程或完成顺序，这些由具体执行器保证。
- 任务异常策略需要明确；`TryPost` 的 `noexcept` 只约束提交入口，不代表任务本身不会抛异常。

任务队列的条数上限不能替代 RPC payload 的字节预算，大消息仍需要入口额度控制。运行时持有的执行器引用和 handler 注册项也必须在所有在途调用结束前保持有效。

## 6. 本地与远端透明由 RPC 路由层实现

这是使用通用执行接口的场景之一，但**执行器只负责本地执行，不负责远程调用**。

不能把下面这种本地闭包直接变成跨机器提交：

```cpp
executor.TryPost([&] { /* 本地任务 */ });
```

闭包里的指针、引用和对象状态无法自然地发送到远端。跨执行器 RPC 应使用服务方法与有所有权的请求数据；跨机器时再按协议编码，而不是传输任意闭包。

本地与远端透明应建立在服务寻址和 RPC 传输选择上：

```text
统一的 RPC Call(service, method, request)
                   ↓
                 路由解析
             ┌─────┴─────┐
             ▼           ▼
          本地端点     远端端点
             │           │
        本地消息交接   编码信封并发送
             │           │
             └─────┬─────┘
                   ▼
             目标 RPC 入口
                   ↓
           找到方法绑定的执行器
                   ↓
               执行 handler
```

调用者通常指定服务或对象，而不是指定“远端某个线程池”。多个执行器使用同一套 RPC 能力，不要求每个执行器各自部署一个 RPC 运行时。

### 6.1 本地路径也保留 RPC 语义

本地调用可以省去 socket，但建议仍然：

- 异步入队，不直接调用 handler；
- 登记挂起调用；
- 使用相同的超时、取消、错误与过载规则；
- 使用相同的服务方法注册和执行器选择；
- 明确请求对象的所有权。

为减少本地与远端行为差异，第一版可以统一使用编码后的 Body，本地只省去传输；以后再增加类型化的本地快速路径。

**透明的是调用 API 和主要语义，不是“远端调用与本地函数调用完全一样”。** 超时不代表对方没有执行，取消不保证撤销已经发生的副作用；调用方完成状态唯一，也不等于业务操作天然具备恰好一次语义。重试与幂等必须另行设计。

## 7. RPC 完成通知不能随手丢弃

如果响应、超时和取消完成也无条件挤普通业务队列，队列满时直接丢弃，就会出现：

```text
请求已经完成
  → 完成回调投递失败
  → 调用者永远不知道结果
```

需要为完成通知提供可靠交付策略，例如：

- 限制最大在途调用数，并预留与其配套的完成通知容量；
- 请求接纳时取得完成额度，直到完成回调交付后再释放；
- 停机时先停止新调用，再完成或取消在途调用，最后停止完成执行器；
- 为晚到响应、重复完成和提交失败保留明确的丢弃、计数或错误路径。

这不是执行器接口单独能解决的问题，而是 RPC 运行时、配额与执行器生命周期的共同契约。不能在投递失败时临时改为 IO 线程直接执行用户回调，那会破坏调用方的线程归属。

## 8. 推荐职责划分

| 组件 | 核心职责 |
|---|---|
| 网络库 | 收发、分帧、连接 |
| 消息入口 / 路由层 | 信封校验、本地或远端交接 |
| `RpcRuntime` | 调用关联、超时取消、请求派发、完成路由 |
| `IExecutor` 及适配器 | 把本地任务安排到指定执行环境 |
| 生成代码 / codec | 请求和响应的类型化编解码 |
| 业务服务 | 实现方法，不处理 IO 交接细节 |

这套结构不要求引入 Actor、进程内多 Shard 或位置迁移机制。游戏状态仍可由单个主循环独占，线程池只执行明确满足并发与状态隔离要求的方法。

落地前至少需要修改和验证：

- 现有“所有 handler 在主循环执行”及“工作线程不发起或处理 RPC”的限制；
- 不同执行器之间不再保证同一连接的业务执行全序；
- Lua 状态及其引用仍受创建线程归属约束，不能直接投到任意线程池；
- 响应、超时、取消竞争只产生一个最终结果；
- 本地调用与远端调用都异步完成，不因本地优化引入重入；
- 队列满、执行器停止、连接断开、晚到响应和停机期间仍能交付或明确终结在途调用。

## 补充：RPC 状态归属与多执行器使用入口

### 追问

> 就算是本地 RPC 调用，也保留 RPC 语义，都使用编码后的 Body，统一方式，等后面压测数据再优化，框架设计时先不用考虑。
>
> 多个执行器可以共用一个 RPC 运行时，这种是不是有问题？因为 RPC 只能放在一个执行器上。

### 本地与远端统一编码

**本地、远端 RPC 都使用编码后的 Body，走统一的异步请求/响应语义；当前设计不考虑本地对象直传等优化，等压测数据再决定。** 这明确了 §6.1 中原本作为建议提出的选择。

### 1. RPC 的可变状态必须有明确归属

前文“多个执行器共用一个 RPC 运行时”的表述需要区分**使用入口**和**状态归属**。

如果 RPC 采用单线程状态模型，那么这些内容必须由同一个串行执行上下文管理：

- 挂起调用表；
- 调用 ID 分配；
- 超时定时器；
- 响应、超时、取消的终态仲裁。

其他执行器不能直接操作这些状态。

归属单位是“串行执行上下文”，不只是随便一个 `IExecutor`。**普通线程池允许任务并发，不能直接承载一套假定单线程访问的 RPC 状态。**

因此，“RPC 只能放在一个执行器上”，对于这套单线程状态模型，可以理解为：

> 一个 RPC 状态实例只能归属于一个确定的串行执行上下文。

这不等于只有那个上下文才能发起或处理 RPC。

### 2. 多个执行器使用 RPC，不代表共同操作 RPC 对象

建议区分以下对象：

| 对象 | 线程契约 |
|---|---|
| `RpcRuntime` / `RpcModule` | 固定归属于主循环，管理 RPC 状态 |
| `RpcClient` 之类的调用入口 | 可跨线程提交调用，不直接操作挂起表 |
| `ReplyHandle` | 可从处理请求的执行器提交应答，内部安全交接 |
| 业务 handler | 在注册时指定的执行器上执行 |

```text
主循环 ─────────────┐
计算线程池 ─────────┼─ 通过安全入口提交命令
查询线程池 ─────────┘             │
                                ▼
                     主循环上的 RpcRuntime
                     挂起表 / 超时 / 终态仲裁
```

**共享的是 RPC 能力，不是共享对内部可变状态的访问权。** 安全入口必须实现跨线程入队和生命周期保护，不能只是给普通成员函数换个名字。上述名称是设计角色，不表示已有对应实现。

### 3. 服务方法执行位置与 RPC 状态归属是两件事

例如，主循环调用一个计算服务：

```text
主循环上的 RpcRuntime
  登记挂起调用
  → 本地路由，交付编码后的请求 Body
  → 计算线程池解码请求
  → 执行计算 handler
  → 编码响应
  → ReplyHandle 提交响应
  → 主循环上的 RpcRuntime 匹配调用
  → 主循环执行完成回调
```

计算 handler 运行期间，不持有或修改 RPC 挂起表。

如果计算线程池中的 handler 还要调用下游服务：

```text
计算线程池
  → 通过调用入口提交请求
  → 主循环上的 RpcRuntime 登记并发送
  → 收到响应，主循环仲裁完成
  → 投递到指定的完成执行器
```

这里仍然只有一套 RPC 状态。

**回调在线程池执行，也不表示挂起表搬到了线程池。** RPC 在 owner 上取出挂起项、确定最终结果，再把有所有权的完成任务交给线程池。

### 4. 不必按执行器数量配置 RPC 实例

每个执行器各放一套 RPC 是另一种架构，不是支持线程池 handler 的必然要求：

```text
一个主循环执行器 → 一个确定的串行上下文
一个普通线程池执行器 → 多个可能并发的工作线程
```

不能机械地按照“每个 `IExecutor` 一个 RPC 实例”分配，否则线程池内部仍然会并发访问同一个实例。

如果确实需要多个独立 RPC 状态实例，归属单位应是明确的串行上下文，还要增加响应归属路由、调用身份区分、各自定时器与停机管理。不应仅为了增加线程池执行能力就提前引入这些机制。

### 5. 当前建议

**先保留一个主循环归属的 `RpcModule`，增加跨线程调用和应答入口；允许服务方法和完成回调投递到其他执行器。**

| 边界 | 选择 |
|---|---|
| RPC 状态归属 | 主循环 |
| 服务执行位置 | 服务注册决定 |
| 完成回调位置 | 调用时明确指定，默认主循环 |
| 本地 / 远端选择 | 路由层决定 |
| Body 格式 | 统一编码后的字节 |

代价是所有调用登记、响应和超时仲裁都依赖主循环，主循环阻塞会拖住 RPC 控制流程。因此主循环必须保持非阻塞，后续再用压测判断这条控制路径是否需要独立出来。

前文“共用运行时”的准确含义是：

> 多个执行器可以通过线程安全入口使用同一个、固定归属主循环的 RPC 运行时；不能在多个执行器上直接并发执行它的状态管理逻辑。
